# Автоотклики

**Слой:** `hrwork/application/apply/`. Playwright + Chromium с persistent-профилем.

> ⚠ Единственная подсистема, которая совершает **необратимые внешние действия** — отправляет
> реальные отклики работодателям от имени пользователя. Любая правка здесь проверяется на
> живом прогоне с `--apply-limit 1..5`, а не «должно работать».

## Назначение

Раз в 90 минут: поднять резюме в поиске, отобрать подходящие вакансии, откликнуться,
отправить сопроводительное письмо в чат.

## Цели и потолки

- ~200 откликов в сутки (`HH_DAILY_APPLY_CAP`) — лимит HH, равномерно по окну 10:00–23:30
- поднятие резюме — не чаще раза в 4 часа (`BUMP_COOLDOWN_H`)
- строгие кандидаты уходят первыми, простоя между тирами нет

## User flow крон-прогона

`run()` — `autoclick.py::run`

```
run()
 -> _hang_watchdog()                       # внешний дедлайн, см. ниже
 -> _single_instance(retries=6, wait=60)   # ждёт lock до ~6 мин
 -> _launch()                              # persistent-контекст data/browser_profile
 -> _logged_in()
      | ok   -> session.save_state()       # выгрузка кук -> data/hh_state.json
      | fail -> _auto_login()
                  | fail -> SystemExit «запусти --login»
 -> if do_bump and (force_bump or bump_due()):
        bump_resumes()  -> >0 -> mark_bumped()
 -> if do_apply:
        _sync_applied_from_chats()         # реконсиляция marks, cookie-only
        _apply_batch()                     # основной цикл
        _drain_pending()                   # очередь из ленты
 -> finally: ctx.close()
```

Выгрузка кук на каждом успешном входе — то, что позволяет синку и чату работать
**без браузера**.

### Внутри `_apply_batch` (`autoclick.py::_apply_batch`)

1. `eff = min(apply_limit or 10, daily_cap - used)`; `eff <= 0` -> выход.
2. Пул = `pick_candidates(..., limit=eff * POOL_MULT)`, запас ×5 — пропуски (архив, внешний
   сайт, «уже откликались») не должны тратить лимит.
3. Цикл до `len(applied) >= eff`, пауза 4–9 с между откликами.

**Инвариант: marks / квота / журнал пишутся сразу, поштучно** (`autoclick.py::_apply_batch`).
18.07 они писались в конце батча — прогон умер в середине, 21 реальный отклик ушёл
работодателям, а система о них не знала и предлагала те же вакансии снова.

### Исход одной вакансии (`apply_one`, `autoclick.py::apply_one`)

```
_goto(url)
 -> нет кнопки отклика 8с? -> есть 'view-topic'? -> ALREADY : SKIP
 -> текст кнопки /тест|опрос/ и FORMS_LLM НЕ задан      -> FORM   (крон-дефолт: в очередь)
 -> click -> подтвердить модалку релокации
 -> url /applicant/vacancy_response + 'task-question' (или кнопка-опросник):
      FORMS_LLM НЕ задан                               -> FORM   (в очередь, человек)
      FORMS_LLM=1 -> forms.try_autofill: пробел/пусто   -> FORM   (лог пробелов, в очередь)
                                          все поля решены -> заполнить+письмо+«Откликнуться» -> (верификация ниже)
 -> иначе обычный отклик: submit disabled и есть поле письма? -> вписать письмо
                          click submit
 -> ждём 10с 'view-topic' или «Вы откликнулись» -> APPLIED : SKIP (+ строка в лог, почему)
```

**Формы-анкеты (RFC-003, `docs/rfc-003-form-fill.md`).** По умолчанию (`FORMS_LLM` не задан) анкеты уходят
в форм-очередь. **С 28.07 крон-путь откликов идёт С флагом**: `cron/cron_apply.bat` выставляет
`FORMS_LLM=1` — исходное «не в кроне» из RFC-003 отменено осознанно, потому что без флага очередь росла
быстрее, чем вычерпывалась (за ночь 59 -> 60 при 21 снятом: каждый слот докидывал новые опросники).
Условие, при котором это стало безопасно, — покрытие словаря: `form_answers` закрывает 177 полей из 179.
Инвариант не тронут: `try_autofill` шлёт ТОЛЬКО при полноте, любой пробел -> вакансия в очередь.
При `FORMS_LLM=1` заполнение идёт inline в отклике:
резолв каждого поля из словаря `form_answers`/фактов резюме/LLM; отправка ТОЛЬКО при полноте (иначе лог
пробелов + очередь). Машинный инвариант: у LLM нет execution-канала (стоки — DOM-литерал/print). Бэклог
очереди догоняется `hh.py forms` (тот же авто-путь; `--dry` — превью).

Гейт держит **вызывающий**, а не `form_fill`: функции слоя чистые (юнит-тестируемые без окружения),
поэтому `forms::_resolve` не зовёт `answer_quiz` при пустом `resume_ctx` — а пустым он приходит ровно
при выключенном `FORMS_LLM` (`_dry_preview`). Без этой проверки `--dry` ходил бы в провайдера мимо гейта:
`answer_quiz` контекст не проверяет сам, в отличие от `answer_field`.

Словарь `resume_profile.json::form_answers` — **данные, но с поведением**: `q` это регекс, и первая
запись, чей ответ проходит membership по опциям поля, выигрывает. Отсюда два правила:
- ветки-однословки пишутся с границами (`\bочно\b`): без них `очно` матчилось внутри «нагруз**очно**м»
  и офисный отказ подменял ответ по существу в поле со свободным вводом (инцидент 27.07, `docs/errors.md`);
- на вопрос, встречающийся и текстом и радио, кладутся ДВЕ записи подряд — сначала развёрнутый текст,
  следом точная подпись опции: для радио первая отсеется по membership, для textarea сработает она.

`ApplyOutcome` (`outcome.py::ApplyOutcome`): `APPLIED` / `ALREADY` / `FORM` / `SKIP`.
`ApplyChannel` (`outcome.py::ApplyChannel`): `CRON` / `FEED` / `HH` (ручной отклик, подхваченный синком).

Транспортные состояния воркера (`busy` / `no-session` / `queued` / `error`) в эти VO
намеренно **не входят** — это состояния доставки, другой концепт.

Селектор submit — **одна CSS-строка с запятой**, а не кортеж (`autoclick.py::_RESPONSE_SUBMIT`).
Кортеж перебирался бы посимвольно, и `locator('a')` кликал cookie-ссылку, порождая лавину вкладок.

Письмо в модалку отклика **по умолчанию не пишется** — оно уходит после отклика через
`chatik /save`, правя сообщение-отклик. У работодателя это выглядит как сопроводительное,
а не как реплика в чат.

**Исключение — обязательное письмо** (`autoclick.py::_fill_letter_if_required`, с 04.08.2026).
Часть работодателей помечает сопроводительное обязательным: пока поле пустое, HH отдаёт кнопку
«Откликнуться» с `disabled`. Клик по ней падает по таймауту, исключение подавлено, подтверждение
не приходит — отклик молча не уходит. Поэтому: **кнопка disabled + поле письма на странице ->
вписываем письмо и только потом жмём submit**. Там, где кнопка активна, поведение прежнее.

Текст берётся лениво (`cover.build_cover`) и только в этой ветке: до неё доходят лишь живые
вакансии, где отклик реально идёт, поэтому режим `llm` не тратит запрос на архив и пропуски.
`chatik /save` после отклика всё равно выполняется и перезаписывает тот же текст — идемпотентно.

## Отбор кандидатов

`candidates.py` — чистая функция, без браузера, полностью покрыта тестами.

### `ApplyTier` (`candidates.py::ApplyTier`)

`IntEnum`, значение = приоритет очереди:

- `STRICT = 1` — ядро `RESUME_CORE` (Python/FastAPI), удалёнка
- `WIDE = 2` — широкий стек `APPLY_CORE_WIDE` (Django/Flask/SQL/очереди), удалёнка
- `OFFICE = 3` — любой из стеков, офис в `APPLY_OFFICE_CITIES`

«Не подходит» = `None`, а не магический `0`.

Все три набора — из `resume_profile.json` (`core` / `core_wide` / `office_cities`), значения
выше лишь дефолты. `"office_cities": []` выключает `OFFICE` целиком — см. `config.md`.

**Про `OFFICE`:** это НЕ готовность к переезду. Кандидат живёт в Тольятти и ищет удалёнку;
крупные города в списке потому, что там офисная по описанию вакансия с большой вероятностью
допускает удалённый формат. Это ставка на переговоры.

**Гибрид** (`flexible`) без текстовых маркеров удалёнки идёт по офисной ветке — гибрид
требует ходить в офис, это осознанная семантика (`candidates.py::_apply_tier`).

### Порядок фильтров в `pick_candidates`

Строго по коду (`candidates.py::pick_candidates`):

1. `source != "hh"` — автоклик только под HH
2. уже в `marks`
3. в `form_ids` (при `APPLY_SKIP_FORMS`)
4. `not role.is_it`
5. опыт не в `APPLY_EXPS` (`None` тоже не проходит)
6. **`out_of_scope(v.name)`** — ОДНА проверка по тайтлу вместо прежней лестницы отдельных
   `if` на каждый чёрный список; правила и их порядок — в таблице `_SCOPE_RULES`, см. ниже
7. `role is QA` — роль-детектор ловит то, чего нет в тайтле; исключение для инженерных
   гибридов сюда **не** распространяется
8. `role is ANALYST` и в тайтле нет `APPLY_TARGET_ENGINEERING`
9. гост (`is_ghost`, висит > 60 дней)
10. `_apply_tier(...) is None`

Сортировка: `(tier, опыт, возраст)` — строгие раньше, младший грейд раньше, свежее раньше.
Неизвестный опыт и отсутствующий возраст уезжают в конец.

Пункты 6–8 — **предпочтения пользователя**, а не таксономия рынка. Они живут в apply-слое
именно поэтому: домен классифицирует «что это за вакансия», apply решает «хотим ли мы туда».

### `OutOfScope` и таблица `_SCOPE_RULES`

`out_of_scope(name) -> OutOfScope | None` (`candidates.py::out_of_scope`) — **единый источник
правды о том, что вакансия вне целевой специализации**, для обоих путей отклика: и для отбора
кандидатов (`pick_candidates`), и для чистки форм-очереди (`forms.clean_queue`). Раньше
очередь анкет жила по своим правилам и копила то, на что отклик всё равно не пошёл бы: на
07.08.2026 из 78 накопленных 32 были QA, аналитиками и руководителями — они лежали неделями
и попадали в каждый прогон.

Причина — **VO, а не строка-литерал** (`candidates.py::OutOfScope`): она уходит в логи и в
сводку чистки очереди, то есть это доменное понятие с конечным набором значений. Значение
enum = подпись для человека (`.label`): `senior/lead` · `руководящая` ·
`не инженерная роль` · `QA` · `аналитик` · `ML/DS` · `DevOps/SRE` · `другой язык`.
`clean_queue` печатает по ним `Counter` — видно, чем именно забивалась очередь.

Правила заданы **таблицей `(причина, предикат)`, а не лестницей `if`** — порядок значим и
виден целиком:

1. `SENIOR` — `APPLY_SENIOR_BLACKLIST`: senior/сеньор/ведущий/старший/тимлид/lead/principal/staff
2. `MANAGEMENT` — `_is_management` (см. ниже)
3. `NON_ENGINEERING` — `APPLY_ROLE_BLACKLIST`: риск-аналитик/портфельный/планирование ресурсов
4. `QA` — `APPLY_QA_BLACKLIST`, **безусловно**: стоит ДО аналитики и ML именно потому, что
   исключение для инженерных гибридов на него не распространяется
5. `ANALYST` — `APPLY_ANALYST_BLACKLIST` при отсутствии `APPLY_TARGET_ENGINEERING` в тайтле
6. `ML` — `APPLY_ML_BLACKLIST` при том же условии
7. `DEVOPS` — `APPLY_DEVOPS_BLACKLIST` при отсутствии `_CODE_MARKER` (см. ниже)
8. `OTHER_LANG` — `APPLY_LANG_BLACKLIST` при отсутствии «python» в тайтле: Java/C#/C++/PHP/
   Go/Scala/Ruby/Kotlin/Rust/1С/.NET (JS/TS/React **не** блокируют — Python-fullstack допустим)

**Новое правило = строка в таблице плюс член `OutOfScope`.** Ветвление трогать не нужно —
в этом весь смысл таблицы.

**Ограничение: только по тайтлу, и это намеренно.** В форм-очереди кроме имени и ссылки
ничего нет, а поднимать ради чистки весь кеш вакансий (395 МБ) незачем. Проверки, которым
нужна доменная `Vacancy` — роль, грейд, свежесть, стек, — остаются в `pick_candidates`
(пункты 4, 5, 7–10 выше).

`APPLY_ROLE_BLACKLIST`: целимся в роль, не в домен.

### `APPLY_SKIP_FORMS`

Вакансии-опросники бот не заполняет. Раньше они не исключались, и очередь упиралась в них
каждый прогон — 19.07 из 56 кандидатов 21 был опросником, отклики не двигались.

Исключение идёт через **форм-очередь** (`form_vacancies.json`), а не через `marks`: в ленте
они остаются с бейджем «форма», отказом не помечаются, и фильтр снимается одним флагом.

## Синхронизация статусов — без браузера

`sync_statuses()` (`autoclick.py::sync_statuses`) работает поверх `data/hh_state.json` через httpx.
Chromium не запускается, **lock не берётся**.

Причина: раньше синк вставал в очередь за откликами, и зависший браузер морозил статусы
неделями (наблюдалось: статусы стояли с 05.07).

Один запрос `chat_data` на чат даёт сразу три вещи:

1. статусы откликов -> `response_status.json`
2. дожурналирование новых откликов с **реальной датой** — включая сделанные руками на hh.ru
   (любой отклик создаёт чат)
3. переписку -> `chat_messages.json`

Плюс отметка всех чатов в marks как `applied`: иначе `pick_candidates` выбирал их снова, и бот
тратил ~20 с на загрузку страницы ради вердикта «уже откликались».

### Инкремент по умолчанию, `--sync-full` — полная ветка

Список чатов (`chat.py::list_chats`) отдаёт `lastMessageTime` (creationTime последнего
сообщения) — по нему `autoclick.py::_sync_from_cache` решает, качать ли переписку.
Потолок страниц выводится из числа известных откликов (`len(applied_ids())/20 + запас`,
минимум 120): магический дефолт 30 однажды уже резал корпус на ~600 при 1287 реальных.
Чат берётся из кеша только при **всех трёх** условиях:

1. он уже в кеше **с непустой перепиской** и в журнале (пустая кешевая запись — артефакт
   неудачного фетча, её перекачиваем, иначе заморозится навсегда);
2. кешевый статус **терминальный** (`chat.py::TERMINAL_STATES`: все `DISCARD_*` + `HIRED`
   — назад не флипаются; единый словарь состояний с воронкой);
3. последнее сообщение старше `SYNC_FRESH_DAYS = 7` дней.

Иначе качаем (`chat_data`). Потерь корректности нет: новое сообщение в старом чате
обновляет `lastMessageTime` в списке -> чат синкается; молчаливый флип статуса (отказ
без письма — ~20 % отказов) возможен только у нетерминальных, а их качаем всегда.
Любое сомнение (битая/наивная метка, нет в кеше) — качаем.

**Запись — merge поверх кеша, не replace** (в обоих режимах): `msgs_out`/`statuses`
стартуют с кешевой копии, прогон обновляет поверх. Сетевой сбой одного чата
(`chat_data -> {}`) или `limit` не стирают ранее известное — раньше перезапись файла
целиком теряла записи при любой дырке в прогоне.

**Почему не `lastActivityTime`.** Поле из списка выглядит идеальным сигналом, но его
обновляет само наше чтение `chat_data`: после полного синка 23.07 84 % чатов значились
«активными за сутки», при том что у 676 из 1287 последнее сообщение старше недели.
Самоотравляющийся сигнал — ежедневный крон-синк держал бы все чаты вечно «свежими».

Экономия на замере 23.07: ~333 скипа из 1287 (~26 %, ~5 мин); растёт по мере старения
корпуса — каждый отказ через неделю тишины уходит в кеш навсегда. Полный прогон:
~50 чатов/45 с, на 1287 чатах ~20 мин. `python hh.py autoclick --sync-full` игнорирует
кеш целиком — на случай подозрения, что кеш разъехался.

## Защита от зависаний

Корневая причина найдена по стеку 19.07: `page.wait_for_selector(_HH_ROOT, timeout=20_000)`
внутри `_goto` простоял **50 минут**. Таймауты Playwright исполняет node-драйвер; когда
связка драйвер/CDP клинит, Python блокируется в `_sync()` на трубе навсегда, и собственный
таймаут не спасает.

Три эшелона:

1. **Playwright-таймауты** 6–20 с — работают, пока драйвер жив
2. **`ApplyWorker.RESULT_TIMEOUT = 600`** — HTTP-поток не ждёт вечно
3. **Watchdog** — единственная защита от клина драйвера:
   - `WATCHDOG_DUMP_S = 40 мин` -> `faulthandler.dump_traceback_later`, стек в stderr,
     прогон продолжается (диагностика)
   - `WATCHDOG_KILL_S = 50 мин` -> `taskkill /F /T /PID <свой pid>`, фолбэк `os._exit(1)`

**Почему не хватило `ExecutionTimeLimit` планировщика.** Он снимает только `.bat`; python,
node и chromium осиротевают и продолжают держать профиль и lock — 19.07 после «завершения»
задачи жило 10 процессов. `taskkill /T` по собственному pid снимает всё дерево.
50 минут < 60 минут лимита задачи, чтобы watchdog сработал первым.

### Допустимый опыт шире, чем в резюме

`candidates.py::APPLY_EXPS` = грейды из `resume_profile.json` **плюс** `APPLY_EXTRA_EXPS`
(сейчас «3–6 лет»). Расхождение сознательное: профиль описывает реальный опыт и кормит
процент совпадения в ленте — задерёшь его, и матч начнёт врать; отбор под отклик отвечает
на другой вопрос, «куда имеет смысл писать», а вилку «3–6 лет» массово ставят на мидл-позиции.

Замер 27.07, зачем понадобилось: с одними junior-грейдами в пуле оставалось **296 кандидатов**
— меньше пяти дней работы при темпе ~62 отклика в сутки. С «3–6 лет» пул **1532**
(STRICT 461 · WIDE 292 · OFFICE 779). Очередь при этом не портится: сортировка идёт
tier -> грейд -> свежесть, поэтому junior разбирается первым, а старшая вилка — только когда
младшие кончились.

### Почему пул маленький

Воронка от «удалёнка + junior» (все порталы, 10 764) до кандидатов, замер 27.07:

- **−7 325 не HH** — talanto/hirify, автоклик туда не умеет (Playwright проходит фингерпринт
  только на HH). Это две трети потерь
- −1 134 роль не IT, −476 уже отмечено, −373 доменный аналитик, −398 другой язык в тайтле,
  −131 senior/ML, −76 гост, −50 форм-очередь
- **−755 стек не наш** — из оставшихся 798 удалённых junior-вакансий ядро/широкий стек
  только у 43

Отсюда практический вывод: удалёнка под наш стек на HH — это десятки вакансий, а не тысячи;
основной объём даёт офисная ветка в четырёх городах.

## Single-instance lock

`data/autoclick.lock` = `{pid, ts}`, TTL 4 часа.

TTL должен покрывать самый долгий прогон (батч 25 откликов ~30 мин, полный на 200 — до ~4 ч).
Меньший TTL ложно счёл бы живой батч протухшим -> второй Chromium на один persistent-профиль
-> краш.

Основная проверка — **живость pid** (`lock.py::_pid_alive`): `OpenProcess` на Windows, фолбэк
`os.kill(pid, 0)`. Открытия хендла НЕДОСТАТОЧНО — на убитом процессе `OpenProcess` успевает,
пока чужой хендл держит его объект, поэтому спрашивается `GetExitCodeProcess`: живым считается
только `STILL_ACTIVE` (259). Без этого осиротевший lock блокировал отклики 3 часа (25.07,
`errors.md`).

Прогон, снимаемый watchdog'ом, отдаёт lock сам (`lock.py::release_if_mine`) — иначе
`taskkill /T` убивает процесс раньше `finally`. Снимается только собственный файл: pid в
lock сверяется с `os.getpid()`.

TTL страхует лишь случаи, где живость определить нельзя: переиспользование pid и процесс,
вышедший с кодом ровно 259.

Битый или недописанный JSON не считается «свободным» вслепую: возраст берётся по mtime,
свежий -> вероятно живой писатель.

Кто как берёт: крон — до 6 минут ожидания (сервер ленты держит профиль ~300 с);
`login()` — без ожидания; `ApplyWorker` — 2 коротких ретрая, дальше честный `busy`
(30-минутный батч в HTTP-запросе не переждать); `sync_statuses` — не берёт вовсе.

## Квота

`data/apply_quota.json` = `{date, count}`. `applied_today()` возвращает `count`, только если
`date == сегодня` — запись за прошлый день молча трактуется как 0, счётчик самосбрасывается
без отдельной крон-задачи очистки.

Известная слабость: `bump_quota` — read-modify-write без файловой блокировки. Практической
гонки нет, потому что писатели разведены общим lock'ом, но защиты на уровне файла тоже нет.

## Кулдаун поднятия резюме

`data/bump_state.json` = `{last_ok: ISO}`, `BUMP_COOLDOWN_H = 4`.

Гейт нужен потому, что отклики идут каждые 90 минут — без него тяжёлая страница
`/applicant/resumes` грузилась бы впустую на каждом слоте.

**Инвариант:** `mark_bumped()` только при `bump_resumes() > 0`. Функция возвращает `-1`, если
страница не отрисовалась (DDoS-Guard / деградированный headless), и `0` при реальном кулдауне
HH — в обоих случаях кулдаун **не взводится**, попробуем на следующем слоте.

Селектор — по токену `button[data-qa~="resume-update-button"]` + гард по тексту «в поиске»,
чтобы не нажать платную «Поднять автоматически».

## Ошибки

Разделение принципиальное: **ошибка навигации -> `SKIP` и идём дальше**, ошибка инфраструктуры
-> прогон падает.

- `_goto` — всё в `suppress`, 3 попытки, пауза 6 с при DDoS-Guard. `page.title()` обёрнут
  отдельно: при DDG-навигации контекст рушится («Execution context was destroyed») и голый
  `title()` уронил бы весь прогон
- `apply_one` timeout -> `ALREADY` / `SKIP`, не исключение
- `_apply_batch` ловит исключение вокруг `apply_one` -> warning, цикл продолжается
- `cover.llm_cover` при любой ошибке -> фолбэк на шаблон, отклик всё равно уходит
- `SystemExit` при занятом lock — ловится **явно** в `apply_vacancy` и `ApplyWorker`
  (-> `busy`), в `run()` не ловится: крон-прогон просто выходит

**Протухшая сессия неотличима от пустого результата** — принято осознанно
(`session.py::open_client`): вызовы `chat.*` вернут пусто, а куки обновит следующий браузерный
прогон. Диагностика только через лог «чаты не получены, сессия от <дата> могла протухнуть».
