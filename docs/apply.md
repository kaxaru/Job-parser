# Автоотклики

**Слой:** `hrwork/application/apply/`. Playwright + Chromium с persistent-профилем.

> ⚠ Единственная подсистема, которая совершает **необратимые внешние действия** — отправляет
> реальные отклики работодателям от имени пользователя. Любая правка здесь проверяется на
> живом прогоне с `--apply-limit 1..5`, а не «должно работать».

## Назначение

Раз в 90 минут: поднять резюме в поиске, отобрать подходящие вакансии, откликнуться,
отправить сопроводительное письмо в чат.

## Цели и потолки

- ~200 откликов в сутки (`HH_DAILY_APPLY_CAP`) — лимит HH, равномерно по окну 10:00–23:30
- **~45 откликов за скользящие 24 часа** (`HH_APPLY_ROLLING_CAP`) — второй, НЕ документированный
  HH потолок: выше него HH перестаёт подтверждать отклики, хотя суточная квота ещё не выбрана
  (замер и доказательства — `errors.md`, 23.09.2026). Цель прогона = `min(лимит, дневной
  остаток, остаток окна)`, окно считается по журналу `applied_log.jsonl`
  (`runtime/quota.py::applied_in_window`); окно заполнено целиком — прогон не начинается
- поднятие резюме — не чаще раза в 4 часа (`BUMP_COOLDOWN_H`)
- строгие кандидаты уходят первыми, простоя между тирами нет

Потолок — на АККАУНТ, у каждого свой файл квоты. С 21.09.2026 отклики идёт только `acc2`
(основной приостановлен: `--daily-cap 0` в `cron_apply.bat`, `operations.md`), и его лимиты:
три слота в сутки по 10 откликов, `--daily-cap 60`. Упор при этом в ПУЛ, а не в лимит: пока
пул не пуст, откликов столько, сколько в нём вакансий, дальше — сколько добавляет рынок.

Лимит 20 за прогон стоял 22.09.2026 («10 мало») и откатан 23.09.2026 по замеру: три слота по
20 = до 60/сутки, а HH перестаёт подтверждать отклики уже на ~48 за сутки. С 10 за прогон
три слота дают до 30/сутки и до потолка окна не доводят.

## User flow крон-прогона

`run()` — `autoclick.py::run`

Когти отклика разнесены по модулям (аудит 22.09.2026, §5 — из `autoclick.py` был god-модуль):
`browser.py` (браузер, вход, поднятие резюме), `selectors.py` (селекторы отклика + бюджет
подтверждения), `hh_sync.py` (синк чатов без браузера), `worker.py` (тёплый воркер сервера),
`runtime/watchdog.py` (дедлайн прогона). В `autoclick.py` остаётся сам ОТКЛИК — `apply_one`
с его селекторами и таймингами (прямой запрет CLAUDE.md: выстраданы инцидентами), батч,
дренаж очереди и вход `run`.

```
run()
 -> watchdog._hang_watchdog()              # внешний дедлайн, см. ниже
 -> lock._single_instance(retries=6, wait=60)   # ждёт lock до ~6 мин
 -> browser._launch()                      # persistent-контекст data/browser_profile
 -> browser._session_state(page)           # LoginState: LOGGED_IN / ANONYMOUS / UNKNOWN
      | UNKNOWN   -> SystemExit            # страница не доехала (DDoS-Guard/сеть): НЕ логинимся,
      |                                    #   EXPIRED не пишем — иначе ложный «нужен вход»
      | ANONYMOUS -> browser._auto_login() # по ACCOUNT.login: password(main)/phone(SMS)/manual
      |             | fail -> session_status «expired» + SystemExit «запусти --login»
      | LOGGED_IN -> session.save_state()  # выгрузка кук -> data/hh_state.json (tmp + os.replace)
 -> account_session.verify_session()       # личность сессии == пин аккаунта, иначе SystemExit
 -> if do_bump and (force_bump or bump_due()):
        browser.bump_resumes()  -> >0 -> mark_bumped()
 -> if do_apply:
        _sync_applied_from_chats()         # реконсиляция marks, cookie-only
        _apply_batch()                     # основной цикл
        _drain_pending()                   # очередь из ленты
 -> finally: ctx.close()
```

Выгрузка кук на каждом успешном входе — то, что позволяет синку и чату работать
**без браузера**. Пишется она АТОМАРНО (`session.save_state` -> временный путь + `os.replace`):
Playwright файл пишет сам, а синк в другом процессе читает его без lock, и недописанный JSON
стоил бы всего синка («Нет сохранённой сессии»).

### Внутри `_apply_batch` (`autoclick.py::_apply_batch`)

1. `used = hh_sync._reconciled_today()` — счётчик, **выровненный по журналу** перед стартом
   (см. «Квота»); `eff = min(apply_limit or 10, daily_cap - used)`; `eff <= 0` -> выход.
   Затем `rolling = quota.applied_in_window(store.applied_log())` — отклики за скользящие 24ч;
   `eff = min(eff, HH_APPLY_ROLLING_CAP - rolling)`, остатка нет -> прогон не начинается вовсе
   (23.09.2026: HH перестаёт подтверждать отклики выше ~48 за сутки, а прогон этого не видел
   и кликал в стену — 33 попытки подряд). Дренаж очереди ленты гейтится тем же остатком.
2. Пул = `pick_candidates(..., inputs=ab_split.pool_inputs(split), limit=eff * POOL_MULT)`,
   запас ×5 — пропуски (архив, внешний сайт, «уже откликались») не должны тратить лимит;
   занятые другими аккаунтами вакансии отсеиваются (RFC-004). `PoolInputs` — VO одной тройкой
   (`marks`/`taken`/`ab_reject`) вместо трёх параметров с распаковкой по позиции.
3. Цикл до `len(applied) >= eff`, пауза 4–9 с между откликами. Перед каждым кликом —
   повторная проверка «не занята ли другим аккаунтом» с диска.
   Два предохранителя от холостого прогона: `APPLY_SKIP_STREAK_MAX` (50) — серия «кнопки
   отклика нет» (архив/внешний сайт), и `APPLY_UNCONFIRMED_STREAK_MAX` (5) — серия «клик был,
   подтверждения нет» (упор в потолок окна либо залипший `disabled` сабмит). Второй порог
   малый намеренно: в здоровых прогонах таких отказов 0–1, а упор даёт десятки подряд.
4. Итоговая строка прогона (`autoclick.py::_run_summary`) — **единственный сигнал деградации**:
   `Итог прогона: откликов N, анкет F, пропусков M (скип/отклик R), уже откликались K`
   (+ `, не подтвердилось U`, если такие были; + `, писем не доставлено L`).
   Ориентиры: `R <= 1.5` норма, `R >= 5` разбираться, `F/N >= 2` разбираться; в этих случаях
   строка уходит уровнем WARNING. Анкеты попали в строку потому, что они не отклик и не
   пропуск: прогон «3 отклика, 20 анкет, 0 пропусков» выглядел здоровым, а темп падал.
   Число `U` печатается, но само по себе WARNING не включает: единичный случай — норма,
   серия рвёт прогон предохранителем. Формат менялся 08.08.2026 и 23.09.2026 — тем, кто
   грепает лог, шаблон надо поправить.

**Инвариант: marks / квота / журнал пишутся сразу, поштучно** (`autoclick.py::_apply_batch`).
18.07 они писались в конце батча — прогон умер в середине, 21 реальный отклик ушёл
работодателям, а система о них не знала и предлагала те же вакансии снова.

С 23.09.2026 эта тройка (и снятие анкеты) идёт через **одну точку** —
`store.commit_applied(vid, *, name, url, employer, via, ab=None, drop_form=False)`
(`runtime/store.py::ApplicationStore.commit_applied`): до неё «отметка -> квота -> журнал»
были написаны трижды (`_apply_batch`, `_apply_one_vacancy`, `forms.run`) и уже разошлись —
feed-путь не писал долю A/B (`ab`) в журнал. Порядок внутри точки: снять анкету (если
`drop_form`) -> отметка -> квота -> журнал. Возвращает `applied_today()`. Наблюдаемость
по-прежнему одна на прогон (`_run_summary`), полнота точки закрыта
`tests/backend/application/test_commit_applied.py`.

### Исход одной вакансии (`apply_one`, `autoclick.py::apply_one`)

```
_goto(url)
 -> нет кнопки отклика 8с? -> есть 'view-topic'? -> ALREADY : SKIP
 -> текст кнопки /тест|опрос/ и FORMS_LLM НЕ задан      -> FORM   (крон-дефолт: в очередь)
 -> click -> подтвердить модалку релокации
 -> url /applicant/vacancy_response + 'task-question' (или кнопка-опросник):
      FORMS_LLM НЕ задан                               -> FORM   (в очередь, человек)
      FORMS_LLM=1 -> forms.try_autofill: пробел/пусто   -> FORM   (лог пробелов, в очередь)
                                          все поля решены -> заполнить+письмо+«Откликнуться» -> (верификация ниже)
 -> иначе обычный отклик: submit disabled и есть поле письма? -> вписать письмо
                          click submit
 -> ждём 12с 'view-topic' или «Вы откликнулись» -> APPLIED : UNCONFIRMED (+ строка в лог, почему)
```

`UNCONFIRMED` (клик был, подтверждения нет) отделён от `SKIP` (откликнуться НЕЛЬЗЯ: архив,
внешний сайт, опросник) 23.09.2026. До этого оба шли под общим `skip`, и 33 отказа подряд
выглядели как «много архивных вакансий»: прогон шёл в стену 18 минут, а счётчик прогона
не отличал упор в потолок HH от мусора в пуле. В ленте `unconfirmed` имеет свою подпись
(`outcome.py::APPLY_LABELS`), поэтому человек видит «⚠ не подтвердилось — клик ушёл, ответа
HH нет» вместо «пропущено (внешний/архив/опросник)».

**Капча — стоп всего прогона, а не пропуск вакансии.** `_goto` первым делом проверяет
`browser.py::is_captcha` (HH уводит на `/account/captcha`): исход `ApplyOutcome.CAPTCHA`
останавливает батч целиком — каждый следующий клик под капчей только укрепляет бот-флаг HH
(инцидент 28.07: 35 карточек «перемолоты» до watchdog).

**Формы-анкеты (RFC-003, `docs/rfc-003-form-fill.md`).** По умолчанию (`FORMS_LLM` не задан) анкеты уходят
в форм-очередь. **С 28.07 крон-путь откликов идёт С флагом**: `cron/cron_apply.bat` выставляет
`FORMS_LLM=1` — исходное «не в кроне» из RFC-003 отменено осознанно, потому что без флага очередь росла
быстрее, чем вычерпывалась (за ночь 59 -> 60 при 21 снятом: каждый слот докидывал новые опросники).
Условие, при котором это стало безопасно, — покрытие словаря: `form_answers` закрывает 177 полей из 179.
Инвариант не тронут: `try_autofill` шлёт ТОЛЬКО при полноте, любой пробел -> вакансия в очередь.
При `FORMS_LLM=1` заполнение идёт inline в отклике:
резолв каждого поля из словаря `form_answers`/фактов резюме/LLM; отправка ТОЛЬКО при полноте (иначе лог
пробелов + очередь). Машинный инвариант: у LLM нет execution-канала (стоки — DOM-литерал/print). Бэклог
очереди догоняется `hh.py forms` (тот же авто-путь; `--dry` — превью).

Гейт держит **вызывающий**, а не `form_fill`: функции слоя чистые (юнит-тестируемые без окружения),
поэтому `forms::_resolve` не зовёт `answer_quiz` при пустом `resume_ctx` — а пустым он приходит ровно
при выключенном `FORMS_LLM` (`_dry_preview`). Без этой проверки `--dry` ходил бы в провайдера мимо гейта:
`answer_quiz` контекст не проверяет сам, в отличие от `answer_field`.

Словарь `resume_profile.json::form_answers` — **данные, но с поведением**: `q` это регекс, и первая
запись, чей ответ проходит membership по опциям поля, выигрывает. Отсюда два правила:
- ветки-однословки пишутся с границами (`\bочно\b`): без них `очно` матчилось внутри «нагруз**очно**м»
  и офисный отказ подменял ответ по существу в поле со свободным вводом (инцидент 27.07, `docs/errors.md`);
- на вопрос, встречающийся и текстом и радио, кладутся ДВЕ записи подряд — сначала развёрнутый текст,
  следом точная подпись опции: для радио первая отсеется по membership, для textarea сработает она.

`ApplyOutcome` (`outcome.py::ApplyOutcome`): `APPLIED` / `ALREADY` / `FORM` / `SKIP` /
`UNCONFIRMED` (клик был, подтверждения нет) / `CAPTCHA` (HH увёл на `/account/captcha` —
прогон останавливается целиком).
`ApplyChannel` (`outcome.py::ApplyChannel`): `CRON` / `FEED` / `HH` (ручной отклик, подхваченный синком).

Транспортные состояния доставки запроса — отдельный VO `TransportStatus` (`outcome.py::TransportStatus`):
`queued` / `busy` / `no-session` / `taken` / `error`. Это состояния ДОСТАВКИ, а не исход отклика,
поэтому в `ApplyOutcome` они намеренно **не входят** — другой концепт. Подписи обоих наборов для
ленты лежат в `outcome.py::APPLY_LABELS` (ключ — код `ApplyOutcome` ИЛИ `TransportStatus`) и
уезжают в JS мостом `APPLY_LABELS_PY` (`feed.py::build_feed`); полнота словаря закрыта
`tests/backend/application/test_outcome_labels.py`.

Селектор submit — **одна CSS-строка с запятой**, а не кортеж (`selectors.py::RESPONSE_SUBMIT`).
Кортеж перебирался бы посимвольно, и `locator('a')` кликал cookie-ссылку, порождая лавину вкладок.
Там же лежат поле письма (`selectors.RESPONSE_LETTER`, без тег-квалификатора: тот ломается при
смене контрола и молча пропустил бы ОБЯЗАТЕЛЬНОЕ письмо), маркеры успеха и **единый бюджет
подтверждения** `selectors.CONFIRM_BUDGET_S` с единственной функцией ожидания
`selectors.wait_response_confirmed`. До 23.09.2026 селекторы были продублированы в `autoclick`
и `forms` и **уже разошлись** (с `textarea` против без), а бюджет расходился (10 с против
6×2 с), причём тексты логов жёстко зашивали числа: HH меняет разметку — замечает один путь,
второй молча перестаёт вписывать письмо. Взят больший бюджет (12 с) — объединение не имеет
права ужесточать обязательный путь; расширение только уменьшает ложные SKIP (подтверждение
на 11-й секунде уже стоило недосчитанной квоты, см. «Квота»).

Письмо в модалку отклика **по умолчанию не пишется** — оно уходит после отклика через
`chatik /save`, правя сообщение-отклик. У работодателя это выглядит как сопроводительное,
а не как реплика в чат.

**Исключение — обязательное письмо** (`autoclick.py::_fill_letter_if_required`, с 04.08.2026).
Часть работодателей помечает сопроводительное обязательным: пока поле пустое, HH отдаёт кнопку
«Откликнуться» с `disabled`. Клик по ней падает по таймауту, исключение подавлено, подтверждение
не приходит — отклик молча не уходит. Поэтому: **кнопка disabled + поле письма на странице ->
вписываем письмо и только потом жмём submit**. Там, где кнопка активна, поведение прежнее.

Текст берётся лениво (`cover.build_cover`) и только в этой ветке: до неё доходят лишь живые
вакансии, где отклик реально идёт, поэтому режим `llm` не тратит запрос на архив и пропуски.
`chatik /save` после отклика всё равно выполняется и перезаписывает тот же текст — идемпотентно.

## Отбор кандидатов

`candidates.py` — чистая функция, без браузера, полностью покрыта тестами.

### `ApplyTier` (`candidates.py::ApplyTier`)

`IntEnum`, значение = приоритет очереди:

- `STRICT = 1` — ядро `RESUME_CORE` (Python/FastAPI), удалёнка
- `WIDE = 2` — широкий стек `APPLY_CORE_WIDE` (Django/Flask/SQL/очереди), удалёнка
- `OFFICE = 3` — любой из стеков, офис в `APPLY_OFFICE_CITIES`

«Не подходит» = `None`, а не магический `0`.

Все три набора — из `resume_profile.json` (`core` / `core_wide` / `office_cities`), значения
выше лишь дефолты. `"office_cities": []` выключает `OFFICE` целиком — см. `config.md`.

**Про `OFFICE`:** это НЕ готовность к переезду. Кандидат ищет удалёнку;
крупные города в списке потому, что там офисная по описанию вакансия с большой вероятностью
допускает удалённый формат. Это ставка на переговоры.

**Гибрид** (`flexible`) без текстовых маркеров удалёнки по умолчанию идёт офисной веткой
(только `APPLY_OFFICE_CITIES`). Ключ профиля `accept_hybrid` (RFC-004) это меняет: с ним гибрид
берётся в ЛЮБОМ городе (частично из дома) — так нишу расширяет второй аккаунт, а основной
(ключа нет) не меняется (`candidates.py::_apply_tier`, `config.md`).

### Порядок фильтров в `pick_candidates`

Строго по коду (`candidates.py::pick_candidates`):

1. `source != "hh"` — автоклик только под HH
2. уже в `marks`
3. занята другим аккаунтом (`taken`, RFC-004)
4. доля другого аккаунта по A/B-сплиту (`ab_reject`, RFC-004)
5. в `form_ids` (при `APPLY_SKIP_FORMS`)
6. работодатель в блок-листе (`employer_blocked`, см. «Блок-лист работодателей» ниже)
7. `not role.is_it`
8. опыт не в `APPLY_EXPS` (`None` тоже не проходит)
9. **`out_of_scope(v.name)`** — ОДНА проверка по тайтлу вместо прежней лестницы отдельных
   `if` на каждый чёрный список; правила и их порядок — в таблице `_SCOPE_RULES`, см. ниже
10. `role is QA` — роль-детектор ловит то, чего нет в тайтле; исключение для инженерных
    гибридов сюда **не** распространяется
11. `role is ANALYST` и в тайтле нет `APPLY_TARGET_ENGINEERING`
12. роль вне белого списка `APPLY_ROLE_SET` (только когда он задан — RFC-004)
13. задан `APPLY_DEVELOPER_TITLE`, а `«Разработчик»` в тайтле не назвал своего слова (RFC-004)
14. гост (`is_ghost`, висит > 60 дней, при `APPLY_SKIP_GHOSTS`)
15. `_apply_tier(...) is None` — стек/формат/город

Сортировка: `(tier, опыт, возраст)` — строгие раньше, младший грейд раньше, свежее раньше.
Неизвестный опыт и отсутствующий возраст уезжают в конец.

Пункты 6 и 9–11 — **предпочтения пользователя**, а не таксономия рынка. Они живут в apply-слое
именно поэтому: домен классифицирует «что это за вакансия», apply решает «хотим ли мы туда».

Первая сработавшая проверка — это и есть причина отсева: `pick_candidates(..., stats=)` копит
счётчики по `candidates.py::_reject_reason`, их печатает `hh.py autoclick --dry-pool`. Каждая
причина — именованная константа `candidates.py::REASON_*` (не литерал): набор эксплуатационной
наблюдаемости `autoclick.py::_POOL_WATCH_REASONS` собирается из них, поэтому переформулировка
причины не гасит строку отсева молча (аудит 22.09.2026, §3.2).

### Блок-лист работодателей (`APPLY_EMPLOYER_BLOCKLIST`)

Работодатели, куда не откликаемся ни с какого аккаунта (RFC-004). Список живёт в `.env`, а не в
профиле резюме: он общий для всех аккаунтов, а в репозитории пуст. Разделитель `;` — запятая
встречается в самих названиях («Ромашка, Управляющая компания»).

- **Целое слово, без учёта регистра:** `K7` ловит «K7 Tech» и «K7, Медиа», но не «BMK7».
- **Похожие буквы свёрнуты с обеих сторон** (`candidates.py::_fold_employer`): в кеше HH один и
  тот же работодатель встречается и с латинской, и с кириллической «К»/«Х»/«С». Свёртка
  касается ТОЛЬКО сравнения названий работодателей — к тайтлам её применять нельзя, она
  сломала бы русские чёрные списки («тестировщ», «стажёр»).
- **Проверка стоит на всех путях отклика**, а не только на отборе: лента и очередь ожидания
  идут мимо `pick_candidates` (`autoclick.py::_apply_one_vacancy` возвращает `skip` без клика —
  дренаж считает запись обработанной), дренаж анкет проверяет перед открытием страницы и
  снимает такую анкету из очереди (`forms.py::run`). `forms.py::clean_queue` блок-лист не
  проверяет: работодателя в очереди нет, а кеш вакансий чистка не поднимает (см. ниже).

Какие написания пойманы, видно до первого отклика: `hh.py autoclick --dry-pool` печатает строку
`блок-лист работодателей:` с каждым совпавшим названием из кеша HH.

### `OutOfScope` и таблица `_SCOPE_RULES`

`out_of_scope(name) -> OutOfScope | None` (`candidates.py::out_of_scope`) — **единый источник
правды о том, что вакансия вне целевой специализации**, для обоих путей отклика: и для отбора
кандидатов (`pick_candidates`), и для чистки форм-очереди (`forms.clean_queue`). Раньше
очередь анкет жила по своим правилам и копила то, на что отклик всё равно не пошёл бы: на
07.08.2026 из 78 накопленных 32 были QA, аналитиками и руководителями — они лежали неделями
и попадали в каждый прогон.

Причина — **VO, а не строка-литерал** (`candidates.py::OutOfScope`): она уходит в логи и в
сводку чистки очереди, то есть это доменное понятие с конечным набором значений. Значение
enum = подпись для человека (`.label`): `lead и выше` · `стажировка` ·
`инженерия не про софт` · `эксплуатация, не разработка` · `руководящая` ·
`не инженерная роль` · `QA` · `аналитик` · `ML/DS` · `DevOps/SRE` ·
`безопасность, не разработка` · `геймдев-движок` · `другой язык`.
`clean_queue` печатает по ним `Counter` — видно, чем именно забивалась очередь.

## Синхронизация статусов — без браузера

`sync_statuses()` (`hh_sync.py::sync_statuses`) работает поверх `data/hh_state.json` через httpx.
Chromium не запускается, **lock не берётся**.

Причина: раньше синк вставал в очередь за откликами, и зависший браузер морозил статусы
неделями (наблюдалось: статусы стояли с 05.07).

Один запрос `chat_data` на чат даёт сразу три вещи:

1. статусы откликов -> `response_status.json`
2. дожурналирование новых откликов с **реальной датой** — включая сделанные руками на hh.ru
   (любой отклик создаёт чат)
3. переписку -> `chat_messages.json`

Плюс отметка всех чатов в marks как `applied`: иначе `pick_candidates` выбирал их снова, и бот
тратил ~20 с на загрузку страницы ради вердикта «уже откликались».

### Инкремент по умолчанию, `--sync-full` — полная ветка

Список чатов (`chat.py::list_chats`) отдаёт `lastMessageTime` (creationTime последнего
сообщения) — по нему `hh_sync.py::_sync_from_cache` решает, качать ли переписку.
Обход идёт по КУРСОРУ `chats.nextFrom` и прекращается на пустой странице, повторе chatId
или при `pages` максимум. Потолок страниц выводится из числа известных откликов
(`len(applied_ids())/20 + запас`, минимум 120): магический дефолт 30 однажды уже резал
корпус на ~600 при 1287 реальных. До 21.09.2026 здесь стоял `&page=N`, который chatik
игнорировал (`errors.md`, «Синк чатов ходил по кругу»).
Чат берётся из кеша только при **всех трёх** условиях:

1. он уже в кеше **с непустой перепиской** и в журнале (пустая кешевая запись — артефакт
   неудачного фетча, её перекачиваем, иначе заморозится навсегда);
2. кешевый статус **терминальный** (`chat.py::TERMINAL_STATES`: все `DISCARD_*` + `HIRED`
   — назад не флипаются; единый словарь состояний с воронкой);
3. последнее сообщение старше `SYNC_FRESH_DAYS = 7` дней.

Иначе качаем (`chat_data`). Потерь корректности нет: новое сообщение в старом чате
обновляет `lastMessageTime` в списке -> чат синкается; молчаливый флип статуса (отказ
без письма — ~20 % отказов) возможен только у нетерминальных, а их качаем всегда.
Любое сомнение (битая/наивная метка, нет в кеше) — качаем.

**Запись — merge поверх кеша, не replace** (в обоих режимах): `msgs_out`/`statuses`
стартуют с кешевой копии, прогон обновляет поверх. Сетевой сбой одного чата
(`chat_data -> {}`) или `limit` не стирают ранее известное — раньше перезапись файла
целиком теряла записи при любой дырке в прогоне.

**Почему не `lastActivityTime`.** Поле из списка выглядит идеальным сигналом, но его
обновляет само наше чтение `chat_data`: после полного синка 23.07 84 % чатов значились
«активными за сутки», при том что у 676 из 1287 последнее сообщение старше недели.
Самоотравляющийся сигнал — ежедневный крон-синк держал бы все чаты вечно «свежими».

Экономия на замере 23.07: ~333 скипа из 1287 (~26 %, ~5 мин); растёт по мере старения
корпуса — каждый отказ через неделю тишины уходит в кеш навсегда. Полный прогон:
~50 чатов/45 с, на 1287 чатах ~20 мин. `python hh.py autoclick --sync-full` игнорирует
кеш целиком — на случай подозрения, что кеш разъехался.

## Защита от зависаний

Корневая причина найдена по стеку 19.07: `page.wait_for_selector(_HH_ROOT, timeout=20_000)`
внутри `_goto` простоял **50 минут**. Таймауты Playwright исполняет node-драйвер; когда
связка драйвер/CDP клинит, Python блокируется в `_sync()` на трубе навсегда, и собственный
таймаут не спасает.

Три эшелона:

1. **Playwright-таймауты** 6–20 с — работают, пока драйвер жив
2. **`ApplyWorker.RESULT_TIMEOUT = 600`** — HTTP-поток не ждёт вечно
3. **Watchdog** — единственная защита от клина драйвера:
   - `WATCHDOG_DUMP_S = 40 мин` -> `faulthandler.dump_traceback_later`, стек в stderr,
     прогон продолжается (диагностика)
   - `WATCHDOG_KILL_S = 50 мин` -> `taskkill /F /T /PID <свой pid>`, фолбэк `os._exit(1)`

**Почему не хватило `ExecutionTimeLimit` планировщика.** Он снимает только `.bat`; python,
node и chromium осиротевают и продолжают держать профиль и lock — 19.07 после «завершения»
задачи жило 10 процессов. `taskkill /T` по собственному pid снимает всё дерево.
50 минут < 60 минут лимита задачи, чтобы watchdog сработал первым.

### Допустимый опыт шире, чем в резюме

`candidates.py::APPLY_EXPS` = грейды из `resume_profile.json` **плюс** `APPLY_EXTRA_EXPS`
(сейчас «3–6 лет»). Расхождение сознательное: профиль описывает реальный опыт и кормит
процент совпадения в ленте — задерёшь его, и матч начнёт врать; отбор под отклик отвечает
на другой вопрос, «куда имеет смысл писать», а вилку «3–6 лет» массово ставят на мидл-позиции.

Замер 27.07, зачем понадобилось: с одними junior-грейдами в пуле оставалось **296 кандидатов**
— меньше пяти дней работы при темпе ~62 отклика в сутки. С «3–6 лет» пул **1532**
(STRICT 461 · WIDE 292 · OFFICE 779). Очередь при этом не портится: сортировка идёт
tier -> грейд -> свежесть, поэтому junior разбирается первым, а старшая вилка — только когда

## Несколько аккаунтов: вход и личность (RFC-004)

Один процесс — один аккаунт (`HR_ACCOUNT`, см. `config.md`). Отклики второго аккаунта идут
тем же путём, но с тремя жёсткими ограничениями.

- **Способ входа выбирается по аккаунту** — поле `login` в `account.json`, диспетчеризация в
  `browser.py::_auto_login`, куда сходятся `run`, `ApplyWorker._run` и `login`.
  Три способа:
  - `password` — **только у `main`**: автомат по `HH_EMAIL`/`HH_PASSWORD` из `.env`. Ни один
    дополнительный аккаунт этот способ не получает (`resolve_account` его отвергает) — иначе
    форма входа второго аккаунта заполнилась бы учёткой основного.
  - `phone` — авто-вход по телефону+SMS (`_phone_login`): «Войти» → номер → «Дальше» шлёт SMS
    → код читается из уведомлений Windows (`sms.py`, «Связь с телефоном») и вводится в форму.
    Номер даётся **только в рантайме** переменной `HR_LOGIN_PHONE` (10 нац. цифр), нигде не
    хранится — в лог идут лишь последние 4 цифры. Капча/ненайденный код → деградация в ручной
    вход (`--login` с окном).
  - `manual` (дефолт для не-основного) — автомат ничего не вводит; `hh.py autoclick --login`
    при `HR_ACCOUNT=<code>` открывает форму и ждёт до 5 минут ручного ввода телефона и кода.

  `--login` работает для всех способов: сперва пробует авто (`_auto_login`), при неуспехе
  оставляет окно на ручную доводку. Истёкшая сессия в кроне у аккаунта без авто-входа — останов
  с командой входа и `session_status.json` = `expired`, без ретраев учётными данными.
- **Личность сессии сверяется до откликов** (`account_session.py::verify_session`). При первом
  входе аккаунт запоминает хеш куки `_hi` (id пользователя HH). Прогон и синк останавливаются,
  если в сессии другой пользователь или пользователь, закреплённый за другим аккаунтом: это
  ловит вход не в тот аккаунт в окне `--login`, скопированный профиль браузера и забытую в
  консоли переменную. Файлы — `storage.md`.
- **Режимы и анкеты.** Не-основному открыт только `autoclick`; анкеты выключены, исход
  «анкета» у его отклика ложится в его собственную очередь и не дренируется.
- **Вакансия, занятая другим аккаунтом, не кликается** (`taken.py::taken_by_others`: журналы и
  очереди ожидания остальных аккаунтов, читаются с диска на каждый вызов). Проверка стоит
  при отборе (причина отсева «занята другим аккаунтом»), перед КАЖДЫМ кликом батча — пул
  собран минуты назад, — в `_apply_one_vacancy` (лента и очередь ожидания, исход `taken`) и в
  `POST /api/apply`. Это второй слой: первый — A/B-сплит пулов. Синк пишет WARNING
  «конфликт аккаунтов», если чат этого аккаунта стоит на вакансии из журнала другого: двойной
  отклик уже случился (руками на hh.ru), и он должен быть виден.

Первая строка лога любого `hh.py autoclick` — `Аккаунт HH: <code> (<label>)`.

### Владение пулом двух аккаунтов (`ab_split.py`)

Второй аккаунт (`acc2`) заведён под свою нишу (Python backend, удалёнка+гибрид) и имеет
ПРИОРИТЕТ на неё (решение владельца 16.09.2026, заменяет прежний A/B-50/50 по хешу).

- **Пул acc2** — вакансии по правилам acc2 (`eligible.json`, формат — `storage.md`). Считает
  его только acc2 (правила пекутся на импорте, основной их не знает) — в начале своих прогонов,
  по `hh.py autoclick --dry-pool --write-eligible` и браузерно-независимо после сбора
  (`cron_collect.bat`).
- **acc2 берёт ВЕСЬ свой пул** — включая вакансии, на которые основной откликался раньше. Дедуп
  acc2 — только против СВОЕЙ истории (`taken.own_handled_ids`: свой журнал, очередь, статусы),
  а НЕ против общих `marks.json` (там отклики основного, которые acc2 как раз и добирает).
  Для acc2 `ab_reject` всегда None, `taken` пуст — его никто не блокирует.
- **Основной ОТСТУПАЕТ** — его отбор вычитает ВЕСЬ `eligible.json` acc2 целиком
  (`AbSplit.reject`, причина «A/B: доля другого аккаунта»), так что тому же работодателю от
  одного человека два отклика не уходят.
- **Отступление основного НЕ зависит от сессии acc2**: приоритет за acc2, даже когда он в
  дауне (вход по SMS ~раз в 2 недели). Цена — ниша acc2 простаивает, пока acc2 без входа.
- **`eligible.json` устарел** — основной всё равно вычитает последний известный набор
  (недобрать безопаснее дубля), WARNING «A/B: пул … устарел». **Файла нет** (acc2 ни разу не
  считал) — деления нет, основной берёт весь пул; двойной отклик и тут ловит `taken.py`.
- **Единый источник входов пула** — `ab_split.pool_inputs()`: и боевой `_apply_batch`, и превью
  `--dry-pool` берут `(marks, taken, ab_reject)` отсюда, чтобы превью не расходилось с прогоном.
- **Журнал**: у каждой строки `account`, у крон-откликов — `ab` (была ли вакансия в пуле acc2).
- **Белый список ролей** acc2 — ключ профиля `apply_roles`, для фолбэк-роли «Разработчик» —
  `developer_title_words`: слово из списка обязано стоять в тайтле (`config.md`).

Наблюдаемость: строка пула называет аккаунт (`Пул кандидатов [acc2]: N …`), а отсев блок-листа,
ролей, чужой доли и занятых вакансий идёт отдельной строкой `отсев блок-листа/ролей/аккаунтов:`
только когда он был. С одним аккаунтом деления нет, отбор основного прежний.

## Single-instance lock

`data/autoclick.lock` = `{pid, ts}`, TTL 4 часа.

TTL должен покрывать самый долгий прогон (батч 25 откликов ~30 мин, полный на 200 — до ~4 ч).
Меньший TTL ложно счёл бы живой батч протухшим -> второй Chromium на один persistent-профиль
-> краш.

Основная проверка — **живость pid** (`lock.py::_pid_alive`): `OpenProcess` на Windows, фолбэк
`os.kill(pid, 0)`. Открытия хендла НЕДОСТАТОЧНО — на убитом процессе `OpenProcess` успевает,
пока чужой хендл держит его объект, поэтому спрашивается `GetExitCodeProcess`: живым считается
только `STILL_ACTIVE` (259). Без этого осиротевший lock блокировал отклики 3 часа (25.07,
`errors.md`).

Прогон, снимаемый watchdog'ом, отдаёт lock сам (`lock.py::release_if_mine`) — иначе
`taskkill /T` убивает процесс раньше `finally`. Снимается только собственный файл: pid в
lock сверяется с `os.getpid()`.

TTL страхует лишь случаи, где живость определить нельзя: переиспользование pid и процесс,
вышедший с кодом ровно 259.

Битый или недописанный JSON не считается «свободным» вслепую: возраст берётся по mtime,
свежий -> вероятно живой писатель.

Кто как берёт: крон — до 6 минут ожидания (сервер ленты держит профиль ~300 с);
`login()` — без ожидания; `ApplyWorker` — 2 коротких ретрая, дальше честный `busy`
(30-минутный батч в HTTP-запросе не переждать); `sync_statuses` — не берёт вовсе.

## Квота

`data/apply_quota.json` = `{date, count}`. `applied_today()` возвращает `count`, только если
`date == сегодня` — запись за прошлый день молча трактуется как 0, счётчик самосбрасывается
без отдельной крон-задачи очистки.

Известная слабость: `bump_quota` — read-modify-write без файловой блокировки. Практической
гонки нет, потому что писатели разведены общим lock'ом, но защиты на уровне файла тоже нет.

## Кулдаун поднятия резюме

`data/bump_state.json` = `{last_ok: ISO}`, `BUMP_COOLDOWN_H = 4`.

Гейт нужен потому, что отклики идут каждые 90 минут — без него тяжёлая страница
`/applicant/resumes` грузилась бы впустую на каждом слоте.

**Инвариант:** `mark_bumped()` только при `bump_resumes() > 0`. Функция возвращает `-1`, если
страница не отрисовалась (DDoS-Guard / деградированный headless), и `0` при реальном кулдауне
HH — в обоих случаях кулдаун **не взводится**, попробуем на следующем слоте.

Селектор — по токену `button[data-qa~="resume-update-button"]` + гард по тексту «в поиске»,
чтобы не нажать платную «Поднять автоматически».

## Ошибки

Разделение принципиальное: **ошибка навигации -> `SKIP` и идём дальше**, ошибка инфраструктуры
-> прогон падает.

- `_goto` — всё в `suppress`, 3 попытки, пауза 6 с при DDoS-Guard. `page.title()` обёрнут
  отдельно: при DDG-навигации контекст рушится («Execution context was destroyed») и голый
  `title()` уронил бы весь прогон
- `apply_one` timeout -> `ALREADY` / `SKIP`, не исключение
- `_apply_batch` ловит исключение вокруг `apply_one` -> warning, цикл продолжается
- `cover.llm_cover` при любой ошибке -> фолбэк на шаблон, отклик всё равно уходит
- `SystemExit` при занятом lock — ловится **явно** в `ApplyWorker._run`
  (-> `busy`), в `run()` не ловится: крон-прогон просто выходит

**Протухшая сессия неотличима от пустого результата** — принято осознанно
(`session.py::open_client`): вызовы `chat.*` вернут пусто, а куки обновит следующий браузерный
прогон. Диагностика только через лог «чаты не получены, сессия от <дата> могла протухнуть».
