# Безопасность

Модель угроз локальной однопользовательской системы, которая ходит в чужие сервисы под
учётной записью пользователя и обрабатывает текст, написанный посторонними.

## Что защищаем

1. **Учётные данные HH** — доступ к аккаунту соискателя
2. **Репутацию пользователя** — система пишет работодателям от его имени
3. **Машину пользователя** — обрабатывается неподконтрольный текст (описания вакансий,
   сообщения в чатах)

## Секреты

Ничего секретного в репозиторий не коммитится — механизм защиты — `.gitignore` в корне
(там перечислены ключи, куки, прокси-файлы, PII).

**Ключи/пароли — `.env` в корне** (`.env*` в `.gitignore`; в репо — только обезличенный
шаблон `.env.example`): `HH_EMAIL`, `HH_PASSWORD`, `HH_ACCESS_TOKEN`, `PG*`, и LLM-ключи
`OPEN_ROUTER_API_KEY` (intent/rephrase/forms), `ANTHROPIC_API_KEY` (письма). Полный список
переменных — [`config.md`](config.md).

**Живой доступ к аккаунту — `data/`** (весь каталог в `.gitignore`): куки сессии
`hh_state.json`, профиль браузера `browser_profile/`. В бэкап для передачи наружу попадать
не должны.

**PII — вне репо:** `resume_profile.json` (гражданство, дата рождения, контакты, факты для
ответов — в `.gitignore`; в репо только обезличенный `resume_profile.example.json`),
каталог `personal/` (резюме, письма), `data/talanto_contacts.json` (телефоны/telegram
рекрутёров, собранные под авторизацией — сторонние персональные данные).

**Прокси:** `proxie.txt` в репо — безопасный шаблон (одни комментарии); реальные креды —
в `proxy.txt` / `proxie.bak.txt` (в `.gitignore`). `mask_proxy()`
(`net/proxy.py::mask_proxy`) прячет их в логах. Пароль нигде не печатается.

## Локальный сервер

`ThreadingHTTPServer` привязан к **`127.0.0.1`**, наружу не смотрит. Аутентификации нет —
это осознанно для локального инструмента.

Следствие, которое надо помнить: **любой процесс на машине может дёрнуть `POST /api/apply`**
и отправить отклик. Открывать порт наружу или пробрасывать туннелем нельзя без добавления
аутентификации.

Лимит тела `POST /api/marks` — 1 МБ. Значения фильтруются по allowlist при записи.

## XSS в ленте

Описания вакансий — чужой HTML, и это единственное место, где он попадает в `innerHTML`
без экранирования.

Защита — `_DescSanitizer(HTMLParser)` + `sanitize_desc` (`views/feed.py::_DescSanitizer`, `::sanitize_desc`):
allowlist тегов `{p, br, ul, ol, li, strong, em, b, i}`, **все атрибуты срезаются**,
`script` и `style` выбрасываются вместе с содержимым.

Чистка на этапе сборки, а не рендера — поэтому защищает и `serve`, и открытие из `file://`.
Покрыто `tests/backend/presentation/test_sanitize.py`.

Остальной текст (названия, работодатели, теги) идёт через `esc()`.

## SQL-инъекции

`infrastructure/search.py`: все пользовательские входы — **только параметры** psycopg2.
В текст SQL подставляется единственная вещь — имя таблицы из переменной окружения
`SEARCH_TABLE`, то есть значение под контролем владельца машины, а не запроса.

## Анти-бот и правила площадки

Система имитирует поведение живого пользователя: реальный `User-Agent` вместо
HeadlessChrome (HH его режет), `--disable-blink-features=AutomationControlled`,
`locale=ru-RU`, паузы 4–9 с между откликами, 0.1–0.3 с между чатами.

Потолки соблюдаются: `HH_DAILY_APPLY_CAP = 200` (лимит площадки), поднятие резюме не чаще
раза в 4 часа (ограничение HH).

Это инструмент для собственного аккаунта в объёмах, которые площадка разрешает вручную.
Обход лимитов, работа с чужими аккаунтами и массовая рассылка — вне назначения системы.

**Group-IB fingerprint** гейтит отклик и `/resumes/touch`. Он не обходится — именно поэтому
эти операции идут через реальный браузер, а не через HTTP. Чат такого гейта не имеет и
работает по кукам легально.

## Prompt injection

Актуально: LLM (DeepSeek через OpenRouter) классифицирует намерение вопросов бот-рекрутеров.
Входные данные — текст от посторонних, среди которых могут оказаться инструкции для модели.

**Главный вопрос — может ли инъекция запустить что-то на машине.** Ответ определяется
не текстом промпта, а тем, что доступно модели.

### Гарантии дают не промптом, а кодом вокруг модели

- **У модели нет инструментов.** `chat_intent.classify_intent` даёт LLM текст и получает
  текст. Нет доступа к файлам, шеллу, сети, HTTP-клиенту. Инъекция «выполни команду»
  физически некому исполнить.
- **LLM возвращает МЕТКУ, не текст в чат.** Ещё сильнее «валидатора на выходе»: выход модели
  — одна из фиксированного набора `_LABELS`; `_parse_intent` режет всё вне набора и битый
  JSON в `None`. Метка лишь ВЫБИРАЕТ, к какому локальному факту маршрутизировать. Текст,
  уходящий работодателю, генерирует **код**, а не модель, — из `resume_profile.json`.
- **Минимальный контекст.** В промпт классификатора уходит ТОЛЬКО текст вопроса (усечён до
  ~500 симв). Факты профиля, резюме, переписка, `.env` — НЕ передаются. Утечь нечему.
- **intent не расширяет отвечаемое.** Даже неверная метка (в т.ч. вызванная инъекцией) ведёт
  максимум к неверному маршруту, но инвариант «нет факта -> молчим» + backstop-гвард
  (`_answer_years`) не дают выдумать факт. Худший исход — вопрос уйдёт человеку.
- **Отправка по флагу.** Деньги/место/`confirm` не уходят автоматически (`manual`, требуют
  `[y/N]`); intent их не касается (не в кластере). Весь автоответ — под `--send`, dry-run
  по умолчанию.

Шаблонный движок `chat_answer.py::suggest` — нижняя граница: не выдумывает фактов, молчит при
сомнении. LLM встроена **внутрь** этого контура (маршрутизатор), а не вместо него.

Худший реалистичный исход — модель отдаст неверную метку, вопрос уйдёт человеку или получит
не тот факт из профиля (который сам по себе правдив). Запуск кода на машине через текст
в чате невозможен: у модели нет инструментов, а её выход — метка, не команда.

**Статус:** реализованы LLM-классификатор намерения (`chat_intent`, только метка) и
LLM-переформулировка одобренного факта (`chat_rephrase`, etap 2, human-gated) — провайдер
DeepSeek V4 Flash через OpenRouter. Оба **по умолчанию ВЫКЛЮЧЕНЫ** (`INTENT_LLM`/`REPHRASE_LLM`
не заданы) — движок на regex + дословные факты; включение opt-in.

**Приватность etap-2 (важно):** в отличие от классификатора (наружу только вопрос),
переформулировка шлёт LLM **один уже одобренный факт + вопрос** — не профиль/резюме/переписку/
`.env`. Факт — это текст, который мы и так публично отправляем боту. Инвариант «не выдумывать»
держит валидатор `_grounded` (первый рубеж) + **подтверждение человеком** любой изменённой
формулировки (крон шлёт источник дословно): гарантия дана контуром, не послушанием промпта.
Валидатор ЛЕКСИЧЕСКИЙ — перестановку клауз ловит человек, не он. C3 допускает русскую морфологию
источника (работал→работаю), но НЕ новые числа/технологии/латиницу; остаточный риск кор-коллизий
(работал/работник отсекается порогом 0.7) страхует человек-гейт. Детали — `chat.md`, RFC-002.

**Приватность форм (RFC-003):** контекст `form_fill.build_resume_ctx` = allowlist-факты
профиля + PII-скраб `resume.md` + **неперсональная разметка `form_answers`** («утверждённые
ответы» — LLM отвечает в их духе, когда регекс словаря не сработал). Записи с `pii: true`
(дата рождения, контакты, ссылки, город, военник) провайдеру НЕ уходят; вторым рубежом —
`_scrub_pii` по строкам блока. Зарплату резолвит ТОЛЬКО код (`is_salary_q`), в LLM она не
попадает никогда. Тех-задания идут отдельным код-промптом БЕЗ фактов резюме.

## Что не реализовано и не планируется

- Аутентификация локального сервера — не нужна при bind на `127.0.0.1`
- Шифрование `data/` — защита уровня ОС считается достаточной
- Аудит-лог доступа — один пользователь
