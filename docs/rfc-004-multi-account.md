# RFC-004: Второй аккаунт hh.ru и A/B-сплит резюме

> Формат RFC: меняются боевой путь откликов, схема хранения `data/` и вход в HH. Ссылки на код — по
> имени символа. Итог ревью: **один процесс — один аккаунт**, вакансии делятся детерминированным
> хешем, второй аккаунт никогда не вводит учётные данные основного.

**Статус:** Принят (2026-09-15) · **Связано:** `apply.md`, `storage.md`, `operations.md`, `config.md`, `feed.md`, `api.md`, `security.md`, RFC-003

---

## Motivation

Система автооткликов обслуживает один аккаунт hh.ru, понятия «аккаунт» в коде нет. Состояние
разложено по ~14 путям под `data/`, профиль резюме читается при импорте `config.py`, вход —
только по email и паролю (`browser.py::_auto_login`).

Нужно подключить второй аккаунт: вход по телефону и SMS, одно резюме. Требования владельца:
на localhost видно, от какого профиля ушёл каждый отклик; одна вакансия получает отклик только
от одного аккаунта (дубли запрещены); блок-лист работодателей действует в обоих аккаунтах.

> **ЗАМЕНЕНО 16.09.2026 (S8).** Требование «одна вакансия — один аккаунт» действует теперь
> В ОДНУ СТОРОНУ. Приоритет отдан acc2 на его нишу: основной по-прежнему не берёт НИЧЕГО из
> пула acc2, но acc2 берёт свою нишу целиком, включая вакансии, на которые основной откликался
> раньше (дедуп acc2 — только против СВОЕЙ истории, `taken.py::own_handled_ids`). Значит один
> работодатель может получить два отклика одного человека с двух резюме: замер 21.09.2026 —
> **72 из 103** откликов acc2 на вакансии из журнала основного, 137 из 184 в его текущем
> `eligible.json`. Это осознанная цена приоритета, а не дефект сплита: конфликт виден в ленте
> (метка профиля и множество аккаунтов на вакансии) и в WARNING синка. Мотивы решения —
> «Alternatives», актуальная модель — `apply.md` («Владение пулом двух аккаунтов»).

**Второй аккаунт не добавит откликов: рынок исчерпывается раньше квоты.** 12.09.2026 пул
основного обнулился в 16:14 при неизрасходованном остатке 137/200. Поэтому цель — не объём, а
**A/B-сравнение двух резюме** на непересекающихся выборках вакансий.

Ещё два факта эксплуатации, определившие решение:

- сессия HH истекает примерно раз в 2 недели, автовход по паролю — 0 успешных из 4 попыток.
  Ручной вход раз в две недели плюс баннер дешевле автоматизации SMS-входа;
- повторяющиеся триггеры планировщика перестали срабатывать после сна 10.09.2026, поэтому
  расписание второго аккаунта — отдельные ежедневные триггеры, а не повтор.

## Problem

Нет способа откликаться от двух аккаунтов HH так, чтобы каждая вакансия получала не больше
одного отклика, профиль каждого отклика был известен, а основной аккаунт работал без изменений.
(Что осталось от этого требования после S8 — во врезке выше: отклик не больше одного у
ОСНОВНОГО, а acc2 свою нишу добирает.)

- **R26.** `own_handled_ids` — дедуп приоритетного аккаунта против СВОЕЙ истории: журнал +

- **Чаты и анкеты второго аккаунта; выбор профиля при ручном отклике из ленты; переезд данных
  `main`; параллельные браузерные прогоны.**
- **Разбивка воронки и дашборда по аккаунтам** — по-прежнему не делаем. **Отчёт по A/B сделан

  `feed.md`, «Панель профилей»), живой по `/api/applied` + `/api/statuses`.
- **Прочие дыры отбора `main`** (Go/Node, ярус WIDE, роли) — отдельное решение. Здесь только
  блок-лист работодателей и «С++/С#» с кириллической «С».

## Solution

### Принцип: один процесс — один аккаунт

Аккаунт задаётся **только** переменной `HR_ACCOUNT` до импорта `hrwork`; без неё — `main`. Первая
строка лога прогона — активный аккаунт. Два аккаунта в одном процессе не держим: правила отбора
(`candidates.py::APPLY_LANG_BLACKLIST` и соседи) — константы, скомпилированные из профиля при
импорте. `--account` в argv не делаем: `hh.py` импортирует `config` на верхнем уровне, а тесты
импортируют `hh`.

```
cron_collect.bat: collect -> feed -> HR_ACCOUNT=acc2 hh.py autoclick --dry-pool --write-eligible
                                                         -> data/accounts/acc2/eligible.json
main:  кандидаты main - (eligible ∩ ab_owner=acc2) - taken_ids - блок-лист -> клик -> data/applied_log.jsonl
acc2:  eligible -> sync -> кандидаты acc2 ∩ ab_owner=acc2 - taken_ids - блок-лист -> клик
                                                         -> data/accounts/acc2/applied_log.jsonl
serve (main): журналы всех аккаунтов -> /api/applied{account} -> лента (метка профиля, конфликт)
```

### Аккаунт и пути

- `hrwork/domain/account.py`: `HhAccount` (VO аккаунта) и чистый `parse_account_code`;
  `hrwork/accounts.py::resolve_account` — проверка папки на диске (домен диска не трогает).
  `config.py` печёт `ACCOUNT` и `ACCOUNT_DIR` (у `main` это `DATA_DIR`). Отдельного VO путей нет:
  пути остаются модульными константами поверх `ACCOUNT_DIR`. Не в application: разрешение зовёт
  сам config, а config не импортирует ничего выше домена.
- `HR_ACCOUNT` читается **до** `load_dotenv`: строка в `.env` сделала бы вторым аккаунтом каждый процесс.
- **`main` работает на текущих путях**, миграции нет.
- **Второй аккаунт** описан `data/accounts/acc2/account.json` (`label`, без телефона и паролей) и
  своим `resume_profile.json`. Неизвестный код, отсутствующий `account.json` или профиль — немедленная
  ошибка; папка **не создаётся**, так что опечатка в `HR_ACCOUNT` не заведёт новый аккаунт.
- **Своё у второго аккаунта:** `browser_profile`, `hh_state.json`, квота, `bump_state`,
  `applied_log.jsonl`, `response_status.json`, `chat_messages.json`, `form_vacancies.json`,
  `apply_pending.json`, `chat_replies.jsonl`, `resume_profile.json`, `account_identity.json`,
  `session_status.json`, `eligible.json`.
- **Очередь анкет своя** (дополнение к плану при реализации S2): исход «анкета» у отклика второго
  аккаунта бывает, а общую очередь дренировал бы анкетный прогон `main` — вакансия из доли второго
  ушла бы откликом от основного.
- **Общее:** кеш вакансий, meta и fx, файлы ленты, `marks.json`, `forms_cache.json`, `autoclick.lock`
  (один на машину — браузерные прогоны строго по очереди).
- Имена модульных констант (`session.py::STATE_FILE`, `followup.py::APPLIED_LOG_FILE`,
  `quota.py::QUOTA_FILE` и др.) не меняются, значения вычисляются из текущего аккаунта — monkeypatch
  в тестах работает. Загрузчики данных других аккаунтов получают `path=`.
- `followup.py::append_applied` создаёт `parent` своего файла, а не `DATA_DIR`: первым писателем в
  папке второго аккаунта бывает синк.
- **От не-`main` запрещены режимы** `collect/enrich/analyze/feed/dashboard/serve/all/chat/forms/hhapi`:
  `files.py::cache_valid` сверяет `search_queries` и `cities` профиля, и общий кеш под профилем
  второго аккаунта был бы испорчен. Тот же запрет — в `scripts/chat_stats.py` и
  `scripts/chat_review.py`, где пути захардкожены.
- **`FORMS_ENABLED=False` для не-`main` принудительно**, независимо от `FORMS_LLM`. Иначе анкеты
  заполнялись бы профилем и `personal/resume.md` основного.

### Вход и личность

- **Защита и диспетчеризация входа — внутри `browser.py::_auto_login`** — единственной точки,
  через которую проходят `run`, `ApplyWorker._run` и `login`. Способ берётся из
  `ACCOUNT.login`: `password` (только `main`, `HH_EMAIL`/`HH_PASSWORD`), `phone` (авто по
  телефону+SMS, `_phone_login`), `manual` (окно ждёт ручного ввода, 5-минутный цикл). Не-`main`
  **никогда** не вводит `HH_EMAIL`/`HH_PASSWORD` — `resolve_account` отвергает `login=password`.
- **Пин личности** — хеш куки `_hi` (id пользователя HH; её же chatik принимает как applicantId)
  из `hh_state.json`, без лишних запросов. Пишется при первой сверке в `account_identity.json` папки
  аккаунта — у всех аккаунтов одинаково, `account.json` остаётся файлом, который пишет человек
  (`account_session.py::identity_problem`). Проверяется в `run`, `login`,
  `ApplyWorker._run` и `sync_statuses`. Личность, совпавшая с пином другого аккаунта, — стоп с понятной
  ошибкой, это ловит и вход не в тот аккаунт. Пин `main` записан 15.09.2026 из текущей сессии.
- **Истёкшая сессия второго аккаунта:** `session_status.json` = `{"state":"expired"}`, ERROR с
  командой входа, стоп прогона. Ретраев с учётными данными нет.
- Диагностика «капча или код» при входе второго аккаунта отложена до S6: селекторы шага кода
  не подтверждены вживую, а вслепую их не пишем.

### A/B-сплит — главная гарантия «одна вакансия — один аккаунт»

> **ЗАМЕНЕНО 16.09.2026 (S8).** A/B-50/50 по хешу отменён. Новая модель: **acc2 — приоритет на
> свою нишу** (Python backend, удалёнка+гибрид), берёт ВЕСЬ свой пул (включая ground основного),
> дедупясь только против своей истории (`taken.own_handled_ids`); **основной вычитает весь
> `eligible.json` acc2 целиком** и отступает независимо от того, жива ли сессия acc2. `ab_owner`
> удалён; `session_alive` больше не гейтит деление (и сам удалён как мёртвый). Актуальное описание — `apply.md` («Владение
> пулом двух аккаунтов») и план `bubbly-crunching-lynx.md` (раздел S8). Ниже — исходный дизайн.

- **Владелец:** `ab_owner(vid)` = `sha256(vid) % 2` -> `[main, acc2]`. Встроенный `hash()` не
  годится — он рандомизирован между процессами.
- **Общая часть** — вакансии, подходящие по правилам второго аккаунта; стабильна, от marks и
  журнала не зависит. Второй аккаунт без браузера пишет её в `eligible.json` (время + id):
  `HR_ACCOUNT=acc2 hh.py autoclick --dry-pool --write-eligible`. Файл освежается после сбора (шаг в
  `cron_collect.bat` после ленты) и в начале каждого прогона второго аккаунта.
- **Пул второго аккаунта** = его кандидаты с `ab_owner = acc2`.
- **Пул `main`** = его кандидаты минус (`eligible` ∩ `ab_owner = acc2`). Всё, что подходит только
  основному, остаётся основному.
- **`eligible.json` отсутствует или старше кеша** -> `main` пропускает все вакансии с
  `ab_owner = acc2`: лучше недобрать, чем испортить A/B. В строке пула — WARNING и счётчик.
- В строку журнала пишется `"ab": true`, если вакансия была в общей части на момент отклика.

### Дедуп ручных путей — второй слой

- `taken_ids()` = id из журналов всех аккаунтов ∪ pending всех аккаунтов ∪ общие `marks`.
- Проверяется в `pick_candidates`, **перед каждым кликом** в `_apply_batch`, в `_apply_one_vacancy`
  (лента и pending) и в `server.py::_apply_post` (статус `taken` с владельцем). Закрывает ручные
  отклики из ленты и прямо на hh.ru, которых сплит не видит.
- `sync_statuses` логирует конфликт, если в чатах аккаунта есть вакансия из журнала другого.

### Отбор

- **Профиль второго аккаунта** (локальный, не в репозитории): `core` — Python, FastAPI; `core_wide` —
  Django, Flask; `exp_ids` — `between1And3`, `extra_exp_ids` — `between3And6`; `office_cities` — один
  офисный город из профиля второго аккаунта (сначала удалёнка, затем офис или гибрид только там);
  `cover_template` — `cover.py::_DEFAULT_TEMPLATE`, текст утверждается до первого боевого отклика.
- `blacklists.other_lang` второго аккаунта: **полный** дефолтный список плюс go, bitrix, битрикс,
  wordpress, typescript, node.js, nestjs, react, angular, vue, flutter, dart, swift. Профильный
  список **заменяет** дефолтный регэксп целиком, поэтому дефолты повторяются.
- **Новый ключ `apply_roles`** — белый список `Role`. Ключа нет — ограничений нет, `main` не меняется.
  У второго аккаунта: `Role.BACKEND`, `Role.DEVELOPER`, `Role.GENAI`.
- **Кириллическая «С» в тайтле** — точечная замена `candidates.py::_CYRILLIC_C_LANG`
  (`[Сс](?=\s*(?:\+\+|#))` -> `C`) перед прогоном `_SCOPE_RULES` в `out_of_scope`: иначе
  «Разработчик С++» обходил `OutOfScope.OTHER_LANG`. В самом `APPLY_LANG_BLACKLIST` этой
  ветки нет — кириллическая «С» нормализуется отдельно, до правила `OTHER_LANG`.
- **Блок-лист работодателей для обоих аккаунтов:**
  - `.env` `APPLY_EMPLOYER_BLOCKLIST`, разделитель `;` — запятая встречается в самих названиях.
    В коде список пуст, в `.env.example` — вымышленный пример `ООО Ромашка`.
  - Совпадение по границе слова без учёта регистра; нормализация омоглифов — **и к шаблону, и к
    названию**: кириллическое и латинское написание одинаковых по виду букв — одно имя. Причина:
    в кеше найдено 8 написаний одного работодателя, включая кириллический омоглиф в названии.
  - `employer_blocked(name)` вызывается на всех путях отклика: `pick_candidates`,
    `_apply_one_vacancy` (через него же `_drain_pending` и лента), `forms.run` — там анкета ещё и
    снимается из очереди. `forms.clean_queue` блок-лист не проверяет: работодателя в записи
    очереди нет, а кеш вакансий чистка сознательно не поднимает (`apply.md`).
- **`hh.py autoclick --dry-pool`** без браузера печатает пул: размер, ярусы, роли, топ названий,
  работодатели и счётчики отсева (блок-лист, роль, `taken`, A/B).

### `marks.json` — межпроцессная защита

`store.merge_marks` — это чтение -> изменение -> запись, а `marks.py::_SAVE_LOCK` сериализует только
потоки одного процесса. Писателей станет больше (оба аккаунта, синки, сервер), а потерянная
отметка «отклонено» может закончиться необратимым откликом. Решение: межпроцессный lock-файл на
запись marks; `server.py::_marks_post` подмешивает с диска отметки `applied`, а не затирает их.

### Localhost (слой presentation)

- Каждый аккаунт пишет свой журнал, строки получают `"account"`; легаси-строки — владельцу файла.
- **API** (`serve` работает от `main`, читает все аккаунты): `/api/applied` — объединение журналов с
  `account`; `/api/statuses` и `/api/chats` — прежние форматы, значение у владельца по журналу;
  новый `/api/accounts` — `[{code,label,session}]`.
- **`feed.py`:** объединённые статусы и `hr_ts`; `ACCOUNTS_PY` определяется в Python и внедряется в
  `feed-data.js`, плюс JS-фолбэк и тесты моста.
- **Фронт:** `model.js::journalById` собирает **множество** аккаунтов на вакансию (двойной отклик —
  конфликт); `view.js::statusBadge` — метка профиля; чипы по профилю — от двух аккаунтов; баннер
  «аккаунт acc2: нужен вход». Ручной отклик из ленты — только от `main`.

### Крон и гигиена

- **`cron/cron_apply_account.bat <code> [limit]`:** `set HR_ACCOUNT=%1`; `--apply-limit <limit>
  --daily-cap 60` -> `--sync-status` (отклики первыми: синк обходит тысячи чатов и не должен
  их задерживать); лог `logs\cron_apply_<code>.log`; `FORMS_LLM` не выставляется. `eligible.json`
  освежает не эта обёртка, а `cron_collect.bat` после ленты. **Лимиты:** три слота (10:45, 14:15,
  17:45) по 10. Поднимали до 20 22.09.2026, откатили 23.09.2026: HH перестаёт подтверждать
  отклики при ~48 за скользящие 24ч (`HH_APPLY_ROLLING_CAP`, `errors.md`) — `operations.md`,
  «Приоритетный крон второго аккаунта».
- **Мягкий дедлайн второго аккаунта** ~35 мин: дальше кандидаты не берутся. Watchdog стартует раньше
  ожидания `autoclick.lock`, и без дедлайна второй аккаунт мог бы съесть слот основного.
  **В КОДЕ НЕ РЕАЛИЗОВАН** (аудит 22.09.2026): бюджета времени прогона нет, длину ограничивают
  `--apply-limit` и watchdog (`WATCHDOG_KILL_S`, 50 мин на процесс). `ExecutionTimeLimit` задачи
  (PT50M) фактически не действует: `run_hidden.vbs` запускает `.bat` без ожидания и сразу
  завершается. Замер по последним ~9 слотам `logs\cron_apply_acc2.log` (сентябрь 2026): шаг откликов 7–33 мин, синк
  3–5 мин; один раз watchdog снял зависший шаг откликов (>50 мин) — слот съеден целиком.
- **Задача планировщика:** отдельный ежедневный триггер на каждый слот, сдвиг +45 мин от `hh_apply`.
- `.gitignore`: `resume_profile.json.bak*` — рядом лежала неотслеживаемая копия профиля на 70 КБ
  личных данных. Телефон и данные второго резюме в коммиты не попадают.
- Корневой `conftest.py::pytest_configure` удаляет `HR_ACCOUNT` до импорта `config`. Тесты:
  «растяжки» на кросс-аккаунтные загрузчики (не читать реальный `data/accounts/`), пин
  `APPLY_ROLES` в `_default_profile`, новые ключи — в `resume_profile.example.json` и множестве `wired`.

### Срезы

Каждый проверяется отдельно, крон `main` между ними не ломается.

- **S0.** Этот RFC, `.gitignore`, каталог в `append_applied`, защита в conftest.
- **S1.** Только `main`: блок-лист работодателей, `[cс]\+\+`/`[cс]#`, `--dry-pool`.
- **S2.** Аккаунт и пути, запрет режимов, защита `_auto_login`, отключение анкет, пин. `main` без изменений (R1).
- **S3.** Межпроцессный lock marks и слияние на сервере (полезно и `main`). **S4.** `taken_ids` и
  проверка перед кликом — с одним аккаунтом ничего не меняет.
- **S5.** Профиль второго аккаунта, `apply_roles`, `eligible.json`, сплит; владелец утверждает пул и письмо.
- **S6.** Ручной вход второго аккаунта (SMS), пин, **только синк**. **S7.** Лента и сервер: объединение,
  метки, фильтр, конфликт, баннер.
- **S8.** Крон, доки из «Связано» плюс `architecture.md`, живой запуск `--apply-limit 1 --headed` -> `5`
  -> крон с лимитом 10.

## Alternatives

- **Ничего не делать** — ноль риска для боевого пути / два резюме не сравнить на непересекающихся
  выборках, а объёма второй аккаунт и так не даст (остаток 137/200 на 12.09.2026).
- **Два аккаунта в одном процессе** — один крон / правила отбора — константы импорта, это
  рефакторинг боевого пути откликов.
- **`--account` в argv** — нагляднее / `config` импортируется раньше разбора argv.
- **Claims-файл «кто первый взял»** — не нужен хеш / координация процессов и своя политика
  восстановления окна «клик -> журнал». Хеш-сплит даёт непересекающиеся пулы без координации.
- **Встроенный `hash()`** — короче / рандомизирован между процессами, владелец менялся бы.
- **Глобальная нормализация омоглифов в отборе** — закрыла бы все обходы / сломала бы русские
  блок-листы «тестировщ», «сетевой инженер», «стажёр»; отсюда точечные `[cс]` в правиле языка.
- **Автовход второго аккаунта по паролю или перехват SMS** — без ручного шага / автовход по паролю —
  0 из 4, чтение уведомлений запрещено фильтром безопасности.
- **Переезд `main` в `data/accounts/main/`** — единообразие / миграция живых данных без выгоды (R1).

## Risks

- **HH связывает аккаунты по IP и отпечатку**: ограничения и капчи на обоих -> прогоны по очереди
  со сдвигом, раздельные профили браузера, лимит 10, наблюдение за капчами `main`.
- **Маленькая общая часть** (удалёнка Python backend/AI плюс один офисный город из профиля второго
  аккаунта): A/B набирает статистику медленно -> `--dry-pool` показывает размер до запуска. Основной
  аккаунт теряет половину ниши — осознанная цена A/B.
- **Второй аккаунт действует данными основного** (автовход с `HH_EMAIL`, вход не в тот аккаунт,
  скопированный крон с `FORMS_LLM=1`) -> защита в `_auto_login` (R4), пин личности (R5),
  принудительный `FORMS_ENABLED=False` (R6).
- **Операция прервалась на середине** -> «Политика восстановления»; **параллельный запуск** -> один
  `autoclick.lock` на машину, мягкий дедлайн, межпроцессный lock marks (R21).
- **Пустой вход** (`eligible.json` пуст или отсутствует) -> пул acc2 пуст, `main` пропускает всех с
  владельцем acc2 (R11). **Обход блок-листа написанием** -> омоглифы и граница слова (R8, R9).
- **Приватность** -> `account.json` без телефона и паролей, `data/` и `resume_profile.json.bak*` в
  `.gitignore`; `server.py::_static_allowed` раздаёт только белый список из корня `data/`, так что
  `data/accounts/` недоступен; тесты не видят реального аккаунта (R20).
- **Деньги**: новых платных вызовов нет. **Накопленные данные `main`**: пути и формат прежние (R14).

## Migration

- Пересборка данных (`hh.py collect --force`) и конвертер не нужны: файлы `main` совместимы как есть
  (R1), легаси-строки журнала относятся к владельцу файла.
- Промежуточное состояние рабочее: срезы S0–S8 выкатываются по одному. До S5 сплита нет, S3 и S4
  с одним аккаунтом ничего не меняют. `data/account_identity.json` заполняется первым прогоном после S2.

- Включение второго аккаунта: `account.json` и локальный профиль -> `--dry-pool` обоим, утверждение
  пула и письма -> вход по SMS -> только синк -> `--apply-limit 1 --headed` -> `5` -> крон с лимитом 10.

## Rollback

- **Второй аккаунт:** удалить его задачу планировщика (`schtasks /Delete /TN <задача> /F`) и шаг
  `--write-eligible` в `cron_collect.bat`, затем `data/accounts/acc2/` — `main` не затронут (R1).
- **До удаления папки:** её `applied_log.jsonl` — единственный след откликов второго аккаунта для
  `taken_ids`. Если дубли недопустимы и после отката, id из него переносятся в `marks.json` как
  `applied`, иначе `main` может откликнуться на те же вакансии.
- **Поля `account` и `ab`** добавочные — старый код их игнорирует. **Блок-лист:** очистить
  `APPLY_EMPLOYER_BLOCKLIST` в `.env` — поведение как до S1.
- **Код:** срез — отдельный коммит, откат `git revert`. Бэкап не нужен: данные `main` не переписываются.
