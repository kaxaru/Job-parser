# Операционка

Крон, логи, диагностика. Заменяет привычную тройку `deployment.md` / `logging.md` /
`monitoring.md` — для локальной однопользовательской системы три отдельных файла были бы
на 80 % пустыми.

## Развёртывание

Локальная машина, Windows 11. Никаких контейнеров и удалённых окружений.

```
python -m venv .venv3
.venv3\Scripts\python.exe -m pip install -r requirements.txt
.venv3\Scripts\python.exe -m playwright install chromium
npm install                                    # esbuild + biome
```

Важно: `pip.exe` в venv сломан (указывает на чужой путь) — использовать
`python.exe -m pip`. Запускать всегда через абсолютный путь к `.venv3\Scripts\python.exe`.

Первый вход в HH — разово и с окном браузера:

```
.venv3\Scripts\python.exe hh.py autoclick --login
```

Сессия сохраняется в `data/browser_profile/`, куки выгружаются в `data/hh_state.json`.

### Регистрация крон-задач (чистая машина)

Планировщик задач Windows не входит в репо — на новой машине задачи создаются вручную.
Действие каждой обёрнуто в `cron/run_hidden.vbs` (запускает `.bat` без окна). Активны три
(`hh_sync`/`hh_bump` отключены — слиты в `hh_chat`/`hh_apply`):

```bat
set REPO=<путь к вашему клону hr_work>       REM напр. C:\projects\hr_work
set BAT=%REPO%\cron
set VBS=%BAT%\run_hidden.vbs

schtasks /Create /TN hh_collect /TR "wscript.exe \"%VBS%\" \"%BAT%\cron_collect.bat\"" /SC DAILY /ST 12:00 /F
schtasks /Create /TN hh_apply   /TR "wscript.exe \"%VBS%\" \"%BAT%\cron_apply.bat\""   /SC MINUTE /MO 90 /ST 10:00 /ET 23:30 /K /F
schtasks /Create /TN hh_chat    /TR "wscript.exe \"%VBS%\" \"%BAT%\cron_chat.bat\""    /SC MINUTE /MO 90 /ST 10:30 /ET 23:30 /K /F
```

`schtasks /Create` не выставляет `ExecutionTimeLimit` и `StartWhenAvailable` — для `hh_collect`
(2-ч лимит на сбор+пересборку статистики) добить через PowerShell:

```powershell
Set-ScheduledTask -TaskName hh_collect -Settings (New-ScheduledTaskSettingsSet `
  -ExecutionTimeLimit (New-TimeSpan -Hours 2) -StartWhenAvailable)
```

Проверка — `schtasks /Query /TN hh_collect /V /FO LIST`. Сами `.bat` портабельны: корень
репо выводят из своего расположения (`cd /d "%~dp0.."`), а venv-python — из `%REPO%\..\.venv3`
(venv рядом с репо; если создан ВНУТРИ репо по README — в `.bat` заменить `\..\.venv3` на
`\.venv3`). Так что правки при переносе репо нужны только в командах `schtasks /Create` выше
(значение `%REPO%`).

## Расписание

Планировщик задач Windows. Сводка:

```
10:00 ─┬─ hh_apply                     каждые 90 мин до 23:30, по 20 откликов
10:30 ─┼─ hh_chat                      каждые 90 мин до 23:30: синк чатов + автоответы (loop)
12:00 ─┼─ hh_collect                   раз в сутки
       ├─ hh_sync                      ОТКЛЮЧЕНА (её синк поглощён hh_chat)
       └─ hh_bump                      отключена (слита в hh_apply)
```

Только `hh_apply` берёт браузер и `autoclick.lock`. Остальные — HTTP, поэтому наложения
безопасны. `hh_chat` смещён на +30 мин от `hh_apply`, чтобы браузерный прогон и синк
не стартовали ровно вместе.

---

### `hh_collect`

**Расписание.** Ежедневно 12:00, `ExecutionTimeLimit` 2 ч, `StartWhenAvailable`.

**Команда.** `cron/cron_collect.bat`: `hh.py collect`, затем best-effort пересборка
(шаги −1…3): `hh.py feed` (лента), `docker compose up -d --wait` (поднять стек),
`search_demo/load.py` (переиндексация поиска), `hh.py dashboard` (Plotly),
`python -m etl all` (DWH).

**Что делает.** Пересбор вакансий трёх источников (hh + hirify + talanto) ->
`data/vacancies_raw.json`, следом освежает ленту, поиск, дашборд и DWH из этого же среза.

**Почему лента идёт первым шагом.** `feed-data.js` — снимок на диске, а не живое чтение
кеша: `serve` его только раздаёт. Пока шаг отсутствовал (до 01.08.2026), лента застывала
на дате ручного `hh.py feed` — в ней не хватало 5331 собранной вакансии и 68 вакансий
с живыми чатами. Оверлей `initOverlay` подтягивает status/forms/chats и синтезирует
«призраков» из журнала, но состав ленты и `hr_ts` (сортировка «Ответы») он не чинит.
Порядок: до Docker-блока, потому что шаги 0/1/3 идут минуты и падают на выключенном Docker.

**Ресурсы.** Сам сбор — curl/HTTP (браузер и `autoclick.lock` не трогает). Шаги пересборки
дополнительно поднимают Docker-стек и гоняют ETL/дашборд (best-effort: Docker выключен ->
шаги залогируют ошибку, собранные данные целы).

**Лог.** `logs/cron_collect.log`

**Edge cases**

- Санити-гейт сработал -> кеш не перезаписан, в логе `Источник hh: 300 << 16000 (< 50%)`
- Источник упал -> собирается второй, прогон не падает
- Не успел за 2 ч -> задача снимается планировщиком; кеш цел (запись атомарная в конце)

**Почему так**

- **Без `--force`** намеренно: флаг снимает санити-гейт, и один сбойный прогон без присмотра
  уничтожил бы кеш
- **`CACHE_TTL_HOURS=20`**, а не 24: при суточном запуске возраст кеша попадал бы ровно
  на границу, и сбор то срабатывал бы, то нет
- **12:00 внутри окна откликов** безопасно: сбор идёт по HTTP, lock не берёт, запись
  `vacancies_raw.json` атомарная — параллельный прогон прочитает либо старый файл целиком,
  либо новый

### `hh_apply`

**Расписание.** Каждые 90 минут в окне 10:00–23:30 (10 слотов), лимит 1 ч.

**Команда.** `cron/cron_apply.bat` -> `hh.py autoclick --apply-limit 20`

**Что делает.** Поднятие резюме (если прошёл кулдаун) + отклики + дренаж очереди из ленты.

**Ресурсы.** Playwright + Chromium, **берёт `autoclick.lock`** с ожиданием до ~6 минут.

**Лимиты.** 20 × 10 слотов = ровно 200/день (лимит HH), плюс потолок в `apply_quota.json`.
Эффективный лимит слота = `min(20, дневной остаток)`.

**Лог.** `logs/cron_apply.log`

**Edge cases**

- Занят lock (сервер ленты держит профиль ~300 с) -> ждёт, потом выходит
- Зависание -> watchdog: дамп стеков на 40 мин, `taskkill /F /T` на 50 мин
- Сессия протухла -> `SystemExit` с просьбой запустить `--login`
- Прогон оборван -> отклики не теряются: marks, квота и журнал пишутся поштучно

**Почему так.** Поднятие резюме и отклики **слиты в один браузерный прогон** — раздельные
задачи дрались за `autoclick.lock`. Watchdog на 50 минут выбран меньше лимита задачи
в 60 минут, чтобы сработать первым: `ExecutionTimeLimit` снимает только `.bat`, оставляя
python, node и chromium сиротами.

### `hh_chat`

**Расписание.** Каждые 90 минут в окне 10:30–23:30, лимит 80 мин.

**Команда.** `cron/cron_chat.bat` — два шага последовательно:
1. `hh.py autoclick --sync-status` — инкрементальный синк чатов: терминальные (отказ) без
   сообщений 7 дней берутся из кеша (полный — `--sync-full`); подтягивает свежие вопросы ботов
2. `hh.py chat --send --loop` — автоответы по шаблонам, диалог до конца

**Что делает.** Синкает переписку, затем отвечает бот-рекрутерам на вопросы, для которых
в профиле есть факт, ведя цепочку до упора (`--loop`): ответ -> ждём следующий вопрос ->
отвечаем.

**Ресурсы.** Только HTTP (chatik cookie-only). **Браузер и `autoclick.lock` не берутся** —
с `hh_apply` не конфликтует.

**Лог.** `logs/cron_chat.log`

**Безопасность без присмотра — по конструкции, не по инструкции:**

- **деньги/место (`manual`) и `confirm` НЕ уходят** — `_console_consent` требует tty,
  у крона его нет -> пропускаются, остаются человеку
- **нет факта** в профиле -> движок молчит, вопрос человеку
- отвечаем только боту/шаблону (не живому человеку) и только на прямой вопрос
- дедуп по вопросу -> один вопрос дважды не отвечается

Итог: без присмотра уходит **только то, на что есть выверенный владельцем факт**.

**Edge cases**

- Куки протухли -> чаты пустые, автоответов нет; обновит следующий `hh_apply`
- `--loop` упёрся в вопрос без факта -> цепочка по чату останавливается (человеку)
- Предохранитель `--loop-rounds 8` от зацикливания; `--reply-limit 10` на раунд

**Почему поглотил `hh_sync`.** `hh_chat` делает синк первым шагом каждые 90 мин — чаще, чем
прежние 3 ч. Держать оба нельзя: два `sync_statuses` параллельно перезаписывали бы
`chat_messages.json` (гонка). Поэтому `hh_sync` **отключена**, `cron_sync.bat` оставлен
для ручного синка.

### Проверить и поправить

```powershell
# обзор всех задач: путь, состояние, следующий и последний запуск
Get-ScheduledTask -TaskName hh_* | ForEach-Object {
  "{0,-12} {1} [{2}]" -f $_.TaskName, $_.Actions.Execute, $_.State }
Get-ScheduledTask -TaskName hh_* | Get-ScheduledTaskInfo |
  Select-Object TaskName, NextRunTime, LastRunTime, LastTaskResult

# сменить время / удалить
schtasks /Change /TN hh_collect /ST 12:00
schtasks /Delete /TN hh_collect /F
```

**Смена команды задачи — только через `Set-ScheduledTask`.** `schtasks /Change /TR` у задач
с сохранёнными учётными данными требует пароль учётки и виснет на интерактивном запросе
`Please enter the run as password`, что делает его непригодным для скриптов:

```powershell
Set-ScheduledTask -TaskName hh_apply -Action (New-ScheduledTaskAction `
  -Execute "<путь к репо>\cron\cron_apply.bat")
```

`Set-ScheduledTask` заменяет только действие; триггеры, `ExecutionTimeLimit` и принципал
сохраняются. После правки стоит убедиться в этом явно — `$_.Triggers.Count` и
`$_.Settings.ExecutionTimeLimit`.

## Логи

**loguru**, два синка (`config.py`):

- stderr — `HH:mm:ss | LEVEL | message`, цветной, уровень DEBUG
- файл `logs/hr_work_<PID>.log` — ротация 5 МБ, retention 3, utf-8, `delay=True`,
  `enqueue=True` (запись через очередь, не блокирует прогон на I/O)

**Почему файл на процесс.** Раньше все писали в один `hr_work.log`. После развязки задач
(синк перестал брать lock и побежал параллельно с serve/apply) ротация начала падать:
на Windows нельзя переименовать файл, который держит другой процесс —
`PermissionError [WinError 32]` обрывал прогон. 20.07 синк умер на 550 из 600 чатов.

Один писатель на файл — ротации нечего делить.

Крон-обёртки дополнительно пишут свои: `logs/cron_apply.log`, `cron_chat.log`,
`cron_sync.log`, `cron_collect.log`, `cron_bump.log`.

### Скрытое окно крон-задач

Задачи Планировщика идут как `LogonType=Interactive` (в сессии пользователя), поэтому
запуск `.bat` напрямую открывал видимое окно `cmd`, висевшее весь прогон (у `hh_chat` —
до часа). Действие каждой задачи обёрнуто в `cron/run_hidden.vbs`, который запускает `.bat`
со скрытым окном (`WScript.Shell.Run …, 0`).

Альтернатива — `LogonType=Password` (фон, сессия 0, окна нет вовсе) — требует пароль учётки
при регистрации и виснет на интерактивном запросе, поэтому не годится для скриптов.

## Мониторинг — Grafana + Loki (свой стек)

`observability/` — **самодостаточный** стек из 3 контейнеров (Loki + Promtail + Grafana),
читает `logs/*.log` и рисует дашборд крон-задач. Не зависит от `dwh_demo` (там свой стек
ради ETL-демо; смешивать — значит поднимать 12 контейнеров ради наблюдения одной машины).

Сами задачи остаются на Task Scheduler — этот стек их только **наблюдает**.

```bash
cd observability && docker compose up -d      # поднять
# открыть http://localhost:3002  (admin / admin)
```

Порты смещены (**Grafana 3002, Loki 3101**), чтобы не конфликтовать с `dwh_demo`
(3001/3100) — оба стека могут работать одновременно.

**Что на дашборде «hr_work — крон-задачи»** (`observability/dashboards/hr-work-cron.json`):

- **зависания** — счётчик `WATCHDOG` (сработавший watchdog = снятый по таймауту прогон)
- **ошибки** — счётчик `ERROR`
- **отклики за сегодня** — из строки `Отклик (сегодня N)`
- **автоответы** — счётчик `Отправлено #`
- **светофор** — уровни логов во времени (SUCCESS/WARNING/ERROR), с фильтром по задаче
- **синк + автоответы + зависания** — три ряда во времени
- **поток проблем** — сырые `ERROR`/`WARNING`/`могла протухнуть`/санити-гейт `<<`

**Как устроено.** Promtail (`observability/promtail.yml`) скрейпит `logs/*.log`, парсит
loguru-уровень в метку `level` и имя файла в метку `task`. Per-process логи `hr_work_<pid>`
схлопываются в один `task=hr_work` — иначе десятки PID раздули бы кардинальность
Loki-индекса. Хранилище Loki — filesystem, retention 30 дней (дольше файловых логов
с ротацией).

**Оговорки**

- Дашборд жив, только пока поднят Docker. Задачи от него не зависят — крон работает сам.
- Пароль `admin/admin` — для локального; наружу Grafana не публиковать.
- Панели по извлечённым из текста числам (отклики, «сегодня N») хрупки к смене формата
  строки лога; светофор по `level` и watchdog — устойчивы.
- Исторические логи до первого запуска Promtail в Loki не попадут (читает с момента старта).

## Диагностика

**Идут ли отклики.** В `logs/cron_apply.log` ищем `Пул кандидатов: N`, затем
`Отклик (сегодня K): <название>`.

Формат строки менялся — грепать `"Отклик:"` неверно, это уже давало ложный вывод
«0 откликов за день».

**Сколько за сегодня.** `data/apply_quota.json` -> `{date, count}`. Если `date` вчерашний,
счётчик считается нулевым.

**Живы ли процессы.**

```powershell
Get-Process python, node, chrome -ErrorAction SilentlyContinue |
  Select-Object Id, ProcessName, StartTime
```

Прогон дольше ~50 минут не должен существовать: сработает watchdog.

**Кто держит lock.** `data/autoclick.lock` -> `{pid, ts}`. Мёртвый pid освобождает lock
автоматически при следующей проверке — вручную файл удалять не надо.

Осторожно с диагностикой: `Get-Process -Id <pid>` может не найти процесс, а lock всё равно
считаться занятым, если проверка живости смотрит только на `OpenProcess` (убитый процесс
открывается, пока чужой хендл держит его объект). Достоверный ответ даёт сам код:

```powershell
..\.venv3\Scripts\python.exe -c "from hrwork.application.apply.runtime.lock import _lock_holder; print(_lock_holder())"
```

`None` — lock свободен/протух, кортеж `(pid, age)` — держит живой инстанс.

**Не протухла ли сессия.** В логе синка — «чаты не получены, сессия от <дата> могла
протухнуть». Лечится браузерным прогоном (`hh_apply`) или `--login`.

**Не сработал ли санити-гейт.** В `cron_collect.log` — `Источник hh: 300 << 16000 (< 50%)`.
Кеш при этом цел. Разбираться с блокировкой, а не запускать `--force` рефлекторно.

## Убить всё

`kill` из bash **не убивает** Windows-процессы Python. Только PowerShell:

```powershell
taskkill /F /IM python.exe /T
taskkill /F /IM node.exe /T
Get-Process python, node -ErrorAction SilentlyContinue      # должно быть пусто
```

После этого удалить `data/autoclick.lock`, если остался.

## Ручные прогоны

```
python hh.py collect                   # уважает кеш и гейт
python hh.py feed                      # пересобрать ленту (крон делает это сам после сбора;
                                       # руками — когда нужна лента свежее суточной)
python hh.py dashboard
python hh.py serve --port 8000
python hh.py autoclick --apply-limit 1 --headed     # один отклик, глазами
python hh.py autoclick --sync-status                # без браузера
```

## Правила эксплуатации

- **Не запускать два браузерных прогона одновременно.** Lock защищает, но `--force`-обходов
  быть не должно: два Chromium на один persistent-профиль = краш профиля.
- **После тестового запуска Python-процесс убивать.** Иначе они накапливаются и дерутся
  за lock.
- **`--force` на сборе — только руками**, когда точно известно, что спад реальный.
- **Правки в `apply/` проверять живым прогоном** с `--apply-limit 1..5`. Это единственный
  путь, отправляющий необратимые действия наружу.
