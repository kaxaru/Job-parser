# Тесты и критерии приёмки

## Главное правило

**Ожидаемое значение пишется ЛИТЕРАЛОМ до запуска кода.** Сначала из спецификации выводится,
что именно должно получиться, и это записывается в тест константой. Только потом запускается
реализация. Тест, чей `expected` подогнан под фактический вывод, не проверяет ничего — он
фиксирует поведение, включая баг.

Четыре следствия, каждое обязательно:

1. **Литерал, а не вычисление.** `assert codes == ("ack", "bot_interview")`, а не
   `assert codes == tuple(sorted(k.code for k in FROZEN_KINDS))`. Второй вариант повторяет
   реализацию и пройдёт при любой её ошибке.
2. **Точное значение, а не обобщённый флаг.** Никаких `assert is_ok`, `assert result`,
   `assert len(x) > 0`. Проверяется конкретика: `assert tone == "botiv"`,
   `assert applied == 1388`. Обобщённый булев проходит на десятке разных неправильных ответов.
3. **Словарь имён — из спецификации, не из кода.** Тест называет защищаемое свойство теми же
   словами, что и требование: `test_reject_on_bot_interview_keeps_red_frame`, а не
   `test_card_tone_branch_2`. Имя переживает рефакторинг, потому что описывает договор.
4. **Детали реализации в тест не протекают.** Тест не знает про приватные поля, порядок
   внутренних вызовов и промежуточные структуры — только вход и наблюдаемый результат. Иначе
   любой безопасный рефакторинг красит набор.

Практический критерий: **тест должен быть написуем по одной спецификации, не открывая код.**
Если для его написания понадобилось заглянуть в реализацию — он проверяет реализацию, а не
требование.

Исключений ровно два, оба узкие и обязаны быть подписаны комментарием на месте:

- **Стражи согласованности** (`test_role.py`) сравнивают два места намеренно — там одна
  сторона всё равно литерал, а не два вычисления.
- **Эквивалентность с эталонной реализацией** (`test_prescreen.py`: оптимизированный
  `_detect_techs` против прямого regex) — ожидаемое считает эталон, литерала быть не может
  by design. Смысл теста именно в равенстве двух реализаций.

**Циклов `for` в тестах нет — только `@pytest.mark.parametrize`** (JS: отдельный `it` на
случай). Цикл падает на первом же случае и скрывает остальные: неизвестно, сломан один вход
или все двадцать. Параметризация даёт отдельный тест на вход и называет его в отчёте —
`test_skips_non_engineering_roles[Риск-аналитик…]`. Подробности — раздел «Параметризация».

То же относится к «скрытым циклам»: цепочка `assert a and b and c` и `assert all(...)` —
такой же одиночный провал без имени виновника. Разворачивается в параметризацию.

Цикл допустим там, где случай **генерируется, а не перечисляется** (property-тест на
случайном корпусе с фиксированным seed) — перечислять нечего, и это подписывается
комментарием. Обход дерева/файла внутри одного случая циклом не является перебором случаев.

## Герметичность

**Тест не читает ни личный профиль запускающего, ни живое CRM-состояние, ни `.env`.** Правило
выглядит очевидным и именно поэтому нарушается тихо: набор остаётся зелёным, но проверяет
предпочтения владельца машины вместо договора проекта. Аудит 08.08.2026 нашёл здесь два
класса дефектов сразу, и оба стоили дороже любой другой находки того дня.

Первый — **личные настройки**. `candidates.py` компилирует чёрные списки, а `cover.py` —
шаблон письма ОДИН РАЗ на импорте, из значений `resume_profile.json`. Владелец, воспользовавшийся
ДОКУМЕНТИРОВАННОЙ ручкой (`"blacklists": {"qa": []}`, `"cover_template": "…"`), получал либо
сотню красных тестов, либо — хуже — зелёные тесты, проверяющие его личные предпочтения
(находка 57). Машинерия против этого — фикстуры в `tests/backend/conftest.py`, см. «Запуск».

Второй — **второй держатель зависимости**. Тест подменяет зависимость у объекта, через который
ходит ОН, а код ходит в неё через другого держателя, и подмена не срабатывает. В
`test_feed_build.py` фикстура подменяла четыре метода `store`, а `feed.py::_last_hr_replies`
звал пятый — `store.chat_messages()`, — и поле `hr_ts` считалось из переписки запускающего
(находка 59). Проверенный приём: **растяжка на настоящий загрузчик**. Рядом с подменой у
держателя, через которого идёт вызов, настоящий модуль патчится функцией, которая ПАДАЕТ, —
`mp.setattr(followup, "load_chat_messages", _live_crm_tripwire)`. Пока подмена на месте,
растяжка молчит; как только появится второй путь к живым данным, тест назовёт его вслух.

Патчить надо У ТОГО ДЕРЖАТЕЛЯ, ЧЕРЕЗ КОТОРОГО ИДЁТ ВЫЗОВ, а не у первого попавшегося: подмена
`hrwork.infrastructure.storage.followup.X` не видна коду, который импортировал `X` в свой
модуль, и наоборот. Растяжка снимает необходимость угадывать — она отвечает на вопрос
«а точно ли все пути перекрыты?» падением, а не зелёным прогоном.

## Запуск

```
pytest                                      # 2342 теста бэкенда: 2336 pass + 6 opt-in skip
pytest tests/backend/domain                 # один слой
npm test                                    # 184 теста фронта в 46 сюитах (node:test)
npm run lint                                # biome
ruff check .
mypy                                        # строгая проверка типов (mypy.ini)
```

Числа в этом файле — с прогона 08.08.2026 (`pytest --collect-only -q`). Все опубликованные
здесь разбивки идут ИЗ ОДНОГО прогона и в сумме дают общее число: 748 + 801 + 418 + 226 + 149
= 2342. Если сумма перестала сходиться — устарел этот файл, а не арифметика.

**mypy — strict, ноль ошибок.** Область: пакет `hrwork` + `hh.py` (`dwh_demo` исключён —
у него свой стек и свои конфиги). Внешние библиотеки без стабов (playwright, plotly,
httpx) идут как `Any` через `ignore_missing_imports` — это про ЧУЖОЙ код, свой типизирован
полностью. Значения, пришедшие из JSON/HTTP/Playwright, аннотируются `Any` осознанно:
это честный тип внешней границы, а не заглушка.

`conftest.py` в корне добавляет корень в `sys.path`. У `dwh_demo` свой `pytest.ini`,
гоняется отдельно.

### Pre-commit — те же проверки до пуша

```
pre-commit install                   # установить (один раз на клон)
pre-commit run --all-files           # прогнать по всему репо
SKIP=pytest git commit ...           # пропустить один хук
git commit --no-verify               # пропустить все
```

Конфиг — `.pre-commit-config.yaml`. Порядок: гейт venv -> ruff -> mypy strict -> pytest ->
npm test -> biome lint.

**`language: system`** — инструменты берутся из АКТИВНОГО окружения, а не из отдельных venv'ов
фреймворка: mypy и pytest требуют всех зависимостей проекта, а venv лежит вне репо
(`../.venv3`). Значит, **коммитить надо из активированного окружения**.

**Все вызовы через `python -m`**, а не голым именем. В `.venv3` нет `pytest.exe` — есть только
`ruff.exe` и `mypy.exe`; это тот же класс поломки, что описанный в CLAUDE.md сломанный
`pip.exe`. Голое `pytest` уходило в системный Python 3.14 и падало 37 ошибками сборки
`No module named 'dotenv'`, где настоящая причина не видна (инцидент 07.08.2026). Первым идёт
гейт `tools/check_venv.py`: он проверяет версию интерпретатора и даёт одну внятную строку.

`tools/` — инфраструктура сборки, нужна всем и версионируется целиком. Не путать со `scripts/`:
там ЛОКАЛЬНАЯ отладочная песочница, и 4 файла из 6 в `.gitignore`.

**`pass_filenames: false`** — ruff/mypy/pytest конфигурируются файлами в корне и знают свою
область сами. Список изменённых файлов сузил бы проверку: mypy на одном файле не увидит
поломку в его вызывающих, pytest прогнал бы не те тесты.

**`ruff format` выключен сознательно.** Замер 07.08.2026: переформатировал бы 103 файла из 115.
Код выровнен вручную (параметры в столбик по `=`, комментарии по колонкам), и коммит на сотню
файлов сделал бы `git blame` бесполезным — а комментарии здесь объясняют инциденты. Включать
только отдельным коммитом «форматирование», чтобы его можно было пропускать
через `git blame --ignore-rev`.

**mypy до 07.08.2026 не проверялся автоматически нигде** — правило «ноль ошибок» жило только
дисциплиной. Теперь он и в хуке, и в CI (джоба `scraper`).

### Профиль резюме в прогоне — два механизма

**Фолбэк профиля — в КОРНЕВОМ `conftest.py`, в `pytest_configure`/`pytest_unconfigure`.**
Если персонального `resume_profile.json` нет (чистый клон, CI), подкладывается
`resume_profile.example.json` и убирается после. Без него 12 тестов chat_reply/form_fill
падали пустыми ответами (вскрыто CI 23.07). Живой профиль не трогается и не читается —
только проверяется его наличие.

Раньше это была session-autouse фикстура, и она **опаздывала на целую конфигурацию**
(находка 63 аудита 08.08.2026): `hrwork/config.py` читает профиль НА ИМПОРТЕ, то есть при
сборке тестовых модулей, а фикстура работает при setup первого теста. На чистом клоне один
прогон жил на двух разных профилях — config на дефолтах, движки ответов (читают файл лениво)
на примере. `pytest_configure` вызывается до сборки.

Отсюда правило: **conftest стартового пути не имеет права импортировать `hrwork` на уровне
модуля.** Conftest'ы `testpaths = tests/backend` грузятся РАНЬШЕ `pytest_configure` корневого,
и такой импорт испёк бы конфигурацию до подкладывания профиля. Порядок не предполагается,
а стережётся: `tests/backend/test_profile_isolation.py::test_profile_fallback_precedes_config_import`
читает флаг `_config_imported_at_configure` через session-фикстуру `config_imported_at_configure`.

**Фикстуры `tests/backend/conftest.py` — вторая половина той же задачи** (находка 57):
документированные ручки профиля не должны менять результат тестов проекта.

- `apply_defaults` — прибивает `candidates.py` и `cover.py` к ДЕФОЛТАМ проекта. Подключается
  модульным `pytestmark = pytest.mark.usefixtures("apply_defaults")` в `test_autoclick.py`
  и `test_cover.py`. Дефолты иначе не достать: они стоят прямо в вызовах
  `candidates.py::_rx(key, default)` и после импорта уже перекрыты профилем запускающего,
  а из скомпилированного `re.Pattern` исходный дефолт не восстановить. Поэтому модуль
  выполняется заново в отдельном пространстве имён (в `sys.modules` не попадает), и наружу
  отдаются только UPPER-константы: классы второго экземпляра (`OutOfScope`, `ApplyTier`)
  не были бы равны настоящим по `is`.
- `module_constants_with_profile` — та же фабрика, но на ЗАДАННОМ профиле; ею пользуются
  стражи изоляции, которым нужно показать «с этой настройкой поведение другое».
- `pinned_profile_defaults` — значения профиля, на которые прибивает `apply_defaults`
  (`core`/`exp_ids` записаны литералом, их совпадение с репозиторными дефолтами стережёт
  `test_profile_isolation.py`).

## Раскладка

`tests/` зеркалит слои пакета — тест лежит там же, где код, который он защищает:

```
tests/
├─ backend/                   2342
│  ├─ domain/                  748  VO, классификация, парсинг, дедуп, период зарплаты,
│  │                                грейд, страж пресина
│  ├─ application/             801  отбор кандидатов, чаты, intent/rephrase, формы-анкеты
│  │                                (RFC-003), воронка автоотказов, аналитика, фасады
│  ├─ infrastructure/          418  девять источников, сеть, хранилище, поиск, LLM-транспорт
│  ├─ presentation/            226  сервер, графики, дашборд, фид, отчёты, санитайзер
│  └─ (корень backend/)        149  кросс-слойное: санити-гейт сбора, изоляция от профиля,
│                                   личные настройки, маскировка лога
└─ feed/                       184  фронт в 46 сюитах, гоняется node:test — НЕ pytest
```

Перекос в сторону `domain/` кажущийся: 510 из 748 — параметризованный страж пресина
(`test_prescreen.py`: 127 фрагментов словаря × 4 обёртки + 2 корпусных теста). Без него
слой весит 238 тестов.

`testpaths = tests/backend` сужен намеренно: иначе pytest пытается собирать
`tests/feed/*.js`. Фронт запускается своим раннером через `npm test`.

Файл кладётся по **основному предмету теста**, а не по всем импортам:
`test_collect_guard.py` импортирует `hrwork.config`, но проверяет `hh.py::_degraded_source`,
поэтому лежит в корне `backend/`, а не в `infrastructure/`. По тому же правилу в корне
оказались тесты, чей предмет — не слой, а весь прогон: изоляция от личного профиля
и маскировка тел в логе проверяются сквозь `config.py`, а не внутри одного пакета.

## Правила `pytest.ini`

```ini
addopts = -ra --strict-markers --strict-config
xfail_strict = true
markers =
    slow: тяжёлые прогоны по полному кешу вакансий (opt-in через переменную окружения)
```

- **`--strict-markers`** — незарегистрированный маркер становится ошибкой. Без него
  опечатка в `@pytest.mark.uint` молча выключала бы тест
- **`--strict-config`** — опечатка в самом `pytest.ini` тоже ошибка, а не тихий игнор
- **`xfail_strict`** — внезапно прошедший `xfail` считается провалом: баг починен,
  метку пора снять
- **`-ra`** — сводка по non-pass в конце, чтобы пропуски не терялись в выводе

## Пирамида

Основание — юниты на чистых функциях: классификация, отбор кандидатов, VO, ACL.
Интеграция — точечно, там, где есть внешний контракт. E2E нет и не будет: единственный
сквозной путь отправляет реальные отклики.

Playwright-путь покрыт **вокруг браузера**: `pick_candidates`, квота, lock тестируются
без Chromium, потому что вынесены в чистые модули. Это и было причиной их выноса.

## Параметризация

Набор однотипных входов оформляется `@pytest.mark.parametrize`, **не циклом внутри теста**:

```python
@pytest.mark.parametrize("name", [
    "Риск-аналитик (проект ПВР)",
    "Портфельный аналитик/портфельный менеджер",
])
def test_skips_non_engineering_roles(name):
    assert pick_candidates([_raw(name=name)], marks={}, limit=10) == []
```

Причина не стилистическая. Цикл падает на первом же случае и **скрывает остальные**:
неизвестно, сломан один вход или все. Параметризация даёт отдельный тест на случай,
имя которого сразу называет вход — `test_skips_non_engineering_roles[Риск-аналитик…]`.

Замер того перевода (исторический, набор с тех пор вырос до 2342): семь циклов дали
209 -> 246 тестов при том же покрытии. Тот же эффект в масштабе виден на `test_prescreen.py` —
127 фрагментов × 4 обёртки = 508 именованных случаев вместо одного цикла, падающего на первом.

Когда у входов **разные ожидаемые значения**, они идут в параметризацию парой
`(вход, ожидаемое)` — литералом, по главному правилу, а не вычислением из кода:

```python
@pytest.mark.parametrize("text, expected", [
    ("Пройдите интервью с ГигаРекрутером", "bot_interview"),
    ("Заполните небольшую анкету", "screening"),
    ("Напишите мне в телеграм @ivan_hr", "redirect"),
])
def test_employer_message_kind(text, expected):
    assert classify(text).code == expected
```

В JS роль параметризации играет отдельный `it` на случай (`node:test` не имеет table-driven
API) — цикл внутри `it` запрещён по той же причине.

## Тесты-стражи

Отдельный жанр: они защищают не поведение функции, а **согласованность между двумя местами**.

- `test_role.py` — каждый ключ `config.ROLE_PATTERNS` (16) имеет член `Role` (17: `NON_IT`
  служебный, паттерна у него нет). При расхождении импорт `parsing.py` упал бы в проде;
  тест ловит раньше.
- `test_prescreen.py` — оптимизация даёт тот же результат, что чистый regex. Замер на момент
  ввода: 0 расхождений на 34k вакансий, 137 c -> 8 c.
- `test_feed_build.py` — константы, продублированные между Python и JS, реально доезжают
  в `feed-data.js`; ожидаемое — литерал (`CHAT_FROZEN_PY == ["ack", "bot_interview"]`),
  а не `list(FROZEN_CODES)`, иначе тест повторил бы реализацию.
- `test_feed_bridge.py` — вторая сторона того же моста: офлайн-фолбэк в `src/feed/*.js`
  (копия константы для `file://` без `feed-data.js`) равен источнику в Python. Копия без
  стража живёт своей жизнью — так уже разъехались `STATE_LABELS` и `APPLY_CORE`.
- `test_grade.py` — два смежных словаря грейдов: `experience.py::_GRADE_TO_EXP` через
  `Grade.from_experience` против `grade.py::_TITLE_RX` через `Grade.from_title`. Набор
  намеренных расхождений закреплён литеральным словарём из ТРЁХ записей (`middle`, `mid`,
  `senior`); цена дрейфа здесь — сумма, которую называют работодателю.
- `test_profile_settings.py::test_example_blacklist_rejects_the_same_titles_as_the_default`
  — `resume_profile.example.json` отсеивает те же тайтлы, что и дефолты кода. Пример,
  разошедшийся с дефолтом, даёт форку молчаливые отклики на то, что он отбирать не хотел
  (инцидент 08.08.2026: в примере не было QC/Test Engineer).
- `test_collect_guard.py` — санити-гейт не даёт затереть кеш деградированным срезом; заодно
  стережёт имя meta-ключа `pre_dedup_by_source`. Имя записано в тесте ЛИТЕРАЛОМ, а не
  импортом константы, намеренно: переименование ломает совместимость с уже лежащим на диске
  `cache_meta.json` и обязано ронять тест, а не молча переезжать вместе с кодом.

Страж согласованности сам может отстать от кода — и это тоже расхождение. Так вышло
с `PORTAL_SITES_PY`: глобал появился в `build_feed` 01.08.2026, а в литеральный список
`test_feed_build.py` его не добавили, и «каждый глобал обязан присутствовать» проверялось
для десяти из одиннадцати. Лечится метастражем:
`test_globals_guard_covers_every_injected_const` считает фактические `const` в бандле
и сверяет множество с параметризацией (сейчас 15 имён). Там, где список перечислен руками,
стоит завести такую сверку с реальностью.

Такие тесты обязательны везде, где константа продублирована или введена оптимизация.

## Как называть тесты

Имя описывает **защищаемое свойство**, а не вызываемую функцию — тогда оно переживает
рефакторинг.

- Плохо: `test_suggest`
- Хорошо: `test_specific_practice_over_known_tech_is_silent`

В тестах-регрессиях полезно оставлять дату и суть инцидента:

```python
def test_specific_practice_over_known_tech_is_silent():
    # БАГ 20.07: «опыт автоматизации тестирования ML-сервисов НА Python» -> движок отвечал
    # «Да, есть опыт: Python», подтверждая не то, о чём спросили. Теперь молчим.
```

## Пробелы в покрытии

Признаём честно (после закрытия дыр по `server.py`/`charts.py`/`dashboard.py`/`build_feed` —
остались тонкие, осознанные):

- **Бизнес-логика хендлеров `server.py`** (`_marks_get`, `_forms_get`, `_statuses_get`,
  `_applied_get`, `_chats_get`, `_search`, тело `_apply_post`) — покрыт их ДИСПАТЧ (нужный
  хендлер вызван), но не внутреннее поведение: делегируют в `store`/`search`/`autoclick`,
  тестировались бы стабами этих зависимостей. `_write` в реальный сокет и `run_server` — вне
  юнитов намеренно (без биндинга порта).
- **`build_feed` / `build_dashboard` — нет DI-шва.** Обе функции без аргументов: читают
  модульные пути-константы, синглтон `store`, `rates.get_rates()` и сами конструируют репозиторий.

  `feed.rates.get_rates`, `feed.shutil.which`, `feed.DATA_DIR/FEED_OUT`). Минимальный шов на

  сознательно НЕ добавлен (правка структуры ради тестов = отдельная задача -> бэклог).
- **esbuild-ветка `build_feed`** — не гоняется: `shutil.which` застабан в `None`, тест бьёт по
  фолбэку и остаётся герметичным. Реальный бандл — интеграционная забота, не структурная.
- **`age/gap/fresh` по значению** — проверяются как присутствующие ключи, но не по значению:

- **Иные формы фигур `charts.py`** (`chart_salary_lang`/`_exp`, `heatmap_city_lang`,

- **Вкладка «Автоотказы / воронка» на уровне presentation** — покрыта только её АГРЕГАЦИЯ

## Критерии приёмки

Задача считается выполненной, когда:

1. **Тесты зелёные** — `pytest` + `npm test`, ноль упавших
2. **Линтеры чистые** — `ruff check .` + `npm run lint` + `mypy` (strict, ноль ошибок)
3. **Новое поведение покрыто тестом**, имя которого называет свойство
4. **Регрессия оформлена тестом с датой и сутью инцидента**
5. **Ручная верификация из спеки выполнена** — команды выполнены, вывод совпал с ожидаемым
6. **Для правок в `apply/`** — живой прогон `--apply-limit 1..5`, отклики появились
   в `applied_log.jsonl` и в ленте
7. **Документация обновлена** — соответствующий файл в `docs/`, если менялось поведение
   или контракт
8. **Осознанные компромиссы записаны** — в коде комментарием и в доке разделом

Пункты 6 и 8 — не формальность. Шестой ловит то, что юниты поймать не могут, восьмой
не даёт следующему аудиту «починить» намеренное решение.
