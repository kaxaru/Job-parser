# Хранилище

## Overview

**Слой:** `hrwork/infrastructure/storage/`, плюс `infrastructure/search.py` для Postgres.

Полноценной БД в ядре нет — осознанный выбор (обоснование в [`architecture.md`](architecture.md)).
Раздел заменяет привычный `database.md`: роль таблиц играют файлы в `data/`.

```
источники ──> ACL ──> VacancyRecord ──> JsonVacancyRepository ──> data/vacancies_raw.json
                                              │
                                              └── _to_dict / _from_dict  ← единственное место,
                                                     знающее сырую схему

лента ──> server ──> ApplicationStore ──┬──> marks.json          отметки пользователя
                                        ├──> applied_log.jsonl   журнал (append-only)
autoclick ──────────────────────────────┼──> apply_quota.json    рантайм
                                        └──> followup.*          статусы, чаты, формы, очередь
```

## Соглашения

**Атомарная запись** — `jsonio.atomic_write_json`: `mkdir(parents)` + tmp-файл **рядом
с целевым** + `os.replace`. Читатель видит либо старый файл целиком, либо новый.
Tmp создаётся рядом, а не в системном temp, потому что `os.replace` атомарен только
в пределах одной ФС.

**Мягкое чтение** — `jsonio.read_json_or(path, default)`: нет файла, битый JSON **или тип
не совпал с типом `default`** -> `default`. Проверка типа важна: `{}` вместо ожидаемого `[]`
роняет потребителя не в момент чтения, а позже и в другом месте.

**Один писатель на файл** — обеспечивается снаружи: single-instance lock для браузерного
пути, `threading.Lock` для marks (пишет многопоточный сервер).

**Три категории по жизненному циклу** — кеш данных, состояние пользователя, рантайм.
Различие практическое: первое восстанавливается пересбором, второе невосстановимо,
третье пересоздаётся само.

## Репозиторий

**`VacancyRecord`** (`repository.py::VacancyRecord`) — сущность плюс payload хранения:
`vacancy: Vacancy` + `url`, `description_html`, `requirement`, `sig`, `enriched`,
`enriched_at`.

Разделение принципиально: домен не знает про HTML описания, URL портала и маркеры кеша.
`Vacancy` остаётся чистой, всё внешнее висит на записи.

**Протокол** (`repository.py::VacancyRepository`, `runtime_checkable`):

```python
exists() -> bool
load()   -> list[VacancyRecord]
save(records) -> None
```

Реализация — `JsonVacancyRepository(path=RAW_FILE)`. Подмена на `PgVacancyRepository`
не затронет ни одного потребителя.

**Маппинг** `repository.py::_from_dict` / `::_to_dict` — единственный код в проекте,
знающий сырые ключи. Парсинг происходит **один раз** внутри репозитория; раньше каждый
читатель звал `parse_vacancy` сам.

## Файлы состояния

### `vacancies_raw.json` — кеш данных

**Назначение.** Все собранные вакансии четырёх источников (hh, hirify, talanto, getmatch),
после кросс-портального дедупа (`domain/dedup.py`).

**Формат.** Массив записей. Реальная запись (описание вырезано, сниппет обрезан):

```json
{
  "id": "135125416",
  "name": "Python-разработчик",
  "area": {"id": "1", "name": "Москва"},
  "salary": {"from": 150000, "to": null, "currency": "RUR", "gross": false},
  "experience": {"id": "noExperience"},
  "schedule": {"id": "fullDay"},
  "snippet": {"requirement": "О компании ООО НПП «МетаСофт ПРО» — команда…",
              "responsibility": "…"},
  "alternate_url": "https://hh.ru/vacancy/135125416",
  "employer": {"name": "НПП МетаСофт Про"},
  "created_at": "2026-07-13T12:04:03.511+03:00",
  "published_at": "2026-07-19T12:04:03.511+03:00",
  "responses": 432,
  "_source": "hh",
  "_sig": "2026-07-19T12:04:03.511+03:00",
  "_enriched": true,
  "_enriched_at": "2026-07-19T11:50:17.474928+00:00",
  "description_html": "<p>…</p>"
}
```

Служебные ключи с подчёркиванием — payload хранения, не данные портала.

**Пишет.** `repository.py::save` / `files.py::save_raw` (атомарно, + `save_meta`).
**Читает.** `repository.py::load`, дальше все потребители.

**Edge cases**

- `salary: null` — вилки нет вовсе; `to: null` — только нижняя граница
- Зарплата хранится уже **net** (`gross: false`), поэтому повторное чтение не вычитает
  НДФЛ второй раз — roundtrip стабилен
- `_enriched: false` — описание ещё не добрано (tldr-заглушка hirify)
- id hirify/talanto неймспейснуты: `hirify_749017`, `talanto_<uuid>` — не сталкиваются
  с числовыми id HH

### `cache_meta.json` — кеш данных

**Назначение.** Метаданные последнего сбора; на них работает решение «нужен ли пересбор».

**Формат** (списки обрезаны):

```json
{
  "collected_at": 1784462109.909347,
  "cities": ["1", "2", "3", "..."],
  "queries": ["разработчик", "программист", "software engineer", "..."],
  "sources": ["hh", "hirify", "talanto"],
  "count": 92730
}
```

**Пишет.** `files.py::save_meta`. **Читает.** `files.py::cache_valid`.

**Почему так.** Пересбор нужен, если поменялись **города, запросы или набор источников**,
либо возраст превысил `CACHE_TTL_HOURS`. Правка `SEARCH_QUERIES` инвалидирует кеш, даже
если он свежий по времени — иначе новый запрос не собрался бы сутки.

**Edge cases.** Битый файл -> пересбор с нуля.

---

### `fx_rates.json` — кеш данных

**Назначение.** Курсы валют для приведения зарплат к одной оси.

**Формат.** База — USD:

```json
{
  "fetched_at": 1784495395.6312172,
  "rates": {"USD": 1.0, "RUB": 77.3, "EUR": 0.874, "BYN": 2.884659, "…": 0}
}
```

**Пишет и читает.** `net/rates.py::get_rates`, TTL 24 ч.

**Edge cases**

- Каскад фолбэков: свежий кеш -> фетч -> **старый кеш даже протухший** -> хардкод
- Запись **своим** tmp+replace, а не через `jsonio` — ради независимости от storage-пакета.
  Паттерн живёт в двух местах, это надо знать

---

### `marks.json` — состояние пользователя

**Назначение.** Ручные отметки: отклик или отказ. Переживает любой пересбор — сбор этот
файл не трогает вообще.

**Формат**

```json
{"80675242": "rejected", "134662537": "applied"}
```

**Пишет.** `marks.py::save_marks` — фильтрация по allowlist + `atomic_write_json`
под модульным `threading.Lock`. **Читает.** `marks.py::load_marks`, та же фильтрация.

**Edge cases**

- Битый или не-dict -> `{}` + warning: отметки теряются, система работает
- Значение вне allowlist отбрасывается и при чтении, и при записи
- Пишет многопоточный `ThreadingHTTPServer` — отсюда `Lock`

---

### `applied_log.jsonl` — состояние пользователя

**Назначение.** Журнал откликов с таймстампами. Основа режима «Мои отклики за период»
и восстановления после сбоя.

**Формат.** JSON Lines, одна запись на строку:

```json
{"id": "134809303", "name": "BI-аналитик", "url": "https://hh.ru/vacancy/134809303",
 "via": "cron", "status": "applied", "ts": "2026-07-23T14:03:26+04:00", "employer": "ООО Ромашка"}
```

`via` — `cron` | `feed` | `hh` (`ApplyChannel`). `employer` фиксируется в момент отклика —
вакансия уйдёт из выдачи, а воронка (`funnel.py`) работодателя не потеряет; в старых
записях поля нет (и наивный `ts` без зоны — читается как локальная зона машины).

**Пишет.** `followup.py::append_applied` — **единственная неатомарная запись в проекте**,
обычный `open("a")`. **Читает.** `followup.py::load_applied_log`.

**Edge cases**

- Одна вакансия может встречаться несколько раз (крон + дожурналирование синком);
  лента берёт **самый ранний** `ts`
- Битая строка пропускается при чтении — частичная запись не роняет журнал

**Почему так.** Append-only безопасен без атомарности, потому что single-instance lock
гарантирует одного писателя, а чтение устойчиво к обрыву последней строки. Полная
перезапись на каждый отклик была бы дороже и рискованнее.

---

### `response_status.json` — состояние пользователя

**Назначение.** Статусы откликов с HH для CRM-бейджей в ленте.

**Формат.** Код `currentApplicantState` как есть:

```json
{"134662537": "RESPONSE", "133629751": "DISCARD"}
```

**Пишет.** `followup.py::save_statuses` (из `autoclick.py::sync_statuses`).
**Читает.** `store.statuses()` -> `/api/statuses`.

**Edge cases.** Незнакомый код от HH не ломает ленту — рендерится сырым. Без запуска синка
данные устаревают молча.

---

### `chat_messages.json` — состояние пользователя

**Назначение.** Переписка по каждому чату плюс признак возможности писать.

**Формат**

```json
{
  "134020511": {
    "chatId": 5487335827,
    "write": {"name": "ENABLED"},
    "messages": [
      {"text": "Здравствуйте, Антон…", "mine": false,
       "ts": "2026-07-14T09:12:03", "bot": false}
    ]
  }
}
```

`mine` — наше сообщение (`canEdit` в API). `bot` — `participantDisplay.isBot`.

**Пишет.** `followup.py::save_chat_messages` (из `sync_statuses`).
**Читает.** `store.chat_messages()` -> `/api/chats` -> `chat_class.analyze`.

**Edge cases.** Сохраняются только `type == "SIMPLE"` с непустым текстом — служебные
«рекрутер присоединился» отбрасываются.

---

### `form_vacancies.json` — состояние пользователя

**Назначение.** Вакансии-опросники, которые автоклик не заполняет.

**Формат**

```json
{"134427427": {"name": "Python-backend developer",
               "url": "https://hh.ru/vacancy/134427427", "ts": ""}}
```

**Пишет.** `followup.py::add_form_vacancy` — идемпотентно по id.
**Читает.** `store.forms()` — в `pick_candidates` как `form_ids` и в `/api/forms`.

**Почему так.** Отдельная очередь, а не отметка в `marks`: в ленте опросник получает бейдж
«форма», а не отказ, и фильтр снимается одним флагом `APPLY_SKIP_FORMS`.

**Edge cases.** `ts` пустой у записей, добавленных до введения таймстампа.

---

### `forms_cache.json` — состояние пользователя

**Назначение.** Кеш структуры форм-анкет после свипа (`forms.sweep`): вопрос/тип/опции +
статус (`ok`/`empty`/`error`, VO `FormSweepStatus`). Свип не переоткрывает уже закешированные
формы; мёртвые (`empty`/`error`) чистятся из очереди и гасятся серым «⌛ не актуальна» в ленте.

**Пишет.** `followup.py::cache_form` (фасад `store.cache_form`).
**Читает.** `store.form_cache()` / `store.cached_form_ids()` — свип, `clean_queue`, `feed.py`.

---

### `apply_pending.json` — состояние пользователя

**Назначение.** Очередь «откликнуться» из ленты в крон, когда браузер занят.

**Формат.** Список задач: `[{"id", "url", "name", "cover"}]`.

**Пишет.** `followup.py::enqueue_pending` (идемпотентно, возвращает позицию).
**Читает и снимает.** `followup.py::pop_pending_one` — FIFO **по одному**, чтобы
подхватывать добавленное во время дренажа.

**Edge cases.** Координация чисто файловая; окно гонки признано малым, худший эффект —
пропуск или повтор одного элемента.

---

### `autoclick.lock` — рантайм

**Назначение.** Single-instance: два Chromium на один persistent-профиль ломают профиль.

**Формат**

```json
{"pid": 27560, "ts": 1784489401.4700394}
```

**Пишет и снимает.** `lock.py::_single_instance` (`unlink` в `finally`).
**Читает.** `lock.py::_lock_holder`.

**Edge cases**

- Основная проверка — **живость pid**; TTL 4 ч страхует лишь переиспользование pid
- Битый или недописанный JSON **не** считается «свободным» вслепую: возраст берётся
  по mtime, свежий -> вероятно живой писатель
- После `taskkill` файл остаётся, снимается по мёртвому pid при следующей проверке

---

### `apply_quota.json` — рантайм

**Назначение.** Дневной счётчик откликов против лимита HH.

**Формат**

```json
{"date": "2026-07-20", "count": 3}
```

**Пишет.** `quota.py::bump_quota`. **Читает.** `quota.py::applied_today`.

**Почему так.** Счётчик возвращается, только если `date == сегодня`; запись за прошлый день
молча трактуется как 0. Самосброс без отдельной крон-задачи очистки.

**Edge cases.** `bump_quota` — read-modify-write без файловой блокировки. Практической
гонки нет (писатели разведены общим lock'ом), но защиты на уровне файла тоже нет.

---

### `bump_state.json` — рантайм

**Назначение.** Кулдаун поднятия резюме (HH разрешает раз в 4 ч).

**Формат**

```json
{"last_ok": "2026-07-19T23:30:25+04:00"}
```

**Пишет.** `bump_state.py::mark_bumped` — **только** при успешном поднятии.
**Читает.** `bump_state.py::bump_due`.

**Edge cases.** Битый ISO -> `None` -> `bump_due()` истинно: лучше лишняя попытка,
чем застрявший кулдаун.

---

### `hh_state.json` и `browser_profile/` — рантайм

**Назначение.** Куки сессии для HTTP-клиента и persistent-профиль Chromium.

**Пишет.** `session.py::save_state` при каждом успешном входе.
**Читает.** `session.py::open_client` — весь чат-путь без браузера.

**Edge cases.** Протухание не детектится: вызовы `chat.*` вернут пусто, куки обновит
следующий браузерный прогон. Удаление профиля требует повторного `--login`.

**Безопасность.** Обе сущности дают живой доступ к аккаунту — в передаваемый наружу бэкап
попадать не должны.

## Инкрементальный кеш описаний

Самый дорогой этап сбора — карточки, поэтому описание переиспользуется, пока вакансия
в выдаче и её `sig` не менялся.

`files.py::cache_hit_usable` требует три условия: sig совпал, описание непустое, возраст <
`DESC_CACHE_MAX_AGE_DAYS` (14; `0` отключает).

Третье — предохранитель от **тихой правки вакансии без смены сигнала**.

`files.py::load_desc_cache` берёт только записи с `_enriched` **и** непустым описанием:
tldr-заглушки не должны блокировать будущую дозагрузку.

## Полнотекстовый поиск (Postgres)

`infrastructure/search.py` — **опциональный** путь для `/api/search`. Ядро скрапера БД
не использует.

Таблица из env `SEARCH_TABLE` (дефолт `search_demo.vacancies`), `LIMIT_MAX = 100`.
Контракт запроса и ответа — в [`api.md`](api.md#get-apisearch).

Два режима через фабрику `search.py::_mode_for`: FTS (`websearch_to_tsquery('russian')`,
`ts_rank`, `ts_headline` с `<mark>`) и PLAIN (сортировка по `sal_mid`).
`total` — через `count(*) OVER()` в том же запросе.

**Безопасность.** Все пользовательские входы — только параметры psycopg2; в текст SQL
подставляется единственная вещь: имя таблицы из окружения.

`psycopg2` импортируется лениво внутри `search.py::_connect`, чтобы сборка SQL
тестировалась без драйвера. Падение БД -> `SearchUnavailable` -> 503.

## Бэкап

Копия `data/` без `browser_profile/` и `feed-*.js`. Логи бэкапить не нужно — они живут
отдельно, в `logs/`.

Критично и **невосстановимо**: `marks.json`, `applied_log.jsonl`, `response_status.json`,
`chat_messages.json`, `form_vacancies.json`. Журнал частично восстановим из чатов синком.

Остальное пересоздаётся: кеш — пересбором, рантайм — сам.
