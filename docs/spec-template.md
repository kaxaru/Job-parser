# Шаблон спецификации

Спека здесь — не проза, а **контракт с гейтами**. Она пишется ДО кода и отвечает на вопрос
«почему мы уверены, что это сработает», а не «что примерно сделаем».

Причина строгости: часть путей необратима (`hh_apply` шлёт реальные отклики, сбор перезаписывает
кеш), поэтому стратегия «сделаем и посмотрим» недопустима. Спека — страховка от необратимого
действия.

Приоритеты наследуются из `CLAUDE.md`: evidence > assumptions, correctness → security →
performance → maintainability → DX, минимальные точечные правки вместо переписывания.

---

## Гейты готовности

Спека готова, когда выполнено ВСЁ:

- [ ] каждое фактическое утверждение подкреплено ссылкой на код, цифрой или выводом команды;
      непроверяемое помечено `[Speculation]` со списком допущений
- [ ] ссылки на код — по **имени символа** (`parsing.py::_detect_role`), не по номеру строки:
      номера устаревают после первого же рефакторинга, имена переживают его
- [ ] ни одна новая абстракция не описана примитивом (`str`/`int`/`dict` вместо VO — дефект
      проектирования, а не деталь реализации)
- [ ] новый или изменённый интерфейс выписан **реальным примером** запроса/ответа,
      а не списком полей; перечислены все значения enum-полей и вид ответа при отказе
- [ ] для каждого риска назван фолбэк
- [ ] каждый пункт верификации имеет ОЖИДАЕМЫЙ вывод, а не «проверить что работает»
- [ ] назван раздел «Не делаем» / осознанные компромиссы
- [ ] в plan mode — пройдено Codex-ревью (`upgrade.md`); если Codex недоступен, вместо него
      раздел «Само-ревью» с зафиксированными развилками

Практический критерий качества: раздел «Риски» не короче раздела «Архитектура». Если короче —
крайние случаи ещё не продуманы.

## Структура

### 1. Context — только факты

Цифры и ссылки на код, не ощущения.

- ПЛОХО: «зарплаты неудобно сравнивать»
- ХОРОШО: «HH шлёт `RUR` (16031 записей), hirify — `USD/EUR/RUB/GBP/CAD/PLN/USDT/BYR/AUD`;
  слайдер `SAL_MAX` мешает их на одной числовой оси»

Половина плохих спек умирает здесь — когда выясняется, что проблемы нет.

### 2. Архитектура — по слоям, с именами файлов

Проект разложен на 4 слоя (`domain / application / infrastructure / presentation`).
Для каждого куска сказать, в каком слое он живёт и почему.

Правило: доменное понятие описывается Value Object'ом. `ApplyTier(IntEnum)` появился вместо
`tier: int` именно потому, что магический `0`-сентинел был пойман на этапе спеки.

Два контракта VO в проекте, выбрать явно:
- **мягкий парсер** — `from_code() -> VO | None`, дефолт применяет вызывающий (внешние данные)
- **строгий roundtrip** — `from_label()` бросает исключение, fail-fast на дрейф (наши константы)

### 3. Ключевые файлы

Разделять НОВЫЕ и ПРАВКИ — это оценка риска на глаз. Новый модуль изолирован; правка в
`autoclick.py` трогает боевой путь откликов.

```
НОВЫЙ:  hrwork/rates.py (+ data/fx_rates.json кеш)
ПРАВКИ: hrwork/views/feed.py, src/feed/{model,main}.js
```

### 3a. Контракты — реальными примерами, а не списком полей

Если спека вводит или меняет интерфейс — HTTP-эндпоинт, сигнатуру публичной функции, схему
файла на диске, формат события — привести **настоящий вход и выход**, скопированный из
работающей системы или из кода, а не перечень имён полей.

Перечень полей выглядит понятным и скрывает ровно те ошибки, которые дорого стоят:
как поле называется в query против внутреннего имени, какого оно типа, что приходит при
пустом значении.

ПЛОХО:

```
GET /api/search — параметры: q, city, sal_min, limit, offset
```

ХОРОШО:

```
GET /api/search?q=python&city=Москва&sal=150000&limit=20

{"query": "python", "sal_min": 150000, "total": 412, "count": 20,
 "results": [{"id": "134809303", "name": "Python Developer", "rank": 0.0607}]}
```

Разница не косметическая: в query параметр называется `sal`, а внутри — `sal_min`.
По списку полей это не видно, и фильтр молча не сработает. Ошибка реально жила
в документации, пока контракт не был выписан примером.

Требования к примерам:

- брать из живой системы (`curl`, вызов `store.*`, дамп файла), не сочинять
- перечислять **все** значения enum-полей: `sender` — `bot | template | human`,
  а не «строка»
- показывать не только успех: ответ при отказе, при пустом результате, при занятом ресурсе
- для необратимых операций — пометка в контракте, а не в прозе

### 3b. Единообразие и уровни абстракции

Когда описывается больше трёх однотипных вещей (эндпоинты, источники, задачи крона) —
одинаковые разделы у каждой. Читатель ищет ответ на один и тот же вопрос по всем элементам,
и сканирование одинаковых заголовков быстрее чтения прозы.

Эталон в проекте — [`api.md`](api.md): Назначение · Request · Parameters · Response ·
Status Codes · Implementation · Edge cases · Почему так.

**Уровни не смешивать.** Что снаружи (контракт), чем реализовано (`Implementation`), что при
отказе (`Edge cases`) и почему выбрано так (`Почему так`) — разные разделы. В одном абзаце
`503`, `SearchUnavailable`, Postgres и «лента продолжает работать» — четыре разных уровня,
и такой абзац невозможно ни просмотреть, ни поддерживать.

**Схема, если задействовано больше двух модулей.** ASCII-диаграмма потока экономит абзац
описания и сразу показывает направление зависимостей.

### 4. Риски / крайние случаи

Формат каждого пункта: **ситуация -> что сломается -> что делаем**.

Пример: «`BYR` — старый белорусский код, в API его нет -> конверсия даст мусор -> алиас
`BYR->BYN`; если и `BYN` нет в ответе — фолбэк-курс».

Обязательные вопросы к себе: что при недоступности сети? при пустом входе? при нуле (truthiness
на нуле — уже пойманный в этом проекте класс багов)? при параллельном запуске? что с уже
накопленными данными на диске — нужна ли пере-сборка?

### 5. Верификация — команды и ожидаемый вывод

Три уровня:

1. **Изолированно**: `python -c "from hrwork import rates; print(rates.get_rates())"` ->
   словарь курсов; повторный вызов — из кеша, без сети.
2. **Интеграция**: `python hh.py feed` -> в `feed-data.js` присутствует `FX_RATES`.
3. **Регресс**: `pytest` + `node --test tests/feed/*.test.js` + `ruff` / `biome`.

Новые тесты перечислить С УКАЗАНИЕМ СВОЙСТВА, которое каждый защищает — такая формулировка
переживает рефакторинг:

- ПЛОХО: `test_suggest` — тест на `suggest()`
- ХОРОШО: `test_specific_practice_over_known_tech_is_silent` — движок не подтверждает опыт,
  о котором не спрашивали

### 6. Осознанные компромиссы — «НЕ трогать»

Самый недооценённый раздел. Без него следующий аудит «починит» решение, принятое специально.

Живые примеры: `config.py` помечен `[~] ОСТАВЛЕН ОСОЗНАННО`; город в `resume_profile.json`
намеренно не упоминается в ответах бота (в резюме на HH — Москва ради ATS-ранжирования,
фактически — Тольятти).

### 7. Само-ревью / Codex

В plan mode — протокол `upgrade.md` (максимум 3 цикла, вердикт APPROVED/NEEDS_REVISION).
Codex-модели `gpt-5.x-codex` заблокированы для ChatGPT-аккаунта — тогда вместо него раздел
«Само-ревью», где решение записано ВМЕСТЕ с отвергнутой альтернативой:

> База USD для конверсии — избегаем цепочек ошибок при кросс-курсах; round-trip тест страхует.

## Мини-пример (заполненный)

**Context.** `sync_statuses` помечает FORM-вакансии как отказ; в `feed.html` они уже маркируются
как форма (`hrwork/application/apply/candidates.py:APPLY_SKIP_FORMS`). Двойная маркировка —
47 записей за 19.07.

**Архитектура.** `form_ids: frozenset[str]` прокидывается в `pick_candidates`; решение
«пропустить» принимается в application-слое, синк о формах не знает.

**Риск.** Вакансия перестала быть формой -> id остаётся в `form_ids` навсегда.
Фолбэк: пересчёт множества при каждом сборе, не накопление.

**Верификация.** `pytest tests/backend/application -k form` -> 3 passed; прогон с
`--apply-limit 5` -> в `logs/hr_work_*.log` нет строк `Отклик` по id из `form_ids`.

**Не делаем.** Автозаполнение форм — отдельный трек, требует LLM и валидатора.
