# Переписка с работодателями

**Слой:** `hrwork/application/apply/chat/` — `chat.py` (API chatik), `chat_class.py`,
`chat_answer.py`, `chat_reply.py`, `chat_intent.py`, `chat_rephrase.py`.

## Назначение

После отклика открывается чат. Работодатели пишут отказы, приглашения и вопросы — часть
руками, часть ботами-скринерами с шаблонными сообщениями. Задача: понять, что происходит
в каждом чате, и не заставлять человека читать 600 переписок, чтобы найти 20 живых.

## Транспорт

`chatik.hh.ru` — **cookie-only** плюс `x-xsrftoken`. Group-IB fingerprint-гейта здесь нет,
в отличие от отклика и `/resumes/touch`. Поэтому все чат-операции идут httpx-клиентом поверх
`data/hh_state.json`, без браузера и без lock.

Endpoint'ы (`chat.py`):

- `filter_clusters` — vacancyId всех чатов (= всех откликов)
- `chats?page=N` — постраничный список
- `chat_data?chatId=&applicantId=` — сообщения + `currentApplicantState`
- `save` — правка текста сообщения (слот сопроводительного)
- `send` — новое сообщение
- `quick_replies` — подсказки HH

Заголовки: `accept: application/json`, `x-xsrftoken`, `x-requested-with: XMLHttpRequest`,
`x-hhtmsource: app`, `referer: https://chatik.hh.ru/?platform=xhh&dest=iframe`.

### Отправка сообщения

`send_message(ctx, xsrf, chat_id, text, *, vacancy_url, idempotency_key)` (`chat.py::send_message`).

```json
{"chatId": int, "idempotencyKey": "<uuid4>", "text": "...",
 "metadata": {"chatType": "NEGOTIATION", "parentWindowUrl": "<vacancy_url>",
              "location": "chatik", "platform": {"name": "xhh", "data": {}}}}
```

`idempotencyKey` — защита HH от дублей: повтор с тем же ключом не создаст второе сообщение.
Генерируется на каждый вызов, поэтому **ретрай обязан переиспользовать тот же ключ** —
ответственность на вызывающем, внутри `send_message` ретрая нет.

`metadata.source` намеренно **не** проставляется. В браузере это поле помечает шаблон
быстрого ответа (`quick_reply` + `template_id`); наш текст шаблоном HH не является, и врать
в телеметрии не нужно.

`quick_replies` оказался бесполезен для автоответов: это вопросы **соискателя работодателю**
(«Какой график работы?»), а не варианты ответа. Оставлен для полноты API.

## Классификация переписки

`chat_class.py`. Статистическая база — 600 чатов, 683 сообщения работодателей: 51 %
оказались дословными повторами. Отказ 30 %, приглашение 25 %, живой текст 17 %,
бот-скрининг 14 %, прямой вопрос 13 %.

### `ChatKind` (`chat_class.py::ChatKind`)

`QUESTION` / `SCREENING` / `REDIRECT` / `INVITE` / `REJECT` / `OTHER` / `NONE`.
`.needs_reply` истинно для всех, кроме `REJECT` и `NONE`.

**Порядок проверок важен**: SCREENING -> REJECT -> REDIRECT -> INVITE -> QUESTION -> OTHER.
Скрининг и отказ распознаются раньше вопроса, потому что тоже содержат «?», но отвечать
на них в чат бессмысленно. REJECT раньше REDIRECT: отказ со ссылкой на телеграм-канал
вакансий — всё равно отказ.

**`REDIRECT`** («↗ внешний канал») — перевод в telegram/whatsapp: `t.me/`, `@handle`
(с lookbehind, чтобы не ловить e-mail), «для связи напишите…». Отвечать в чат бессмысленно
by design — реакция человека «пойти по ссылке», поэтому `needs_reply` истинно, а автоответ
запрещён категорией. До введения (20.07) 11 из 19 «молчащих вопросов» оказались такими
редиректами, засорявшими QUESTION повелительным наклонением.

`QUESTION` детектится по наличию «?» **или** по `_IMPERATIVE_ASK` (укажите / расскажите /
напишите / уточните / опишите / сообщите / поделитесь). Боты часто спрашивают повелительным
наклонением без вопросительного знака — «Укажите зарплатные ожидания».

**Темы «деньги»/«место»** — `chat_class.py::SALARY_Q` / `::PLACE_Q` — **единый источник**
для бейджа «решай сам» и роутинга `chat_answer`. Раньше пары регэкспов дублировались,
и дыры («заработной платы», «готовы работать в г. Шатура») чинились только в одной.

### Кто написал — два независимых сигнала

Одного признака не хватает, проверено на 93 ждущих чатах:

1. **`participantDisplay.isBot`** из API — ловит ботов HH («ИИ-помощник», «Робот-рекрутер»),
   22 чата. **Пропускает** шаблоны, отправленные от имени живого рекрутера.
2. **Повтор текста по корпусу** — `build_template_index(chats)` возвращает множество
   нормализованных текстов, встретившихся больше одного раза, 48 чатов. **Пропускает**
   шаблон, отправленный впервые (опознаётся задним числом, когда придёт второй такой же).

Итог: `sender = "bot" if is_bot else "template" if is_template else "human"`.

Явный принцип: **ошибаться безопаснее в сторону «личное»**. Принять живого человека за бота
хуже, чем наоборот.

`norm_text` (`chat_class.py::norm_text`) перед сравнением удаляет **переменные части
шаблона**: ссылки, названия вакансий в кавычках, обращение по имени — затем схлопывает
пробелы и берёт первые 100 символов в нижнем регистре.

Без чистки подстановок один шаблон рассыпался на десятки «уникальных» текстов. Живой
случай — ГигаРекрутер Сбера: «…интервью с ГигаРекрутером на вакансию **"Data Scientist /
MLE"** в Telegram https://…» давал 39 ключей на 50 сообщений, рассылка опознавалась
в 17/50, и письма размечались как личные (`isBot` у них тоже false — шлются от имени
вакансии). После чистки: 6 ключей, 50/50, ложных срабатываний 0 (замер 20.07 по корпусу:
шаблонных сообщений 358 -> 391 из 645).

### `analyze` (`chat_class.py::analyze`)

Возвращает `kind`, `label`, `needs_reply`, `manual_only`, `sender`, `can_write`, `preview`, `ts`.

- Пустой список -> `kind=none`
- Последнее сообщение наше -> `kind=none`: последнее слово за нами, ждать нечего
- `manual_only` (`is_manual_only`) — деньги или переезд: переговоры, решение за человеком
- `can_write = (not wp) or wp.startswith("ENABLED")` из `writePossibility`

`can_write` важен: часть чатов закрыта на запись (нет приглашения либо работодатель запретил).
Это выясняется **заранее из API**, а не по факту `409 CHAT_DOES_NOT_EXIST` при отправке.

## Автоответы — движок

`chat_answer.py` — шаблонный движок ответов. Подключён: работает без LLM, на выверенных
пользователем фактах из `resume_profile.json`. Отправку оркестрирует `chat_reply.py`
(см. ниже).

### Принцип

Движок **ничего не выдумывает**. Отвечает только тем, что явно записано в
`resume_profile.json` -> блок `answers`. Нет факта — нет ответа (`None`), вопрос уходит
человеку.

Приписать опыт, которого нет, хуже, чем промолчать: это репутация кандидата перед
работодателем.

### Два языка

Язык определяется по вопросу (`detect_lang`: кириллица -> ru, иначе en) и держится
сквозным: паттерны двуязычные, формулировки ответов — в `_PHRASES[lang]`, факты берутся
с суффиксом `_en` для английского. **Нет перевода факта — молчим**, а не отвечаем
по-русски на английский вопрос: тот же принцип «нет факта — нет ответа», применённый
к языку. Поэтому `education_text_en` можно не заполнять — такие вопросы уйдут человеку.

### Порядок веток `suggest(question, profile, ctx)`

1. Пустой вопрос -> `None`
2. `_NEVER` (торг: «готовы снизить», «ваш минимум») -> **`None` безусловно**
3. `_SALARY_Q` -> вилка по грейду вакансии (см. ниже)
4. `_PLACE_Q` -> формат по городу (см. ниже)
5. `_CONFIRM` -> «Да, всё верно.»
6. `_YEARS` -> `years_python_text`, если в вопросе есть Python-контекст, иначе `years_text`
7. Простые справки: английский / образование / гражданство
8. `_FORMAT` -> `format_text`
9. `_WHICH_STACK` -> перечисление стека
10. `_HAS_EXP` -> см. ниже
11. Ничего не совпало -> `None`

Пункт 6 существует потому, что общий стаж 5 лет 9 месяцев набран на .NET и 1С. Отвечать им
на «сколько лет на Python» нельзя — это ввело бы работодателя в заблуждение.

### Зарплата — вилка по грейду вакансии

`ctx: VacancyContext(name, experience, city)` — контекст вакансии, из которой пришёл
вопрос. `ctx.grade` -> VO `Grade` (JUNIOR / MIDDLE / SENIOR): тайтл приоритетнее
(«Senior …» при опыте 1–3 — всё равно senior), иначе поле `experience`, заполненное
у всех вакансий (в тайтлах грейда нет в 74 %). Маппинг: noExperience и 1–3 года ->
JUNIOR, 3–6 -> MIDDLE, 6+ -> SENIOR; «1–3 = junior» — решение владельца профиля (20.07).

Вилки лежат в `resume_profile.json::salary_by_grade` ({junior|middle|senior: строка}).
Молчим, если: нет `ctx`, грейд не определился, вилка для грейда не задана. Средней вилки
наугад нет намеренно. Торг вокруг названной суммы (`_NEVER`) — всегда человеку.

**Контракт** (реальный вызов):

```python
>>> suggest("Какой у вас ожидаемый уровень заработной платы?",
...         ctx=VacancyContext(name="Стажёр-разработчик", experience="noExperience"))
{"text": "Ожидаемый уровень — 90 000 — 100 000.", "rule": "salary_junior", "lang": "ru"}
>>> suggest("Укажите зарплатные ожидания",
...         ctx=VacancyContext(name="Разработчик", experience=""))   # грейд неизвестен
None
```

### Место работы

`_PLACE_Q` («готовы работать в г. X», «переезд», «relocate») -> ответ по
`office_city` из профиля: вакансия в этом городе -> «удалённо или офис в X»,
иначе -> «работаю удалённо, офис только в X». Город не задан -> человеку.

Это **единственное место, где бот называет фактический город** (Тольятти) — осознанное
решение 20.07: на прямой вопрос честный ответ важнее ATS-легенды с Москвой в резюме.

Регрессии из живых чатов 20.07: «ожидаемый уровень **заработной платы**» не покрывался
паттерном «зарплат», «готовы **работать в г.** Шатура» — паттерном «переезд»; оба
проходили мимо блокировки. Закрыто тестами на этих формулировках.

### `_residual` — защита от подтверждения не того

Ключевая функция (`chat_answer.py::_residual`). Из вопроса удаляются названные технологии,
шаблонная обвязка (`_BOILERPLATE`) и пунктуация. Остаются слова длиннее 2 символов.

**Непустой остаток = спрашивают про конкретную практику, а не про владение технологией.**

- «Есть ли опыт работы с Docker?» -> остаток пуст -> «Да, есть опыт: Docker»
- «Был ли опыт автоматизации тестирования ML-сервисов на Python?» -> остаток
  «автоматизации тестирования мл-сервисов» -> `None`

Второй случай — реальный баг от 20.07: движок отвечал «Да, есть опыт: Python», подтверждая
не то, о чём спросили.

### Прошлый стек

Технологии из `stack_past` (.NET, C#, 1С) отвечаются честной оговоркой: «Да, работал ранее
с C#, сейчас основной стек — Python, FastAPI, REST API», а не наравне с текущим.

### Отрицательные ответы

«Нет, с этим не работал» выдаётся **только** при `answers.answer_negative: true`.
Иначе движок молчит и вопрос уходит человеку.

### Про город — граница двух решений

В обычных ответах (формат, стаж, стек) город **не упоминается**: в резюме на HH указана
Москва (осознанно, ради ATS-ранжирования), и бот не должен ей противоречить мимоходом.

Исключение одно — **прямой вопрос про место работы** (`_PLACE_Q`): там честный ответ
«удалённо; офис только в Тольятти» важнее легенды (решение 20.07, см. выше). Оба решения
зафиксированы в `_comment`-полях `resume_profile.json`.

## Отправка автоответов — `chat_reply.py`

Связка триажа (`chat_class`), движка (`chat_answer`) и транспорта (`chat.send_message`).
CLI: `python hh.py chat`.

### Контракт безопасности — отправка по флагу

По умолчанию **dry-run**: только печатает предложения. Реальная отправка требует явного
`--send`. Гарантии заложены в `propose`, а не в инструкцию:

- отвечаем **только** `sender` `bot`/`template` — живому человеку пишет человек
- только `kind=QUESTION` — скрининг и редирект уводят на внешние формы
- нет факта в профиле -> `suggest` вернул `None` -> пропуск
- дедуп по **вопросу** (`vid|норм-текст`, журнал `chat_replies.jsonl`): тот же вопрос
  дважды — пропуск, новый вопрос в том же чате — отвечаем (бот-интервьюер ведёт цепочку)

### Деньги и место — `manual`

Вопросы про вилку и город (`manual_only`) в обычный `--send` **не попадают**: переговоры,
цена ошибки необратима. `chat_answer` их текст готовит, но отправляются они только по
`--include-manual` и **каждый с подтверждением** `[y/N]` в терминале.

`_console_consent` требует tty: без интерактивного ввода (крон, пайп, фон) manual-ответ
**пропускается**. `select_targets` — чистая функция отбора (согласие инъектируется),
поэтому логика «что реально уйдёт» тестируется без ввода.

### LLM-классификатор намерения — `chat_intent`

Опциональный слой (opt-in, `INTENT_LLM=1` + флаг `--intent`). Различает намерение вопроса
там, где regex принципиально хрупок: `years` («сколько лет вообще») vs `years_tech` («сколько
лет с конкретной технологией») vs `depth` («какой опыт»). За сессию этот класс латали трижды,
последний костыль — «латинское слово в русском вопросе = технология, молчим».

**Граница: LLM понимает, код отвечает.** Модель (`chat_intent.classify_intent` через
`infrastructure/llm/openrouter`) возвращает только МЕТКУ намерения — `{intent, tech}`. Ответ
по-прежнему собирает `suggest` из `resume_profile.json`. LLM не генерирует текст и не видит
фактов профиля (в промпт уходит только вопрос). Соврать нечем.

**Роутинг только проблемного кластера** `_INTENT_CLUSTER = {has_exp, years, years_tech, depth}`
(`chat_answer.py::_route_cluster`). Прочие метки (salary/place/confirm/справки) -> regex-путь
без изменений: там regex надёжен, трогать = риск без выигрыша.

**Инвариант:** intent НИКОГДА не расширяет отвечаемое. Нет выделенного факта -> `None`
(человек). `years_tech` по `tech`: фронт -> фронт-факт, python -> python-стаж, иначе молчим.
Плюс **backstop-гвард** в `_answer_years`: даже неверная метка `years` на вопросе про чужую
технологию гасится вторым рубежом (defense-in-depth).

**Fallback-safe** (по образцу `cover.py::llm_cover`): выключено / нет ключа / таймаут / битый
JSON / метка вне набора -> `None` -> regex-путь. Система не зависит от внешнего сервиса.

**Провайдер:** DeepSeek V4 Flash через OpenRouter (доступ из РФ, модель = строка в env,
~центы/месяц). Смоук: React-вопрос -> `years_tech`, ~120 in / ~15 out токенов. Живой тест —
`INTENT_LIVE=1 pytest -k live`. Проверка маршрутизации без отправки — `python hh.py chat
--intent` (dry-run). В `cron_chat.bat` флаг НЕ добавлен — сначала ручной прогон.

### LLM-переформулировка ответа — `chat_rephrase` (human-gated)

Опциональный слой (opt-in, `REPHRASE_LLM=1` + флаг `--rephrase`, etap 2). LLM переформулирует
**уже одобренный** факт под вопрос — читается как прямой ответ, не канцелярский шаблон. Факт
выбирает КОД (etap-1/regex); LLM меняет только формулировку.

**Гарантия — контуром, не промптом.** Два рубежа:
1. `_grounded` (`chat_rephrase.py`) — валидатор: значимые токены кандидата ⊆ токены источника ∪
   служебные слова. Режет новые числа/технологии/латиницу/новую кириллицу (C3), вставку/потерю
   отрицания (C4, строгое равенство), смену языка (C2), длину (C1), эхо вопроса (C5). **C3
   послаблен**: русская МОРФОЛОГИЯ слова источника (работал→работаю, опыт→опыта) проходит по
   общему корню (префикс ≥4 и ≥70% длины); цифры/латиница/технологии/числительные — строго
   (там новый токен = факт). Остаточный риск кор-коллизий страхует человек-гейт.
2. **Человек** (`chat_reply.py::_apply_rephrase` + `_rephrase_consent`) — валидатор ЛЕКСИЧЕСКИЙ и
   order-blind: перестановку клауз («X не делал, только Y» -> «Y не делал, только X») он НЕ ловит.
   Поэтому любая ИЗМЕНЁННАЯ формулировка идёт под `[y/N]`; **без tty (крон) -> источник дословно**.
   Крон байт-в-байт как сегодня.

**Whitelist** `chat_rephrase.eligible` — строго default-DENY: практики/стаж/фронт/справки; НЕ
трогает `salary_*`/`place_*`/`confirm`/`has_exp_no` (числа/место/подтверждение/полярность).
Неизвестное будущее правило -> не eligible (fail-closed).

**Fallback-safe:** выключено / нет ключа / таймаут / провал валидации / markdown в выводе ->
источник дословно. Сравнение — `python hh.py chat --rephrase` (dry-run, без `--send`). В
`cron_chat.bat` флаг НЕ добавлен. RU-yield низкий (строгий superset режет морфологию) — начинать
с EN-набора, мерить accept-rate. Развилка масштаба и ревью — RFC-002.

### Anti-loop — один чат раз за прогон

Бот-интервьюер может **переспрашивать**, чуть меняя формулировку («сколько лет с React» ->
«А сколько именно с React» -> …), и дедуп по вопросу этого не ловит. Без защиты `--loop`
долбил бы один чат впустую (БАГ 21.07: 5 отправок общего стажа на вопрос про React-стаж).

Защита в `run`: `answered_vids` — чат, отвеченный в **этом** прогоне, в следующих раундах
пропускается. Реальное продолжение диалога подхватит следующий прогон `hh_chat` (через
90 мин), когда бот действительно задаст новый вопрос, а не переспросит старый.

Смежный фикс в движке: `_YEARS` молчит на «сколько лет с <конкретной технологией>», если
это не Python/backend — отдельного стажа по ней нет, а общий стаж (на другом стеке)
не по теме. Именно он кормил цикл.

### Точечный follow-up — `poll_replies`

После отправки опрашивает **только отвеченные** чаты (не полный синк 600): раз в минуту
до 5 минут; пришёл ответ бота — снимает чат с опроса и сохраняет переписку (merge).
Это дёшево (`O(отправленных)`) и подтягивает следующий вопрос цепочки сразу — полный
`--sync-status` на 600 чатов занимал ~12 минут.

`sleep`/`clock` инъектируются -> тестируется без реального ожидания.

Read-only сводка **вопрос -> наш ответ -> реакция бота** (следующее сообщение). Реакция —
сигнал качества шаблона: `➡ дальше` (принял), `🔁 переспросил`, `❌ отказ`, `ждём ответа`.

## Отображение в ленте

`/api/chats` отдаёт свёртку по всем чатам (кроме `kind=none`). В ленте — бейджи по автору:
👤 человек (красный), 📋 шаблонная рассылка (синий), 🤖 бот (серый), `🔒` при
`can_write=false`, «· решай сам» при `manual_only`. В бейдже — давность последнего
сообщения работодателя («сегодня»/«вчера»/«N дн», `model.js::chatAgeLabel` из `ts`
свёртки): видно, насколько давно пришёл ответ и не протух ли диалог.

Фильтр: «Личные» / «Все ждут ответа» / «💰 Решай сам». «Личные» = живой человек
(`sender=human`), чат открыт для записи и **не фриз-заглушка** (`kind != ack` — «резюме
получено, свяжемся» пишет человек, но диалога там нет; фризы остаются в «ждут ответа»).

Контакты из переписки: `chat_class.find_contacts` ищет телефон/telegram в сообщениях
работодателя по ВСЕЙ переписке (email намеренно не ловится; `*bot`-ники и канальные
`t.me/…` из отказов — шум, отфильтрованы) -> поле `contact` в `/api/chats` -> оранжевый
бейдж «📞 <контакт>» на карточке (тултип — все найденные, до трёх) + чат-фильтр
«📞 С контактами» (показывает и после нашего ответа: контакт не протухает).

Практический результат: 600 чатов -> 94 ждущих ответа -> 23 личных и доступных для записи.
Это и есть реальный список дел.

## Воронка автоотказов — `funnel.py`

`application/funnel.py::compute_funnel` строит аналитику поверх того же CRM-состояния (только
чтение): `applied_log` (время отклика + работодатель) + `chat_messages` (время отказа через
`chat_class.classify == REJECT`) + `response_status` (исход) + репозиторий вакансий.

**Зачем.** Гипотеза «автобан»: чем быстрее пришёл отказ после отклика, тем вероятнее, что
резюме никто не читал — отбил ATS-фильтр. Латентность отказа = `reject_ts - apply_ts`
раскладывается по бакетам **<=10 мин / <=1 ч / <=1 дня / >1 дня**, агрегируется по компаниям
(автобан-доля `auto_reject_rate`, медиана латентности) и в общую воронку.

**Семантика (после ревью fix.md):**
- Исход вакансии — **только по статусу HH** (`chat.py::DISCARD_STATES` / `INVITED_STATES`),
  этажи взаимоисключающие: `applied = rejected + invited + no_outcome`.
- Reject-фраза в чате даёт лишь **время** отказа. Без подтверждающего статуса она отказом
  не считается — у `classify` известные ложные срабатывания на проходное «к сожалению»;
  такие чаты видны счётчиком `chat_reject_only` (замер 23.07: 22 из 1305 — ровно тот шум,
  который раньше завышал отказы до 579 при 556 реальных DISCARD).
- Дубли id в append-only журнале схлопываются в **ранний** `ts` (реальный момент отклика,
  как в `marks.js::applyJournal`).
- `auto_reject_rate` = `le_1h / measured` (не от всех отказов); в ранжировании компании
  с < 3 измеренных отказов идут после компаний с достаточной выборкой — 1/1=100 % больше
  не возглавляет топ. Порядок строк CSV = порядок баров графика (единое ранжирование).

**Оговорки в данных:**
- Наивные легаси-метки `applied_log` трактуются как **локальная зона машины**
  (`datetime.now().astimezone()`, у нас самарская UTC+4) — хардкод МСК сдвигал латентность
  на час. Отрицательная латентность (перекос меток) отбрасывается.
- Работодатель: из текущей выдачи, иначе из поля `employer` журнала (пишется в момент
  отклика — новые записи не теряют компанию); старые записи без поля -> `(вне выдачи)`.
  Общая воронка их учитывает, per-company график — нет (не actionable).
- `measured` = отказы с чат-сообщением и вычислимой латентностью. `Отказов - measured`
  — молчаливые `DISCARD` без письма (латентность неизвестна, сегмент «без метки»).

**Живые цифры — не здесь**: актуальный срез всегда во вкладке дашборда и в
`data/reports/13_company_funnel.csv`, они пересчитываются каждой сборкой. Ниже —
исторический замер, зафиксированный только чтобы обосновать вывод.

Замер 23.07.2026 (1305 откликов): отказов 556, из них <=10 мин — 6, <=1 ч — 24
(~5 % от 444 измеренных), медиана латентности ~744 мин (~12 ч). Вывод по этому резюме:
отказы в основном человеко-темповые, мгновенный ATS-автобан **редок** — сама проверка
гипотезы и есть ценность. Если свежий срез начнёт противоречить выводу — переписать
вывод, а не цифры.

**Куда попадает.** `write_funnel_csv` пишет `data/reports/13_company_funnel.csv`; вызывается из
`build_dashboard` **после** `run_reports` (CRM-данные, не рыночные `Vacancy`, поэтому отдельно
от реестра `_REPORTS` и строго после его `cleanup()`). Вкладка дашборда «Автоотказы / воронка»
(`charts.py::chart_company_funnel`) — горизонтальный стек по бакетам латентности, порядок
компаний — как в CSV. Нет CRM-данных -> CSV не пишется -> вкладки нет.

## Ошибки

Все вызовы `chat.*` обёрнуты в `contextlib.suppress(Exception)` и возвращают пустое значение:
`set()`, `(None, None)`, `{}`, `False`, `[]`.

Следствие: **протухшая сессия неотличима от пустого результата**. Принято осознанно —
куки обновит следующий браузерный прогон. Диагностика только через лог «чаты не получены,
сессия от <дата> могла протухнуть».

`409 CHAT_DOES_NOT_EXIST` предотвращается заранее через `can_write`. Если всё же придёт —
`send_message` вернёт `False` молча, без ретрая и без различения кода.

`deep_get` (`chat.py::deep_get`) — рекурсия без защиты от глубины и циклов. На JSON от API
безопасно; на самоссылающейся структуре зациклилась бы.
