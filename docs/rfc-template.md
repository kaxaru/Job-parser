# RFC-<NNN>: <Название>

> Формат для **крупных или необратимых** изменений: смена источника данных, новый внешний
> сервис (LLM/платный API), изменение схемы хранения, всё что трогает боевой путь откликов.
> Для обычной фичи хватает `spec-template.md` — RFC тяжелее и нужен там, где цена ошибки высока.
>
> Ключевое отличие RFC от спеки: разделы **Alternatives**, **Migration** и **Rollback**.
> Спека отвечает «как реализуем», RFC — ещё и «почему именно так» и «как отменим».

## Motivation

Зачем это нужно. Что болит СЕЙЧАС, с цифрами из системы.

Не «хочется автоответы» -> «94 чата ждут ответа, 22 из них — боты с шаблонными вопросами;
ручная обработка съедает ~40 мин/день».

## Problem

Какую проблему решаем — узко и проверяемо. Одно предложение.
Если проблем несколько — это несколько RFC.

## Goals

Что считаем успехом. Каждая цель измерима и **пронумерована**: `R#` — якорь, по которому цель
связывается с тестом в разделе «Верификация» и переживает ревизию документа.

Без якорей покрытие не считается, и «выглядит полно» подменяет «12 целей, 12 закрыты».
Живой пример: инвариант RFC-003 «шлём ТОЛЬКО при полноте» был записан прозой и не привязан
ни к одному тесту — полнота ЗАПОЛНЕНИЯ выпала молча и всплыла только через шесть дней
(`forms.py::try_autofill`, отклик уходил с невписавшимися полями).

- **R1.** <цель> — измеряется <метрикой>

## Non-Goals

Что НЕ делаем в этом RFC, хотя оно рядом и напрашивается.

Раздел не формальность: он останавливает расползание объёма и защищает решение от
«починки» следующим аудитом.

- <что> — почему вне объёма, куда вынесено

## Solution

Архитектура: слои, модули, контракты, потоки данных.

Требования те же, что в спеке: доменные понятия — Value Object'ами, не примитивами;
для каждого модуля назван слой (`domain` / `application` / `infrastructure` / `presentation`).

Схема потока данных, если задействовано >2 модулей:

```
<источник> -> <ACL> -> <хранилище> -> <потребитель>
```

## Alternatives

Что ещё рассматривали и почему отвергли. Минимум два варианта, иначе выбор не был выбором.

- **<Вариант B>** — <в чём лучше> / <почему отвергли>
- **<Вариант C>** — <в чём лучше> / <почему отвергли>

Здесь же — вариант «ничего не делать»: чем плох статус-кво.

## Политика восстановления

Задаётся для КАЖДОЙ операции, способной прерваться на середине. Не задана здесь — будет
изобретена в коде: обработка ошибки появится в точке вызова, синтаксически корректная и
ничего не решающая на уровне системы.

```
операция:              <что>
единица «сделано»:     <что считается выполненным целиком>
частичное выполнение:  <обработано 3 из 10 — успех, отказ или частичный результат?>
                       <кто и как узнаёт, что результат неполный>
                       <повтор безопасен? идемпотентность>
сбой:                  <распространяется вверх | деградируем и продолжаем>
инвариант после сбоя:  <что обязано остаться верным>
```

Почему отдельным разделом, а не пунктом в рисках: требования к восстановлению **архитектурны**.
Обнаруженные на этапе тестов, они чинятся не добавлением ещё одной проверки, а переделкой
куска. За 28.07 этот класс дал три отказа подряд: watchdog снёс прогон посередине, дренаж форм
упал на 34-й позиции из 52, а `apply_quota` считала 35 отправок при реальных ~103, потому что
`forms.run` не инкрементил счётчик — суточный потолок молча перестал защищать.

## Risks

Формат: **ситуация -> что сломается -> что делаем**.

Обязательно покрыть: недоступность внешнего сервиса, **операция прервалась на середине**
(см. политику восстановления выше), пустой/нулевой вход, параллельный запуск, деньги (если
внешний API платный), приватность данных (что уходит наружу), судьба уже накопленных данных
на диске.

- **<риск>**: <последствие> -> <фолбэк>

## Наблюдаемость

По какому логу, счётчику или метрике видно, что оно сломалось **в эксплуатации**, а не на
прогоне верификации.

```
признак поломки:  <что именно смотреть: строка лога, файл, счётчик>
как часто видно:  <при каждом прогоне | раз в сутки | только по запросу>
```

Раздел появился после того, как расхождение квоты (35 в счётчике против ~103 фактических)
всплыло случайно — от вопроса «а отклики были?», а не от сигнала системы. Признак поломки,
который никто не смотрит, не является наблюдаемостью.

## Migration

Как переходим с работающей системы на новую.

- нужна ли пере-сборка данных (`hh.py collect --force`)? сколько времени займёт?
- совместимы ли старые файлы в `data/`? нужен ли конвертер?
- есть ли промежуточное состояние, где работают обе схемы?
- порядок шагов: что деплоим первым, чтобы не было окна поломки

## Rollback

Как откатываем, если в проде плохо. Должен быть выполним за минуты, без раздумий.

- какие файлы/задачи вернуть в прежнее состояние
- есть ли бэкап данных до миграции, где лежит
- флаг для мгновенного отключения фичи (переменная окружения / константа), если он есть
- что делать с данными, накопленными новой схемой

## Верификация

Каждая цель `R#` из «Goals» связана с проверкой. Строка «непокрытые цели» обязательна:
пустой список — тоже результат, а её отсутствие означает, что покрытие не считали.

```
R1 -> <команда> -> <ожидаемый вывод> · <tests/<файл>::<тест>>
R2 -> <команда> -> <ожидаемый вывод> · <tests/<файл>::<тест>>
непокрытые цели: <перечислить или «нет»>
```

Тесты называются С УКАЗАНИЕМ СВОЙСТВА, которое каждый защищает, — такая формулировка
переживает рефакторинг (`test_specific_practice_over_known_tech_is_silent`, а не `test_suggest`).
Правила самих тестов — литерал до запуска, точное значение вместо флага, никаких деталей
реализации — живут в [`testing.md`](testing.md#главное-правило) и здесь не дублируются.

Регресс: `pytest` + `node --test` + `ruff`/`biome`.
