# Архитектура

## Что это за система

Демо-DWH уровня Data / Analytics Engineer на реальных данных: 109 597 вакансий с девяти
порталов, собранных родительским проектом (`../data/vacancies_raw.json`; перечень порталов
ведёт `hrwork/config.py::SOURCES`). Число — замер кеша на 09.08.2026, он растёт с каждым
сбором; фактический объём прогона печатает строка `prepare:` (см. [`etl.md`](etl.md)).

Один и тот же extract + transform питает **три хранилища** — PostgreSQL, ClickHouse,
MS SQL. Все три показаны в одном BI (Metabase), оркестрация — Airflow, наблюдаемость —
Grafana + Loki.

Смысл проекта — не сами цифры по рынку труда, а демонстрация того, что смена движка
хранилища не требует переписывания конвейера.

## Ports & Adapters

Центральное решение. Главный порт — `warehouse/base.py::Warehouse`, `Protocol` из трёх
методов (второй, для курсов валют, описан ниже):

```python
name: str
init_schema() -> None          # создать/обновить схему, идемпотентно
load(vacancies) -> int         # загрузить, вернуть число строк В ФАКТЕ (прочитанное из БД)
count() -> int                 # верификация + база санити-гейта перезалива
```

Оба числа возвращаются **из хранилища**, а не из длины входа: на них держится
`Pipeline._verify`, и адаптер, отвечающий `len(vacancies)`, делает главную проверку проекта
вакуумной — она совпадёт, что бы ни случилось в базе (так и было в ClickHouse до 09.08.2026).

`Pipeline` принимает список хранилищ как зависимость и не знает, куда грузит. Добавление
целого движка — это один адаптер плюс строка в реестре `pipeline.py::REGISTRY`:

```python
REGISTRY = {
    "postgres":   lambda cfg: PostgresWarehouse(cfg.pg_dsn, SQL_DIR / "postgres" / "schema.sql"),
    "clickhouse": lambda cfg: ClickHouseWarehouse(cfg.ch_url, SQL_DIR / "clickhouse" / "schema.sql"),
    "mssql":      lambda cfg: MSSQLWarehouse(cfg.mssql_dsn, SQL_DIR / "mssql" / "schema.sql"),
}
TARGETS = tuple(REGISTRY)
```

Проверяется тем, что MS SQL добавлялся последним и потребовал ровно этого. Airflow-DAG
тоже строит таски из `TARGETS` — новый бэкенд появляется в графе сам.

### Второй порт: курсы валют

09.08.2026 у стенда появилась вторая внешняя зависимость, и обошлась она в один новый
адаптер — `etl/rates.py`. Витринам понадобилась зарплата в одной шкале: в срезе девять
порталов и десятки валют, а «среднее по вилке» из рублей, долларов и сумов — не число,
а мусор. Пересчёт в рубли требует курса, то есть внешнего мира.

**Внешний мир заперт за портом, и порт этот — файл.** Курсы в стенд приходят из суточного
кеша, который ведёт родитель (`data/fx_rates.json`,
`hrwork/infrastructure/net/rates.py::get_rates`); сам стенд в сеть не ходит вовсе. Причина
не в экономии запросов, а в воспроизводимости: прогон витрин не должен зависеть от
доступности чужого API, и два запуска на одном входе обязаны дать одинаковые цифры — иначе
сравнение трёх движков, ради которого стенд и сделан, перестаёт что-либо значить. Курсы
читаются **один раз на прогон** по той же причине: обновись кеш посреди загрузки, разные
вакансии получили бы разные курсы, и три хранилища разошлись бы на одном входе.

Форма порта здесь другая, чем у хранилищ, — не `Protocol`, а тип аргумента:
`Vacancy.from_raw(rec, fx: dict[str, float])`. Домен получает готовые курсы per-USD и не
знает, откуда они взялись; `Pipeline.prepare` достаёт их адаптером (`rates.load_rates`)
и передаёт явно. Путь к файлу инжектируется в `Pipeline(..., fx_file=)`, а не читается
из окружения внутри домена: иначе тест не смог бы подсунуть свой кеш, не трогая переменные
процесса. Заменить файл на HTTP-клиент или на таблицу в БД — это новая реализация того же
порта; `domain.py` и `pipeline.py` при этом не меняются.

Деградация — как положено на чужих данных: нет файла, битый JSON, нет нужной валюты ->
`salary_*_rub` пустые, предупреждение `[etl] FX: ...`, **прогон продолжается**. Вакансия
выпадает из зарплатного среза, но не приезжает в него нулём — ровно этот дефект родитель
чинил у себя 08.08.2026, когда допущение «по умолчанию рубли» превращало вилку $10 000
в 10 000 ₽ и прятало её любым фильтром.

## Поток данных

Входов ДВА — данные и курсы валют, каждый за своим адаптером:

```
../data/vacancies_raw.json          ../data/fx_rates.json
   (сбор родительского проекта)        (суточный кеш курсов родителя)
        │                                   │
        ▼                                   ▼
   JsonSource.read()   extract         rates.load_rates()   один раз на прогон
        │                                   │
        └─────────────────┬─────────────────┘
                          ▼
   Vacancy.from_raw(rec, fx=…)        transform — ОДИН раз, в Python
   зарплаты + их рублёвый             дедуп по id, счётчики отбраковки
   эквивалент, опыт/график,           (Pipeline.prepare)
   стек из кеша родителя `_techs`,
   is_remote = remote|flexible,
   remote_mentioned (текст) — отдельно
        │
        ├──────────────┬──────────────────┬─────────────────┐
        ▼              ▼                  ▼                 │
   PostgreSQL      ClickHouse         MS SQL                │  load (fan-out)
   staging         широкий факт       staging               │
     → core          + Aggregating      → core (T-SQL)      │
       (звезда)        MergeTree MV       (звезда)          │
     → mart                             → mart (views)      │
       (matview,     витрины на           MERGE/IDENTITY    │
        REFRESH)      вставке                               │
        │              │                  │                 │
        └──────────────┴──────────────────┴─────────────────┘
                       ▼
                   Metabase  (дашборды /2 /3 /4 /5 + sources)
                       +
              Power BI (опционально, поверх MS SQL, вне Docker)
```

**Transform делается один раз** и кэшируется в `Pipeline.prepare()`. Это принципиально:
если бы каждый адаптер парсил сам, три хранилища могли бы разойтись в данных при одинаковом
входе, а сравнение движков потеряло бы смысл. Что три хранилища действительно сошлись,
проверяет не глаз по трём строкам stdout, а `Pipeline._verify`: он сверяет число строк
в факте каждого движка с результатом `prepare` и роняет прогон, называя отставший.

**Под Airflow вход другой.** Пути в схеме — локальные, для запуска с хоста. В контейнерах
оба файла лежат в `/opt/airflow/data`, за которым смонтирован **`../data/export`**, а не
`../data`: рядом с выгрузкой живут куки сессии, профиль браузера и контакты рекрутёров,
а Airflow исполняет произвольный Python. Каталог `export` наполняет хост (шаг 3a в
`cron/cron_collect.bat`), контейнер получает его только на чтение. Переменные —
`DATA_FILE`/`FX_FILE`, см. [`config.md`](config.md) и [`deployment.md`](deployment.md).

## Слои хранилища

Классическая трёхслойка, одинаковая по смыслу во всех движках:

**staging** — типизированный приём. Сырого JSONB-слоя нет намеренно: transform уже сделан
в Python, в staging прилетают готовые колонки.

**core** — звезда: факт `vacancies` плюс измерения `cities`, `employers`, `skills` и мост
`vacancy_skills` (связь многие-ко-многим по навыкам).

**mart** — витрины: `city_stats`, `skill_demand`, `salary_by_experience`, `top_employers`,
`source_stats` (объём/зарплата/remote в разрезе портала-источника).

Исключение — ClickHouse: там вместо звезды **широкий факт** с массивом `skills`, а витрин
не пять, а три — `city_stats` и `top_employers` в нём нет намеренно, и расхождение
зафиксировано комментарием в самой схеме, чтобы читатель не искал пропажу. Это не
непоследовательность, а демонстрация разницы парадигм; таблица «витрина x движок»
и подробности — в [`warehouses.md`](warehouses.md).

## Чем витрины отличаются между движками

Один и тот же результат достигается тремя способами — в этом половина ценности проекта:

- **PostgreSQL** — материализованные представления, обновляются явным `REFRESH MATERIALIZED
  VIEW` на шаге load
- **ClickHouse** — `AggregatingMergeTree` плюс инкрементальные MV, витрины наполняются
  **на каждой вставке**, REFRESH не нужен вовсе
- **MS SQL** — обычные views (всегда live) плюс `MERGE` для upsert измерений

## Слои кода

```
etl/
  domain.py       Vacancy + from_raw, справочники, разметка стека — БЕЗ БД
  rates.py        адаптер курсов валют — читает суточный кеш родителя, без сети
  source.py       JsonSource — extract
  pipeline.py     Pipeline + REGISTRY + build_pipeline — оркестрация, санити-гейты, verify
  config.py       Settings.from_env — пути к данным и курсам + DSN всех бэкендов
  cli.py          python -m etl
  warehouse/      base.py (порт) + postgres/clickhouse/mssql (адаптеры)
  sql/            schema.sql на каждый движок
bi/               провижининг Metabase из кода
dags/             Airflow DAG
observability/    Grafana + Loki как код
search_demo/      отдельный PoC полнотекстового поиска
```

`domain.py` — чистые функции без БД: переиспользуется всеми адаптерами и тестируется
без контейнеров. Это то же разделение, что и в родительском проекте.

**Оговорка к правилу «домен без I/O».** Ввод-вывод в конвейере ровно один — чтение кеша
курсов, и он спрятан за портом: домен принимает готовый словарь курсов аргументом `fx`,
а с диском разговаривает адаптер `rates.py`. Компромисс в том, что `domain.py` всё-таки
импортирует `rates.load_rates` — как ленивый дефолт для вызова `from_raw(rec)` без курсов.
Сегодня этим дефолтом не пользуется никто: `Pipeline.prepare` передаёт `fx=` явно, тесты
тоже. Это остаток переходного периода, и его следует удалить вместе с параметром
`fx: … | None`, после чего правило «без БД и I/O» снова читается дословно.

## Идемпотентность

Все операции рассчитаны на повторный запуск:

- `init_schema` — `CREATE ... IF NOT EXISTS` во всех движках
- `load` — полный перезалив: staging чистится, `core.vacancies` пересоздаётся,
  измерения добираются через `ON CONFLICT DO NOTHING` (PG) или `MERGE` (MS SQL)
- провижининг BI — повторный запуск архивирует старые карточки и пересобирает, без дублей

Идемпотентность здесь не значит «повтор всегда разрешён». Перезалив полный, поэтому
деградированный вход стирает вчерашние данные безвозвратно — от этого стоят санити-гейты
`Pipeline._reject_degraded` (срез просел больше чем вдвое относительно факта) и
`_check_broken_share` (доля неразобранных записей выше порога). Оба роняют прогон до того,
как первый адаптер тронет свой факт; осознанный обход — `python -m etl load --force`.

**Дедуп на входе** (`Pipeline.prepare`) обязателен: дубль по id уронил бы PRIMARY KEY
в PG и MS SQL, а в ClickHouse (MergeTree, ключ не уникален) молча задвоил бы счётчики
витрин. Причина дублей с 09.08.2026 другая, чем раньше: поля `_query` в сырых данных
больше нет, и «одна вакансия из нескольких поисковых запросов» — снятое обоснование.
Кеш родителя копится многими прогонами по девяти порталам, и одна и та же вакансия
приезжает в него повторно. Дедуп — защита конвейера, а не следствие формы запроса.

## Границы

Входит: extract из JSON, transform, загрузка в три движка, схемы, витрины, провижининг
дашбордов, DAG, observability-стек.

Не входит: сбор вакансий (это родительский проект), аналитика поверх витрин (это Metabase),
Power BI Desktop (Windows-приложение, контейнеризовать нельзя).
