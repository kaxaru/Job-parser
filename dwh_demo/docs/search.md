# PoC полнотекстового поиска

**Модули:** `search_demo/` — `load.py`, `bench.py`, `README.md`, `REPORT.md`

## Назначение

Ответить измерением, а не на веру, на два вопроса родительского проекта: нужен ли
`tsvector` вместо наивного `ILIKE` и нужен ли Elasticsearch.

Это отдельный стенд, к DWH-конвейеру отношения не имеющий: он грузит те же данные
в собственную схему `search_demo.vacancies` и меряет запросы.

## Запуск

Нужен поднятый `hh-postgres` (порт 5433):

```bash
python dwh_demo/search_demo/load.py    # грузит + строит индексы, идемпотентно
python dwh_demo/search_demo/bench.py   # меряет -> REPORT.md (UTF-8)
```

Что строится в `search_demo.vacancies`:

- `tsvector` — заголовок весом A, описание весом B — плюс GIN
- trigram-GIN (`pg_trgm`) по `name` — для опечаток
- btree по `city` и `sal_mid`

`bench.py` перезаписывает `REPORT.md` результатами прогона.

## Результаты последнего прогона

Источник — `REPORT.md`, PostgreSQL 16, ~9.7k строк.

**Основной кейс** «python backend в Москве, зарплата >= 200 000»: оба подхода находят
одни и те же строки.

- `ILIKE` наивный — `EXPLAIN ANALYZE` 25.485 мс, медиана 25 прогонов 24.614 мс
- `tsvector` + GIN — 2.110 мс, медиана 2.682 мс

Примерно **десятикратная** разница. Текст у `ILIKE` фильтруется построчно, индекс берётся
только под `city`; у `tsvector` текст ищется прямо по индексу.

**Точность.** `ILIKE '%java%'` даёт 2256 строк, токен `tsquery 'java'` — 1356.
Разница в 900 строк — ложные срабатывания на `javascript` и `java-script`. Подстрока
ловит мусор, токен — нет.

**Морфология.** `tsquery 'программист'` цепляет программист/-а/-ов/-ы одним термом —
3173 строки. У `LIKE` этого нет в принципе.

**Опечатки.** trigram `word_similarity` с `<%`: `'pyton'` находит «QA Automation (Python)»
и подобные, Bitmap Index Scan, 18.303 мс. Это покрывает fuzzy-кейс, ради которого чаще
всего смотрят на Elasticsearch.

**Фасеты.** `GROUP BY unnest(techs)` — счётчики для UI-фильтров, медиана 28.603 мс.
Топ: 1С 6154, Python 4540, PostgreSQL 3254, Docker 2678, ML/AI 2227.

**Ранжирование.** `ts_rank(doc, q)` сортирует по релевантности с учётом весов A и B —
у `LIKE` ранга не существует.

## Выводы

1. **Для текущего состояния** родительского проекта (фильтр в JS на клиенте) не нужно
   ничего — клиентского фильтра достаточно.
2. **Если поиск переедет на сервер** — PostgreSQL `tsvector`. PG уже в стеке, нужна одна
   колонка и GIN; получаем точность, ранжирование, морфологию и опечатки за единицы
   миллисекунд. Отдельный сервис не требуется.
3. **Elasticsearch не нужен** на этом объёме. Он окупается при сотнях тысяч документов
   и высоком QPS, либо при продвинутых требованиях (typeahead под нагрузкой, синонимы,
   обучаемое ранжирование), либо если ELK уже стоит под логи. Иначе это лишний
   JVM-кластер плюс синхронизация данных из БД с её лагом и рассинхроном.

Порог простыми словами: Postgres FTS спокойно тянет до миллионов строк.

## Связь с родительским проектом

Именно этот вывод реализован в `hr_work`: эндпоинт `/api/search` работает через
`tsvector`, `psycopg2` импортируется лениво, а недоступность БД даёт `503` без падения
ленты. Подробности — `../../docs/api.md` и `../../docs/storage.md`.

## Расхождение в цифрах

`search_demo/README.md` цитирует **более ранний прогон**: 9 751 строка, `ILIKE` ~30 мс
против `tsvector` ~1.1 мс, `java` 1125 против 573.

`REPORT.md` — актуальнее и перезаписывается каждым `bench.py`: 25.485 против 2.110 мс,
`java` 2256 против 1356.

Выводы совпадают, различаются только абсолютные значения — данных стало больше. При
расхождении верить `REPORT.md`: он генерируется, а README писался руками.

## Проверка

```bash
docker compose up -d hh-postgres
python dwh_demo/search_demo/load.py
python dwh_demo/search_demo/bench.py
```

Ожидаемо: `load.py` отрабатывает идемпотентно (повторный запуск не дублирует строки),
`bench.py` перезаписывает `REPORT.md`, где `tsvector` быстрее `ILIKE` на порядок.
