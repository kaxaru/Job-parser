# PoC полнотекстового поиска

**Модули:** `search_demo/` — `load.py`, `bench.py`, `README.md`, `REPORT.md`

## Назначение

Ответить измерением, а не на веру, на два вопроса родительского проекта: нужен ли
`tsvector` вместо наивного `ILIKE` и нужен ли Elasticsearch.

Это отдельный стенд, к DWH-конвейеру отношения не имеющий: он грузит те же данные
в собственную схему `search_demo.vacancies` и меряет запросы.

## Запуск

Нужен поднятый `hh-postgres` (порт 5433):

```bash
python dwh_demo/search_demo/load.py    # грузит + строит индексы, идемпотентно
python dwh_demo/search_demo/bench.py   # меряет -> REPORT.md (UTF-8)
```

Что строится в `search_demo.vacancies` (семь индексов, все создаёт `load.py::main`):

- `ix_doc_gin` — GIN по `tsvector`: заголовок весом A, описание весом B
- `ix_name_trgm` — trigram-GIN (`pg_trgm`) по `name`, для опечаток
- `ix_city`, `ix_salmid` — btree под обычные фильтры
- `ix_source` — btree по колонке `source` (портал): фильтр источника на странице `/search`
  основного проекта идёт ровно по нему (`source = %(source)s`)
- `ix_salmid_page` по `(sal_mid DESC NULLS LAST, id)` — под ORDER BY стартового
  показа `/search`. Отдельно от `ix_salmid`: у ASC-индекса NULL'ы в конце, и обратный
  проход даёт `DESC NULLS FIRST` — планировщик его не возьмёт. Замер 01.08.2026: запрос
  без `q` 138 мс -> 1.3 мс (22 буфера вместо ~50 000)
- `ix_salmidrub_page` по `(sal_mid_rub DESC NULLS LAST, id)` — тот же постраничный индекс,
  но по рублёвой серединке; под сортировку, которая должна прийти на смену текущей

Признак удалёнки здесь называется `is_remote_like` (remote + гибрид — доменное
`Schedule.is_remote_like` родителя), а не `is_remote`. Имя разное, потому что в той же базе
`hh` живёт `core.vacancies.is_remote` DWH-конвейера: до 09.08.2026 он считался по другому
правилу, и две одноимённые колонки в одной базе давали разные ответы на вопрос «это
удалёнка?». Сегодня оба поля считаются одинаково, но имя оставлено говорящим — оно называет
правило, а не надеется на него.

### Зарплата хранится дважды, сравнивать можно только рубли

`sal_from`/`sal_to`/`sal_mid` лежат **как пришли, в валюте портала** — это годится только
для показа в карточке. Фильтровать и сортировать можно ТОЛЬКО по `sal_mid_rub` — рублёвому
эквиваленту серединки вилки по курсам `data/fx_rates.json` (`load.py` берёт их один раз
на прогон, чтобы вся таблица оказалась в одной шкале).

Причина — не аккуратность, а два конкретных дефекта общей шкалы по сырым суммам: на первую
страницу выезжали узбекские вилки в 50 000 000 UZS, а фильтр «з/п от 200 000» выбрасывал
все долларовые. Родитель тот же дефект чинил у себя 08.08.2026 в ползунке ленты
(`feed.py::_salary_slider_max`). Нет курса или нет валюты -> `sal_mid_rub IS NULL`:
вакансия выпадает из сравнения, но остаётся в выдаче — нулём её считать нельзя.

**Компромисс: два постраничных индекса вместо одного.** Потребитель — `search.py::_PLAIN.order`
и `_FTS.order` — сегодня всё ещё сортирует по `sal_mid`, и фильтр зарплаты у него тоже по
`sal_mid`. Убрать `ix_salmid_page` заранее нельзя: сегодняшний прод по нему ходит, и его
пропажа вернула бы Seq Scan (те самые 138 мс против 1.3 мс). Поэтому индексы временно живут
парой — плата за то, чтобы правки загрузчика и потребителя могли приехать в любом порядке.
`ix_salmid_page` удаляется сразу после перевода `_PLAIN.order`/`_FTS.order` на `sal_mid_rub`.

### Индекса по `created_at` нет

Был `ix_created`, убран 09.08.2026. Единственный запрос по дате — фильтр свежести
`search.py::_FRESH_WHERE`, и он считает возраст выражением
`floor(extract(epoch from now() - created_at) / 86400)`. Планировщик не знает, что это
выражение монотонно по `created_at`, и btree по голой колонке под такой предикат не
подставляет; выражение-индекс тоже невозможен — `now()` не IMMUTABLE. То есть индекс не
использовался ни одним запросом ни стенда, ни прод-пути `/api/search`, а заливку удорожал.

Вернуть его имеет смысл ровно при одном условии: предикат свежести на стороне родителя
станет саргабельным — `created_at > now() - interval '31 days'` (тождественно `floor(...) <= 30`)
и аналогично для остальных двух полос. Это правка в `hrwork/infrastructure/search.py`,
не в стенде; готовая строка `CREATE INDEX` лежит закомментированной в `load.py::main`.

`bench.py` перезаписывает `REPORT.md` результатами прогона.

## Результаты последнего прогона

Источник — `REPORT.md`, PostgreSQL 16. Объём выборки в его заголовке до 09.08.2026 был
захардкожен («9.7k») и давно врал — теперь `bench.py` читает его из самой таблицы, поэтому
верить надо той цифре, что стоит в свежесгенерированном отчёте. Для порядка величин:
в кеше родителя 109 597 записей (замер 09.08.2026), и загружаются они целиком.

**Основной кейс** «python backend в Москве, зарплата >= 200 000 ₽».

- `ILIKE` наивный — `EXPLAIN ANALYZE` 25.485 мс, медиана 25 прогонов 24.614 мс, **47 строк**
- `tsvector` + GIN — 2.110 мс, медиана 2.682 мс, **45 строк**

Примерно **десятикратная** разница. Текст у `ILIKE` фильтруется построчно, индекс берётся
только под `city`; у `tsvector` текст ищется прямо по индексу.

**Выдачи при этом НЕ совпадают** — 47 против 45. Это не погрешность: `ILIKE '%python%'`
ловит подстроку где угодно, `websearch_to_tsquery` работает токенами со стеммингом и
стоп-словами, и совпадение множеств не гарантировано в принципе. Разница — подстроковые
ложные срабатывания, о них ниже в «Точности». Раньше здесь стояло «оба подхода находят
одни и те же строки», и это противоречило отчёту, на который абзац же и ссылался: вывод
«tsvector быстрее при равном результате» — неверный, результат другой.

Зарплатный порог кейса с 09.08.2026 сравнивается с рублёвой колонкой (`sal_mid_rub >= 200000`),
а не с `sal_mid`: по валюте портала «>= 200 000» выбрасывало все долларовые вилки и
пропускало 50 000 000 UZS. Числа выше — из последнего записанного прогона, то есть ещё
по старому критерию; следующий `bench.py` их пересчитает.

**Точность.** `ILIKE '%java%'` даёт 2256 строк, токен `tsquery 'java'` — 1356.
Разница в 900 строк — ложные срабатывания на `javascript` и `java-script`. Подстрока
ловит мусор, токен — нет.

**Морфология.** `tsquery 'программист'` цепляет программист/-а/-ов/-ы одним термом —
3173 строки. У `LIKE` этого нет в принципе.

**Опечатки.** trigram `word_similarity` с `<%`: `'pyton'` находит «QA Automation (Python)»
и подобные, Bitmap Index Scan, 18.303 мс. Это покрывает fuzzy-кейс, ради которого чаще
всего смотрят на Elasticsearch.

**Фасеты.** `GROUP BY unnest(techs)` — счётчики для UI-фильтров, медиана 28.603 мс.
Топ: 1С 6154, Python 4540, PostgreSQL 3254, Docker 2678, ML/AI 2227.

**Ранжирование.** `ts_rank(doc, q)` сортирует по релевантности с учётом весов A и B —
у `LIKE` ранга не существует.

## Выводы

1. **Серверный поиск уже включён.** Вывод PoC реализован: `/api/search` работает через
   `tsvector` по этой самой таблице. Клиентский фильтр остался только у ленты.
2. **Раз поиск переехал на сервер** — PostgreSQL `tsvector`. PG уже в стеке, нужна одна
   колонка и GIN; получаем точность, ранжирование, морфологию и опечатки за единицы
   миллисекунд. Отдельный сервис не требуется.
3. **Elasticsearch не нужен** на этом объёме. Он окупается при сотнях тысяч документов
   и высоком QPS, либо при продвинутых требованиях (typeahead под нагрузкой, синонимы,
   обучаемое ранжирование), либо если ELK уже стоит под логи. Иначе это лишний
   JVM-кластер плюс синхронизация данных из БД с её лагом и рассинхроном.

Порог простыми словами: Postgres FTS спокойно тянет до миллионов строк.

## Связь с родительским проектом

Именно этот вывод реализован в `hr_work`: эндпоинт `/api/search` работает через
`tsvector`, `psycopg2` импортируется лениво, а недоступность БД даёт `503` без падения
ленты. Подробности — `../../docs/api.md` и `../../docs/storage.md`.

## Откуда цифры и чему верить

Единственный источник — `REPORT.md`: его перезаписывает каждый прогон `bench.py`, включая
объём выборки в заголовке. `search_demo/README.md` и этот файл пишутся руками и цитируют
последний записанный прогон, поэтому **при расхождении верить `REPORT.md`**.

Раньше три файла спорили друг с другом: README держал ещё более ранний замер (9 751 строка,
`java` 1125 против 573), а заголовок `REPORT.md` уверял про «9.7k» при кеше на порядок
больше. 09.08.2026 README переписан на числа отчёта, объём в заголовке стал считаться
прогоном. Устаревают эти абзацы только вместе — от одного запуска `bench.py`.

## Проверка

```bash
docker compose up -d hh-postgres
python dwh_demo/search_demo/load.py
python dwh_demo/search_demo/bench.py
```

Ожидаемо: `load.py` отрабатывает идемпотентно (повторный запуск не дублирует строки),
`bench.py` перезаписывает `REPORT.md`, где `tsvector` быстрее `ILIKE` на порядок.
