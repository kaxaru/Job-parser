# Тесты и критерии приёмки

## Запуск

```bash
python -m pytest                  # 36 unit; integration отфильтрованы (по умолчанию)
python -m pytest -m integration   # 4 теста на реальных PG + ClickHouse — ОСОЗНАННО
python -m ruff check .            # линтер, свой конфиг
```

> ⚠ `-m integration` **делает TRUNCATE базы `hh`**. Только на тестовой базе или в CI,
> никогда на стенде с данными, которые жалко.

## Маркеры и защита по умолчанию

`pytest.ini`:

```ini
addopts = --strict-markers -ra -m "not integration"
markers =
    unit: быстрые тесты без внешних зависимостей (домен, оркестрация на фейках)
    integration: требуют живых Postgres/ClickHouse (CI service containers)
```

**`-m "not integration"` в `addopts`** — защита от разрушительного прогона по привычке.
Раньше голый `python -m pytest` собирал все 40 тестов и на поднятом стеке стирал
демо-данные; теперь он берёт только 36 безопасных.

Аргумент командной строки перекрывает `addopts`, поэтому явный `-m integration`
по-прежнему работает — запуск деструктивных тестов стал осознанным действием,
а не поведением по умолчанию.

**`--strict-markers`** — опечатка в имени маркера становится ошибкой, а не молчаливым
пропуском теста.

## Что покрыто

**`tests/test_domain.py`** — разбор сырой записи: нормализация кодов опыта и графика,
разметка навыков регэкспами, определение удалёнки по маркерам, `strip_html`.
Чистые функции, контейнеры не нужны.

**`tests/test_pipeline.py`** — оркестрация на фейковых хранилищах: порядок шагов,
дедуп по id, отбраковка битых записей, кэширование `prepare`, трактовка пустого списка
шагов как `all`.

**`tests/test_cli.py`** — разбор аргументов: повторяемый `-t`, валидация шага,
пустой ввод.

**`tests/test_bi_client.py`** — фасад Metabase на замоканном HTTP: идемпотентность
`ensure_database` и `upsert_dashboard`.

**`tests/integration/test_warehouses.py`** — реальные PostgreSQL и ClickHouse: схема
создаётся идемпотентно, загрузка кладёт ожидаемое число строк, `count()` совпадает.

**`tests/fixtures/sample_vacancies.json`** — фикстура сырых записей.

Всего собирается **40 тестов**.

## Пирамида

Основание — юниты на чистых функциях (`domain`) и на фейках (`pipeline`, `cli`).
Интеграция — только там, где есть настоящий внешний контракт: SQL-диалект и поведение
движка. E2E нет: полный прогон требует всех 12 контейнеров и проверяет ровно то же,
что интеграционные тесты.

Адаптер MS SQL интеграционным тестом **не покрыт** — в CI-матрице его нет.
Проверяется вручную: `python -m etl -t mssql all`.

## Про CI

`README.md` проекта утверждает, что в корне репозитория лежит
`.github/workflows/ci.yml` с job `unit` -> job `integration` на сервис-контейнерах.

**Этого файла нет.** Ни в родительском каталоге, ни где-либо ещё; каталог `.github`
существует только в корне `hr_work/` и workflows не содержит. Проверено поиском по файловой
системе.

Более того, репозиторий вообще не под git — `git rev-parse` сообщает
`not a git repository`. То есть CI не просто не настроен, ему негде запускаться.

Утверждение в README следует либо убрать, либо реализовать. Пока оно ложное.

## Критерии приёмки

Задача считается выполненной, когда:

1. `python -m pytest` зелёный, 40 тестов
2. `python -m ruff check .` без замечаний
3. Новое поведение покрыто тестом, имя которого называет **свойство**, а не функцию
4. Для правок в адаптерах — прогон `python -m etl -t <backend> all` с совпадающим
   числом строк по всем движкам
5. Для правок в схемах — `init_schema` дважды подряд без ошибок (идемпотентность)
6. Документация в `docs/` обновлена, если менялось поведение или контракт

Пункт 4 — главная проверка этого проекта: расхождение числа строк между движками означает,
что адаптеры разошлись, и юниты этого не поймают.

## Проверка перед сдачей

```bash
python -m pytest -q
python -m ruff check .
docker compose up -d
python -m etl all          # три раза loaded: N с одинаковым N
python -m bi all           # без дублей карточек
```
