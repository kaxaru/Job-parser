# Тесты и критерии приёмки

## Запуск

```bash
python -m pytest                  # 220 unit; integration отфильтрованы (по умолчанию)
python -m pytest -m integration   # 7 тестов на реальных PG + ClickHouse + MS SQL — ОСОЗНАННО
python -m ruff check .            # линтер, свой конфиг
```

> ⚠ `-m integration` **делает TRUNCATE базы `hh`**. Только на тестовой базе или в CI,
> никогда на стенде с данными, которые жалко.

Числа — прогон 09.08.2026 (227 собирается: 220 unit + 7 integration). Набор растёт,
поэтому единственный источник истины — сама команда; если она даёт другое число,
правится этот файл, а не память.

## Маркеры и защита по умолчанию

`pytest.ini`:

```ini
addopts = --strict-markers --strict-config -ra -m "not integration"
xfail_strict = true
markers =
    unit: быстрые тесты без внешних зависимостей (домен, оркестрация на фейках)
    integration: требуют живых Postgres/ClickHouse (CI service containers)
    real_fx: тест проверяет САМ загрузчик курсов — не подменять его синтетикой (conftest)
```

**`-m "not integration"` в `addopts`** — защита от разрушительного прогона по привычке.
Раньше голый `python -m pytest` собирал весь набор и на поднятом стеке стирал демо-данные;
теперь он берёт только безопасное большинство.

Аргумент командной строки перекрывает `addopts`, поэтому явный `-m integration`
по-прежнему работает — запуск деструктивных тестов стал осознанным действием,
а не поведением по умолчанию.

**`--strict-markers`** — опечатка в имени маркера становится ошибкой, а не молчаливым
пропуском теста.

**`--strict-config`** — опечатка в самом `pytest.ini` тоже ошибка. Это защита именно для
строки `addopts`: испорченный ключ молча снял бы фильтр интеграционных тестов.

**`xfail_strict`** — починенный `xfail` обязан стать красным, иначе набор годами носит
«ожидаемое падение», которого давно нет.

**`conftest.py::pytest_collection_modifyitems`** навешивает `unit` на всё, что не помечено
`integration`. Локально отбор идёт по `-m "not integration"`, в CI — по `-m unit`
(`.github/workflows/ci.yml`, джоба `unit`); пока маркер ставился руками, эти два отбора
расходились молча — файл с забытым `pytestmark` локально шёл, а в CI не выполнялся вовсе.
`--strict-markers` ловит ОПЕЧАТКУ в маркере, но не его ОТСУТСТВИЕ, поэтому маркер
навешивается автоматически, а не проверяется.

## Курсы валют в юнит-прогоне

С 09.08.2026 домен переводит вилки в рубли (`etl/rates.py`), а курсы по умолчанию берёт
из суточного кеша родителя `data/fx_rates.json`. В тот же день юнит-тесты стали зависеть
от того, лежит ли этот файл на диске запускающего и какой в нём сегодня курс, — ровно тот
класс дефекта, который аудит того же дня разбирал у родителя («тест зелёный, потому что
читает чужое состояние машины»).

Ответ — autouse-фикстура `conftest.py::_fx_rates_are_synthetic`: она подменяет
`rates.load_rates` круглыми синтетическими курсами (`FX_FOR_TESTS`), намеренно НЕ равными
рыночным. Правило, ради которого она заведена: **прогон на чистом клоне и на машине
владельца обязан давать один результат**; юнит не смеет зависеть от того, что лежит
на диске. Круглые курсы дают ещё и побочную пользу — ожидаемые рубли пишутся литералом
(`45 000 EUR -> 45 000 / 0.5 * 100`), а не пересчитываются в тесте той же формулой,
что и в коде.

Опт-аут — маркер **`real_fx`**, и он нужен ровно тем двум тестам, чей ПРЕДМЕТ и есть сам
загрузчик курсов (`test_load_rates_reads_parent_cache`,
`test_load_rates_without_file_degrades_to_empty`): подменять то, что проверяешь,
бессмысленно. Оба работают на своём `tmp_path`, а не на боевом кеше.

Интеграционный прогон закрепляет курсы файлом `tests/fixtures/fx_rates.json` (фикстура
`cfg` проставляет `FX_FILE`): в данных есть вилки в EUR/USD/BYN, и на живых курсах «числа
сошлись» означало бы в понедельник не то же, что в пятницу, а в CI кеша нет вовсе.

## Что покрыто

**`tests/test_domain.py`** (108) — разбор сырой записи без БД: канонизация валюты
(`RUR->RUB`, `BYR->BYN`, `USDT->USD`, пустая -> `None`) и конверсия вилки в
`salary_min_rub`/`salary_max_rub`, справочники опыта и графика, пустая строка внешнего
источника как отсутствие значения, разделение `is_remote` (коды `remote` + `flexible`)
и `remote_mentioned` (словесный маркер в тексте), стек из кеша родителя `_techs` при
совпадении `_dv` с `PARENT_DETECT_SIG` и пересчёт своим словарём при протухшем `_dv`,
строковый неймспейс-`id`, поле `source` и кап городов `CITY_MAX`.

Отдельный блок того же файла — **страж-тесты копий родителя**. Стенд не импортирует
`hrwork`: каталог `etl/` монтируется в контейнер Airflow без родительского пакета,
поэтому `REMOTE_LIKE_CODES`, `REMOTE_MARKERS`, `CURRENCY_ALIAS` и часть словаря стека
СКОПИРОВАНЫ. Копия без стража расходится молча, и два проекта начинают публиковать разные
доли удалёнки по одному срезу. Стражи читают константы **из исходников родителя AST-разбором,
а не импортом**: `import hrwork.config` на импорте делает `mkdir data/` и `logs/`,
`load_dotenv`, переконфигурирует loguru и читает `resume_profile.json` — юниту стенда нужен
текст константы, а не побочные эффекты. Исключение — `hrwork/domain/schedule.py`: там чистый
enum, его импортируем как есть. Отдельно стережётся пин `PARENT_DETECT_SIG`
(`test_parent_detect_sig_pin_is_current` пересчитывает blake2s по `TECH_PATTERNS` родителя):
протухший пин не ломает прогон, а тихо отключает переиспользование кеша `_techs`.
Если пакета родителя рядом нет, блок пропускается по `skipif`.

**`tests/test_pipeline.py`** (32) — оркестрация на фейковых хранилищах: соответствие порту
ТРЁХ продуктовых адаптеров (а не только фейка), порядок шагов `init -> load` журналом
вызовов, дедуп по id, отбраковка с ИМЕНЕМ причины (`no_id`/`broken`/`dup`), кэш `prepare`
через результат, санити-гейты перезалива (пустой вход, просадка ниже 50 % от факта,
`--force`, недоступный прошлый объём, гейт проверяет все хранилища ДО загрузки первого),
гейт брака (`> 1 %` неразобранных роняет прогон) и сверка `verify`: движок, потерявший
строки, красит прогон и называется по имени.

**`tests/test_cli.py`** (22) — argparse обоих пакетов и wiring: повторяемый `-t`, валидация
шага, `--force` только явным флагом, порядок реестра бэкендов, сборка адаптеров из явного
`cfg` (фикстура `no_env` роняет тест, если фабрика полезет в окружение — `PGPORT=abc`
из чужой оболочки уже ронял wiring), литеральные заголовки пяти дашбордов и литеральный
набор провижининга по умолчанию.

**`tests/test_bi_client.py`** (17) — фасад Metabase на замоканном `_api`: логин и деградация
до обычного логина, когда `/api/session/properties` недоступен; идемпотентность
`ensure_database` (найденное подключение переиспользуется, отсутствующее создаётся
и синхронизируется) и `upsert_dashboard` (старые карточки уходят в архив); ответ `202`
как успех; все ошибочные ветки HTTP названы статусом и телом.

**`tests/test_bi_dashboards.py`** (10) — подписи карточек и заголовки всех пяти дашбордов
на фейковом фасаде, без HTTP. Заголовок — ключ идемпотентного upsert, подпись — контракт

**`tests/test_sql_schema.py`** (27) — что стережём в DDL без БД: ширину ключа вакансии

**`tests/test_search_demo_schema.py`** (4) — схема витрины поиска через `ast`, без БД:

с назначением каждого и отсутствие второй копии `strip_html` в загрузчике.

**`tests/integration/test_warehouses.py`** (7) — реальные PostgreSQL, ClickHouse **и MS SQL**
(параметризация по `TARGETS`): схема создаётся идемпотентно, загрузка кладёт ожидаемое число

**`tests/fixtures/sample_vacancies.json`** — 9 записей = 9 классов боевых данных (см. ниже).

## Фикстура обязана представлять КЛАССЫ данных

Главный урок 09.08.2026. Интеграционная фикстура состояла из пяти записей с id `"1"`..`"5"`,
и на них сходилось что угодно: таргет MS SQL с ключом `id NVARCHAR(80)` проходил тест
зелёным, не будучи способен загрузить боевые данные вовсе — himalayas и arbeitnow неймспейсят
id слагом, и в срезе есть id длиной до 144 символов. Дефект нашёл аудит, а не набор.

Теперь в фикстуре по одной записи на класс: свежий и протухший кеш стека родителя (`_dv`),
отсутствующая вилка, вилка `net`, валюта BYR (канонизируется в BYN) и незнакомый код
графика `shift`, пустые работодатель/опыт/график/город, слаг-id 108 и 144 символа,
локация-сентинел `Remote`, город-агрегатор длиной 202 символа (домен режет его до `CITY_MAX`).

Отдельно — **пара arbeitnow с общим 80-символьным префиксом id** (`…-253251` и `…-253252`:
совпадают первые 107 символов, различаются последние). Класс живой — портал плодит слаги
локацией, — и он же детектор молчаливого усечения ключа: сузь колонку обратно, и две записи
схлопнутся в одну, `count()` вернёт 8 вместо 9. Одна длинная запись такого не поймала бы:
усечение до 80 символов дало бы ровно те же 9 строк, «просто загрузилось».

Смысл каждой записи выписан в докстринге `tests/integration/test_warehouses.py` — туда же
смотреть при правке фикстуры.

## Правило владельца

Действует на оба проекта, полностью — [`../../docs/testing.md`](../../docs/testing.md#главное-правило).
Коротко:

- **Ожидаемое значение пишется ЛИТЕРАЛОМ до запуска кода.** `expected`, подогнанный под
  фактический вывод, фиксирует баг, а не требование. Литерал, а не вычисление той же
  формулой из того же места, что и реализация
- **Точное значение, а не обобщённый булев.** Никаких `assert is_ok` / `assert result` /
  `len(x) > 0` / `assert all(...)`: `assert all(c == 9 for c in {}.values())` истинно
  ВАКУУМНО — так «все движки сошлись» и оставалось зелёным на нуле движков
- **Имена — из словаря спецификации**, не из кода: тест называет свойство, а не функцию
- **Детали реализации в тест не протекают**: только вход и наблюдаемый результат.
  Кэш проверяется подменой источника, а не счётчиком обращений к фейку
- **Однотипные входы — через `@pytest.mark.parametrize`, не циклом.** Цикл падает на первом
  случае и скрывает остальные; параметризация называет виновный вход в отчёте. Тем же
  «скрытым циклом» считается цепочка `assert a and b` — вместо неё один кортежный assert,
  который печатает обе стороны расхождения целиком

Критерий: тест должен быть написуем по одной спеке, не открывая код.

## Пирамида

Основание — юниты на чистых функциях (`domain`), на фейках (`pipeline`, `cli`, `bi`)
и на исходниках как на тексте (`sql_schema`, `search_demo_schema`, страж-тесты домена).
Интеграция — только там, где есть настоящий внешний контракт: SQL-диалект и поведение
движка. E2E нет: полный прогон требует всех 12 контейнеров и проверяет ровно то же,
что интеграционные тесты.

Все три адаптера (PG, ClickHouse, MS SQL) покрыты интеграционным тестом через параметризацию
по `TARGETS` и присутствуют в CI-матрице.

## Пробелы

Признаём честно:

- **DAG** — не тестируется (ни импорт, ни структура графа)
- **`observability/`** — конфиги не валидируются
- **`bi/client.py::run_sql`** — единственный метод фасада, чьи ошибочные ветки не покрыты:
  на ошибке он молча отдаёт `[]`. Остальные (`connect`, `create_card`, `find_database`/
  `ensure_database`, `upsert_dashboard`) названы статусом и телом ответа и покрыты
- **`search_demo/`** — загрузчик не импортируется в юнитах: он тянет пакет `hrwork`,
  которого нет в `requirements-dev.txt` подпроекта, и требует живого Postgres. Проверяется
  по ИСХОДНИКУ (`test_search_demo_schema.py`), то есть схема и индексы застрахованы,
  а поведение загрузки — нет
- **`domain.py::strip_html`** — поведения не проверяет ни один тест: застрахован только
  запрет второй копии функции в загрузчике поиска. Вход с тегами и HTML-сущностями ->
  ожидаемая строка литералом — самый дешёвый непокрытый юнит набора

## CI

`.github/workflows/ci.yml` (в корне `hr_work/`, покрывает и подпроект) реально существует
и запускается на push/PR. Jobs: `unit` (`pytest -m unit`), `integration` (`pytest -m
integration` на сервис-контейнерах **postgres + clickhouse + mssql**), `scraper`
(pytest основного проекта), `biome`/`js-unit` (фронт), `build`. Репозиторий под git
(ветка `dev`, `origin` на GitHub).

## Критерии приёмки

Задача считается выполненной, когда:

1. `python -m pytest` зелёный на всём unit-наборе (на 09.08.2026 — 220 тестов)
2. `python -m ruff check .` без замечаний
3. Новое поведение покрыто тестом, имя которого называет **свойство**, а не функцию
4. Для правок в адаптерах — прогон `python -m etl -t <backend> all` с совпадающим
   числом строк по всем движкам
5. Для правок в схемах — `init` -> изменить определение витрины -> `init` -> витрина отдаёт
   НОВОЕ определение (витрины пересоздаются, а не создаются `IF NOT EXISTS`)
6. Документация в `docs/` обновлена, если менялось поведение или контракт

Пункт 4 — главная проверка этого проекта, и с 09.08.2026 её делает не человеческий глаз
по трём строкам stdout, а `Pipeline._verify`: расхождение числа строк между движками
означает, что адаптеры разошлись, и роняет прогон, назвав отставший движок.

Пункт 5 переформулирован в тот же день. «`init_schema` дважды подряд без ошибок» проходил
и тогда, когда правка определения витрины не доезжала до движка вовсе: `CREATE ... IF NOT
EXISTS` молча оставлял старую версию, и PG расходился с MS SQL (`CREATE OR ALTER VIEW`)
навсегда при зелёной проверке.
