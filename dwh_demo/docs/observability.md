# Наблюдаемость — Grafana, Loki, Promtail, MinIO

**Конфиги:** `observability/` — всё как код, поднимается вместе со стеком, без кликов в UI.

## Поток

```
контейнеры проекта
      │  docker_sd
      ▼
   Promtail          сбор, парсинг уровня в метку level
      │
      ▼
    Loki             хранение; чанки -> MinIO (S3), retention + лимиты
      │
      ▼
   Grafana  ◄──── hh-postgres (БД airflow): статусы и длительности прогонов
            ◄──── hh-postgres (БД hh):      объём и свежесть core.vacancies
```

Три источника в одном месте: логи всего стека из Loki, метрики оркестратора прямо из
метаданных Airflow и результат заливки из самой витрины.

## Файлы

- `grafana-datasources.yml` — Loki и два Postgres-источника (`HH-Postgres` — БД `airflow`,
  `HH-DWH` — БД `hh`), с фиксированными `uid`
- `grafana-dashboards.yml` — провайдер дашбордов
- `dashboards/pipeline-health.json` — дашборд «здоровье пайплайна», 8 панелей
- `loki-config.yaml` — прод-конфиг: S3 (MinIO), retention, лимиты
- `promtail.yml` — `docker_sd`, фильтр по проекту, `pipeline_stages` для разбора `level`

Фиксированные `uid` в datasources нужны, чтобы дашборд ссылался на источник по
стабильному идентификатору — иначе после пересоздания стека панели теряют привязку.

Второй Postgres-источник появился потому, что **состояние прогона и результат заливки —
разные вещи**: `load` делает TRUNCATE и рапортует `success` даже на нулевом срезе. Пока
источника `HH-DWH` не было, подхватить число строк в `core.vacancies` было нечем, и дашборд
«здоровье пайплайна» оставался зелёным при пустой витрине.

Docker-сокет проброшен в Promtail с `:ro` — это **косметика, а не защита**: флаг ограничивает
bind в файловой системе, а не Docker API поверх сокета. Держим для единообразия с
родительским стеком; по существу закрывается только docker-socket-proxy или файловый скрейп
json-логов.

## Дашборд «здоровье пайплайна»

`http://localhost:3001/d/hh-pipeline-health` (`admin` / `DwhDemo2026!`)

Восемь панелей тремя группами:

- **оркестратор** (источник `HH-Postgres`, БД `airflow`) — «Последний прогон hh_etl»,
  «Успешных прогонов (7 дней)», «Длительность задач по времени (сек)», таблица «Последние
  прогоны hh_etl»
- **результат** (источник `HH-DWH`, БД `hh`) — «Строк в `core.vacancies`» и «Свежесть:
  залито за 24 ч» (по колонке `core.vacancies.loaded_at`). Именно эти две отвечают на
  вопрос «данные приехали?», на который зелёный DAG-ран не отвечает
- **логи** (источник `Loki`) — «Логи по уровням во времени» и «Логи стека»

## Сигналы поломки ETL

Конвейер не пишет в файлы: `pipeline.py::log` — это `print` в stdout, `log_error` — в stderr.
В эксплуатации поломка видна по строкам:

- **`[etl] ERROR ...`** — аварийная строка прогона, единственный маркер уровня в потоке.
  Обычный `[etl] [postgres] loaded: 0` в Loki неотличим от успеха, поэтому у аварий есть
  своя подстрока. Её дают ровно пять событий, все — в `etl/pipeline.py`:
  битых записей больше 1 % (`_check_broken_share`), `prepare` вернул ноль вакансий (`load`),
  вход просел больше чем вдвое относительно факта (`_reject_degraded`), падение адаптера
  на середине fan-out (`load`), расхождение факта с `prepare` (`_verify`)
- **`[etl] verify: prepare=N, в факте {...}`** — главная проверка проекта. Строка печатается
  всегда; расхождение дополнительно роняет прогон с `[etl] ERROR`
- **`[etl] prepare: N вакансий ...; пропущено: no_id=.. broken=.. dup=..`** — счётчики
  отбраковки по причинам. Рост `broken` — смена формата у родителя, рост `dup` — пересечения
  порталов; без разбивки по причинам обе выглядят одинаково («стало меньше»)
- **`[etl] FX: ...`** — нет кеша курсов. Прогон продолжается, но рублёвые колонки пустые

Где искать. При ручном прогоне — в консоли (и в `logs/cron_collect.log`, куда крон сводит
оба потока). В Airflow — во вкладке Log таски: task-логи Airflow пишет через `FileTaskHandler`
в том `airflow-logs`, а Promtail собирает stdout/stderr контейнеров, поэтому рассчитывать,
что маркер сам приедет в Loki из этой ветки, нельзя. Отдельных панелей и правил алертинга по
этим сигналам пока нет — маркер введён как точка, к которой такое правило можно привязать
(`{project="hh-dwh"} |= "[etl] ERROR"`).

## Ad-hoc логи

`http://localhost:3001/explore` -> datasource **Loki**:

```logql
{level="ERROR"}                                            # ошибки по всему стеку
{container="hh-postgres"}                                  # логи Postgres
{container="hh-mssql"}                                     # логи MS SQL
sum by (level) (count_over_time({project="hh-dwh"}[5m]))   # логи по уровням
{project="hh-dwh"} |= "[etl] ERROR"                        # аварии ETL, см. выше
```

Promtail собирает логи **всех** контейнеров проекта автоматически через `docker_sd` —
mssql и minio тоже, без отдельной настройки. `level` парсится под формат каждого сервиса.

Только контейнеров: файловые логи родителя (`../logs/*.log`) Promtail стенда не читает,
поэтому маскировка тел сообщений у родителя (`config.py::body`) на здешние парсеры уровня
никак не влияет.

## MinIO как S3 для Loki

`http://localhost:9003` (`minioadmin` / `minioadmin`), бакет `loki` — там физически
лежат чанки.

**Бакет создаёт `minio-init`**, одноразовый сервис: Loki сам бакет не создаёт и без него
молча не пишет.

## Крайние случаи

- **Чанки не появляются сразу** — flush по таймеру, idle 30 минут. Форсировать:
  `curl -XPOST localhost:3100/flush`
- **«entry too old»** — прежняя причина (рестарт Promtail) устранена 09.08.2026: позиции
  чтения лежат в томе `promtail-pos`, без него `/tmp` был эфемерным и сборщик после каждого
  `docker compose restart promtail` перечитывал историю ВСЕХ контейнеров с нуля, упираясь
  в `reject_old_samples_max_age: 168h`. Если строка появилась снова — это чужие контейнеры
  с древней историей либо смена схемы Loki: сбросить том `loki-data`,
  см. [`deployment.md`](deployment.md)
- **Дашборд не обновился** — provisioning перечитывает файл за ~10 секунд; либо бампнуть
  `"version"` в JSON, либо `docker compose restart grafana`
- **Панели оркестратора пустые** — Airflow ещё не делал прогонов, либо БД `airflow` не
  создана (скрипт `postgres/init/` отрабатывает только при первом старте тома)
- **«Строк в `core.vacancies`» пусто или ошибка** — схема ещё не создана (`python -m etl
  init`) либо факт не заливался. Ноль строк при зелёном DAG-ране — ровно тот случай, ради
  которого панель и заведена

## Почему конфигурация в коде

Кликнутая в UI настройка живёт в томе и теряется при `docker compose down -v`.
Provisioning-файлы переживают сброс и видны в диффе — тот же принцип, что и для дашбордов
Metabase.

## Проверка

```bash
curl -s localhost:3100/ready                 # Loki готов
curl -s localhost:3001/api/health            # Grafana
docker compose logs promtail --tail 20       # сборщик видит контейнеры
```

Ожидаемо: Loki `ready`, Grafana `{"database":"ok"}`, в Explore по `{project="hh-dwh"}`
идут строки.
