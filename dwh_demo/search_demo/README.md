# Search PoC — нужен ли tsvector? нужен ли Elasticsearch?

Учебный стенд: измерить на ЖИВЫХ данных (9 751 вакансий из `data/vacancies_raw.json`),
какой поиск реально нужен `hr_work`, а не решать на веру.

## Запуск

Нужен поднятый `hh-postgres` (dwh_demo, порт 5433):

```bash
.venv3/Scripts/python.exe dwh_demo/search_demo/load.py    # грузит + строит индексы (idempotent)
.venv3/Scripts/python.exe dwh_demo/search_demo/bench.py   # измеряет -> REPORT.md (UTF-8)
```

Что строится в `search_demo.vacancies`: `tsvector` (заголовок весом A, описание B) + GIN,
trigram-GIN (`pg_trgm`) по `name`, btree по `city`/`sal_mid`.

## Что показали измерения (PG 16, 9.7k строк)

Кейс «python backend в Москве с зарплатой ≥ 200 000» — оба подхода находят **одни и те же 15 строк**:

- **наивный ILIKE** (`...ILIKE '%python%' AND ...'%backend%'` по тексту): **~30 мс**, текст фильтруется построчно (индекс берётся только под `city`).
- **tsvector + GIN**: **~1.1 мс** — текст ищется прямо по индексу. **≈26× быстрее.**

Кроме скорости tsvector даёт то, чего у `LIKE` нет в принципе:

- **Точность.** `ILIKE '%java%'` = 1125 строк, токен `tsquery 'java'` = 573 → **552 ложных** (`javascript`, `java-script`). Подстрока ловит мусор, токен — нет.
- **Морфология.** `tsquery 'программист'` цепляет программист/-а/-ов/-ы (стемминг) — 2571 строка одним термом.
- **Ранжирование.** `ts_rank(doc, q)` сортирует по релевантности (вес A/B); у `LIKE` ранга нет.
- **Опечатки.** trigram `word_similarity` + `<%` (индекс): `'pyton'` → находит «Разработчик Python», ~6 мс. Это покрывает fuzzy-кейс, ради которого часто смотрят на ES.
- **Фасеты.** `GROUP BY unnest(techs)` — счётчики для UI-фильтров за ~18 мс.

## Вывод для hr_work

1. **Сейчас (4 МБ, фильтр в JS на фронте)** — ничего не нужно, клиентского фильтра достаточно.
2. **Если поиск переедет на сервер** (поисковая строка → бэкенд, или данные перестанут влезать в браузер) — **PostgreSQL `tsvector`**: PG уже в стеке, одна колонка + GIN, даёт точность + ранжирование + морфологию + опечатки. Замерено: 1–6 мс. Отдельный сервис не нужен.
3. **Elasticsearch — НЕ нужен** на этом объёме. Он окупается при: сотнях тысяч+ документов И высоком QPS, ИЛИ продвинутых требованиях (typeahead-автодополнение под нагрузкой, синонимы, обучаемое ранжирование, фасеты по огромной кардинальности), ИЛИ если ELK уже стоит под логи. Иначе это лишний JVM-кластер + синхронизация данных из БД (лаг, рассинхрон).

**Порог простыми словами:** Postgres FTS спокойно тянет до миллионов строк. Пока ты не упёрся в это ИЛИ в продвинутый поисковый UX — `tsvector` выигрывает у ES по совокупной стоимости с разгромом. У тебя 9.7k строк — ES здесь это из пушки по воробьям.

Свежие числа всегда в `REPORT.md` (перегенерируется `bench.py`).
