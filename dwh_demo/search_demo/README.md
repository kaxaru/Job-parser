# Search PoC — нужен ли tsvector? нужен ли Elasticsearch?

Учебный стенд: измерить на ЖИВЫХ данных (весь кеш `../../data/vacancies_raw.json` —
на 08.2026 порядка 110 тыс. записей с девяти порталов), какой поиск реально нужен
`hr_work`, а не решать на веру.

## Запуск

Нужен поднятый `hh-postgres` (dwh_demo, порт 5433):

```bash
python dwh_demo/search_demo/load.py    # грузит + строит индексы (idempotent; venv активирован)
python dwh_demo/search_demo/bench.py   # измеряет -> REPORT.md (UTF-8)
```

Что строится в `search_demo.vacancies`: `tsvector` (заголовок весом A, описание B) + GIN,
trigram-GIN (`pg_trgm`) по `name`, btree по `city`/`sal_mid`, постраничные индексы
`ix_salmid_page`/`ix_salmidrub_page` под `ORDER BY … DESC NULLS LAST, id`, а также колонка
`source` с индексом `ix_source` (фильтр портала на `/search`).

**Зарплата хранится дважды.** `sal_from`/`sal_to`/`sal_mid` — как пришло, в валюте портала:
это годится только для показа в карточке. Сравнивать и сортировать можно ТОЛЬКО по
`sal_mid_rub` — рублёвому эквиваленту по курсам `data/fx_rates.json`. В кеше 45 кодов
валют, и общая шкала по сырым суммам ставила на первую страницу узбекские вилки
(50 000 000 UZS), а фильтр «з/п от 200 000» выбрасывал все долларовые. Нет курса или нет
валюты -> `sal_mid_rub IS NULL`: вакансия выпадает из сравнения, но остаётся в выдаче.

**Индекса по `created_at` нет** (был `ix_created`, убран 09.08.2026). Единственный запрос
по дате — фильтр свежести `search.py::_FRESH_WHERE`, и он считает возраст выражением
`floor(extract(epoch from now() - created_at) / 86400)`: btree по голой колонке под такой
предикат планировщик не подставляет, а выражение-индекс невозможен — `now()` не IMMUTABLE.
Индекс не использовался ни одним запросом и только удорожал заливку. Вернуть его имеет
смысл вместе с саргабельной формой предиката (`created_at > now() - interval '31 days'`,
тождественно `floor(...) <= 30`) — правка на стороне родителя.

## Что показали измерения (PG 16)

Все числа ниже — из `REPORT.md` последнего прогона `bench.py`. README пишется руками,
`REPORT.md` генерируется: **при расхождении верить `REPORT.md`.**

Кейс «python backend в Москве с зарплатой ≥ 200 000 ₽»:

- **наивный ILIKE** (`...ILIKE '%python%' AND ...'%backend%'` по тексту): **25.5 мс**, текст фильтруется построчно (индекс берётся только под `city`).
- **tsvector + GIN**: **2.1 мс** — текст ищется прямо по индексу. **≈12× быстрее.**

Выдачи при этом НЕ совпадают: ILIKE находит 47 строк, tsvector — 45. Разница — подстроковые
ложные срабатывания против токенов; см. «Точность» ниже.

Кроме скорости tsvector даёт то, чего у `LIKE` нет в принципе:

- **Точность.** `ILIKE '%java%'` = 2256 строк, токен `tsquery 'java'` = 1356 → **900 ложных** (`javascript`, `java-script`). Подстрока ловит мусор, токен — нет.
- **Морфология.** `tsquery 'программист'` цепляет программист/-а/-ов/-ы (стемминг) — 3173 строки одним термом.
- **Ранжирование.** `ts_rank(doc, q)` сортирует по релевантности (вес A/B); у `LIKE` ранга нет.
- **Опечатки.** trigram `word_similarity` + `<%` (индекс): `'pyton'` → находит «QA Automation (Python)», 18.3 мс. Это покрывает fuzzy-кейс, ради которого часто смотрят на ES.
- **Фасеты.** `GROUP BY unnest(techs)` — счётчики для UI-фильтров за 28.6 мс.

## Вывод для hr_work

1. **Серверный поиск уже включён.** Вывод PoC реализован: `/api/search` работает через
   `tsvector` по этой самой таблице (`hrwork/infrastructure/search.py`). Клиентский фильтр
   остался только у ленты, и он давно не «4 МБ»: `data/feed-data.js` — 61 МБ,
   `data/feed-desc.js` — 261 МБ.
2. **Почему PostgreSQL, а не отдельный движок.** PG уже в стеке, одна колонка + GIN дают
   точность + ранжирование + морфологию + опечатки. Замерено: 1–6 мс. Отдельный сервис
   не нужен.
3. **Elasticsearch — НЕ нужен** на этом объёме. Он окупается при: сотнях тысяч+ документов И высоком QPS, ИЛИ продвинутых требованиях (typeahead-автодополнение под нагрузкой, синонимы, обучаемое ранжирование, фасеты по огромной кардинальности), ИЛИ если ELK уже стоит под логи. Иначе это лишний JVM-кластер + синхронизация данных из БД (лаг, рассинхрон).

**Порог простыми словами:** Postgres FTS спокойно тянет до миллионов строк. Пока ты не упёрся в это ИЛИ в продвинутый поисковый UX — `tsvector` выигрывает у ES по совокупной стоимости с разгромом. На порядке 110 тыс. строк ES здесь всё ещё из пушки по воробьям.

Свежие числа перегенерирует `bench.py`; объём выборки в заголовке `REPORT.md` теперь
считается прогоном, а не захардкожен (до 09.08.2026 там стояло «9.7k» при кеше на порядок
больше).
