## 🔴 Разрушительные команды

**`python -m pytest -m integration` делает TRUNCATE базы `hh`** — на поднятом стеке
сотрёт демо-данные. Запускать только на тестовой базе или в CI.

Голый `python -m pytest` безопасен: `pytest.ini` содержит `-m "not integration"`
в `addopts`, поэтому берёт 40 юнитов и не трогает БД. **Эту строку не убирать** — она
и есть защита от разрушительного прогона по привычке.

**`docker compose down -v`** удаляет тома: базы, метаданные Airflow, настройки Metabase,
чанки логов. Без `-v` данные переживают перезапуск.

**`python -m etl load`** перезаливает факт целиком (`TRUNCATE` / `DELETE` в core).
Это штатно и идемпотентно, но на общей БД затрёт чужой прогон.

## Конвенции

**Новый бэкенд = адаптер + строка в реестре.** `warehouse/base.py::Warehouse` — порт из
трёх методов. Если правка требует трогать `Pipeline`, значит абстракция протекла.

**Transform живёт в `domain.py` и делается один раз.** Адаптер не парсит сам: разойдясь
в разборе, движки дадут разные цифры на одном входе, и сравнение потеряет смысл.

**`domain.py` — без БД и I/O.** Импорт драйвера в доменный модуль — ошибка проектирования.

**Драйверы опциональны.** `pymssql` импортируется лениво внутри `_conn`: его отсутствие
не должно ломать импорт пакета (например, в Airflow без mssql-таргета).

**Идемпотентность обязательна** для `init_schema`, `load` и провижининга BI. Повторный
запуск не должен дублировать данные или карточки.

**Совпадение чисел по бэкендам — главная проверка.** `loaded: N` должно быть одинаковым
для всех движков; расхождение означает, что адаптеры разошлись, и юниты этого не поймают.

## Свои конфиги

У подпроекта **собственные** `ruff.toml` (`target-version = py310`, line-length 110)
и `pytest.ini` — оба инструмента выбирают ближайший к файлу конфиг, родительские правила
сюда не применяются.

```bash
python -m ruff check .        # из dwh_demo/, не из корня
python -m pytest
```

## Окружение

Настройки только из окружения, дефолты — под локальный compose. `PGPORT` по умолчанию
**5433**, не 5432.

Хост зависит от того, откуда запускают: с машины — `localhost`, из контейнера Airflow —
имя сервиса (`PGHOST=hh-postgres`, `MSSQL_HOST=hh-mssql`). Забытый `MSSQL_HOST` — типовая
причина падения таски `load_mssql`.

Логи проект в файлы не пишет: `pipeline.py::log` — это `print` в stdout, логи контейнеров
собирает Promtail. Если понадобится редирект вручную — класть в `../logs/`, как принято
в родительском проекте.

## Известные пробелы

Не выдавать за сделанное: сами определения дашбордов `bi/dashboards/*` не тестируются
(реестр покрыт), DAG не проверяется даже на импорт, конфиги `observability/` не
валидируются. Подробности — [`docs/testing.md`](docs/testing.md).

Покрыто (не пробел): все три адаптера (PG/ClickHouse/MS SQL) — интеграционным тестом
через параметризацию по `TARGETS`; CI (`.github/workflows/ci.yml`) реально существует
и гоняет unit + integration (с mssql-контейнером) + фронт на push/PR.
